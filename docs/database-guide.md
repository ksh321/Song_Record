# 노래 기록 앱의 DB 작업 안내

## DB가 맡는 일

DB는 앱이 정보를 잊지 않도록 보관하는 장부다. 회원, 곡, 녹음 정보, 플레이리스트, 태그를 서로 연결한다. 예를 들어 플레이리스트에는 노래 파일을 복사하는 대신 어떤 곡이 몇 번째에 들어가는지 기록한다.

| 구성 | 쉬운 설명 | 이 앱에서 맡는 일 |
|---|---|---|
| Flutter 앱 | 사용자가 조작하는 화면 | 녹음하고 곡·메모를 입력한다 |
| 휴대폰 로컬 DB | 휴대폰 안의 장부 | 인터넷 없이 기록하고 나중에 동기화한다. P04-08 이후 연결 예정 |
| Spring Boot 서버 | 요청을 확인하고 처리하는 담당자 | 로그인, 소유권, 수정 규칙을 검사하고 서버 DB에 기록한다 |
| MySQL | 서버의 장부 | 회원·곡·녹음 정보·목록과 관계를 보관한다 |
| 휴대폰 저장공간과 R2 | 녹음 파일 보관함 | 휴대폰에 원본을 두고, 선정된 파일을 비공개 R2에 보관한다. R2 연동은 후속 작업 |

녹음 제목·메모·길이 같은 정보와 실제 M4A 파일은 다르다. 서버 파일 공간이 부족해도 기록과 메모를 남길 수 있도록 두 가지를 분리한다.

## 이번 P04 작업

P04는 장부의 칸과 연결 규칙을 만드는 단계다. 이를 스키마라고 부른다. 테이블은 장부의 종류, 행은 기록 하나, 열은 이름·날짜 같은 항목이다.

P04-01은 회원과 로그인 수단, P04-02는 내 곡, P04-03은 녹음과 파일 정보의 구조를 만들었다. P04-04는 플레이리스트와 태그·컨디션을 추가한다. 이 단계만으로 앱 화면에서 해당 기능을 전부 사용할 수 있게 되는 것은 아니다. 요청 처리와 화면 연결은 후속 단계에서 진행한다.

DB에도 규칙을 넣는다. 예를 들어 한 목록에 같은 곡이 두 번 들어가거나, 다른 회원의 곡을 내 목록에 연결하려 하면 DB가 거절한다. 화면이나 서버의 실수가 있더라도 마지막 저장 지점에서 잘못된 관계를 막는다.

## 2026년 9월 21일 수정 내용

| 기존 문제 | 쉬운 예 | 수정 결과 |
|---|---|---|
| 키 정보의 일부 누락 허용 | 남성 키라고만 적고 몇 반음인지 비워 둠 | 필요한 두 값이 모두 있어야 저장 |
| 활성 업로드의 빈 슬롯 허용 | 번호표 없이 대기열에 들어가 동시 2개 제한을 피함 | 진행 중 업로드는 0번 또는 1번 슬롯 필수 |
| 파일 세대 번호 형식 불일치 | 파일의 교체 이력을 단순 숫자로 구분 | 설계대로 UUID를 사용하고 기존 숫자 대응도 보존 |
| 저장과 파일 명세 삭제의 동시 처리 | 한쪽에서 저장을 확정하는 동안 다른 쪽에서 필요한 파일 정보를 삭제 | 서로 순서를 맞춰 저장된 명세를 보호 |

P04-04에서는 같은 곡을 서로 다른 플레이리스트에 넣을 수 있다. 한 플레이리스트 안의 중복은 막는다. 금영 검색 결과는 곧바로 개인 목록에 저장하지 않고, 후속 화면에서 TJ 결과를 선택하는 정책을 유지한다.

태그는 여러 개 선택할 수 있고, 태그 이름을 바꾸거나 보관 처리해도 과거 녹음의 당시 이름이 유지된다. 컨디션은 매우 좋음·좋음·보통·안 좋음 중 하나 또는 미선택이다.

## DB를 바꾸는 방법

개발자가 DB를 매번 지우고 다시 만드는 대신, 변경 지시서를 순서대로 추가한다. 이 지시서를 마이그레이션이라고 부른다. Flyway가 적용 이력을 확인하고 아직 실행하지 않은 지시서만 실행한다.

| 파일 | 내용 |
|---|---|
| V1 | DB 변경 이력을 위한 기본 구조 |
| V2 | 회원·곡·녹음 구조 |
| V3 | 이번에 발견한 기존 제약과 파일 세대 문제 수정 |
| V4 | 플레이리스트·태그·컨디션 구조 |
| V5 | 보관 역할·고정 자리·파일 보호·정리 작업·개인 및 전체 사용량 구조 |

이미 V2까지 적용된 DB라면 다음에 개발용 서버가 정상 시작될 때 V3·V4·V5를 적용한다. V5까지 적용했다면 재시작 시 같은 변경을 반복하지 않고 기존 파일과 이력이 일치하는지 검사한다. 기존 지시서를 수정하지 않은 이유도 이미 실행한 지시서의 내용을 바꾸지 않기 위해서다. 실제 적용 전 백업과 현재 데이터 점검이 먼저다.

단, 이 자동 적용은 DB에 연결하도록 설정한 `dev` 프로필에서 일어난다. 이 프로젝트의 기본 `bootstrap` 프로필은 DB 없는 서버 골격용이다. GitHub 업로드나 앱 실행만으로 모든 DB가 자동 변경되는 것은 아니다.

## 실제 적용 순서와 현재 상태

1. **코드 기록:** 변경 파일과 설명을 GitHub에 저장한다.
2. **자동 검사:** GitHub Actions가 임시 환경에서 앱·서버 빌드와 DB 검사를 실행한다. 테스트용 DB는 실제 개발 DB와 분리된다.
3. **적용 준비:** PC의 기존 DB 상태와 필요한 백업을 확인한다. 서버에 입력할 접속 정보는 기존 MySQL 설정과 일치시킨다.
4. **개발 DB 적용:** 최신 코드를 받은 뒤 Docker의 MySQL을 켜고 Spring Boot를 `dev` 프로필로 시작한다. Flyway가 남은 변경을 실행한다.
5. **결과 확인:** 서버가 정상 시작했고 Flyway 이력에 V1~V5가 성공으로 기록됐는지, 기존 곡·녹음이 유지되는지 확인한다.

이번 개발 작업에서는 별도 MySQL 8.4.11을 만들어 기존 검사 22개와 확장 검사 63개를 실행했다. 기존 데이터가 있는 업그레이드, 빈 DB 설치, 재실행 시 이력 검증도 확인했다. 사용자 PC의 기존 개발 DB에는 이번 V3·V4를 적용하지 않았다.

변경 코드는 GitHub main의 [602dab5](https://github.com/ksh321/Song_Record/commit/602dab5eee80de8161ebc589ee8ee303d93bdbcb)에 반영했다. 로컬 전체 Spring Boot 빌드는 작업 환경의 파일 접근 오류로 막혔지만, [GitHub 자동 검사](https://github.com/ksh321/Song_Record/actions/runs/35579131995)에서는 서버 전체 빌드·테스트와 DB 검사를 통과했다. DB 검사 통과와 전체 앱 완성은 다른 의미다. 최신 검증 상태는 [진행 기록](progress.md)과 [P04 검증 보고서](verification/P04-04-playlists-classifications.md)를 확인한다.

## 오류가 나면

이미 잘못된 키나 빈 슬롯 데이터가 있다면 V3가 멈출 수 있다. 이때 사용자 값을 추측해서 채우거나 DB 전체를 초기화하지 않는다. 어떤 행이 어떤 규칙을 어겼는지 확인한 뒤 보정 방법을 결정한다. MySQL의 구조 변경은 여러 단계가 한꺼번에 원상복구되지 않을 수 있어 실제 적용 상태와 Flyway 이력을 함께 확인해야 한다.

검증 스크립트는 합성 데이터를 넣는 시험 도구이므로 일상적으로 쓰는 DB에 그대로 실행하지 않는다. Docker의 `down -v`는 DB 저장공간까지 삭제하므로 단순 종료에는 사용하지 않는다. 정상 종료는 `docker compose stop`으로 충분하다.

구체적인 실행 명령은 [MySQL 개발 환경 안내](../infra/README.md)에 있다. 이미 `.env`가 있으면 새 예시 파일로 덮어쓰지 않는다. 비밀번호를 GitHub나 채팅에 올릴 필요는 없다.

P04-05에서는 다음 장부를 추가했다. [상세 변경과 검증](verification/P04-05-retention-storage.md)

- **보관 역할:** 대표·최신·최저가 같은 녹음이면 파일 세 개가 아니라 하나를 함께 가리킨다.

- **파일 보호와 정리:** 지금 지우면 안 되는 이유, 어떤 파일 버전의 정리를 확인했는지, 작업이 끝났는지 따로 기록한다. 장부를 만들었다고 파일을 실제로 지우는 것은 아니다.
- **사용·예약 용량:** 이미 보관한 파일의 크기와 곧 업로드할 파일을 위해 잡아 둔 크기를 분리한다. 삭제 중인 파일도 실제 삭제가 확인될 때까지 사용량에 포함한다.

기존 DB를 V5로 바꾸면 기존 파일·진행 중 업로드를 읽어 초기 사용량을 계산한다. 기존 데이터가 있는데 0부터 시작하지 않는다. 정확한 계산을 위해 백업 후 다른 서버의 쓰기를 멈추고 적용해야 한다. 이번에도 사용자 개발 DB에는 적용하지 않았다.
