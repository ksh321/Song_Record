# 노래 기록 앱의 DB 작업 안내

## DB가 맡는 일

DB는 앱이 정보를 잊지 않도록 보관하는 장부다. 회원, 곡, 녹음 정보, 플레이리스트, 태그를 서로 연결한다. 예를 들어 플레이리스트에는 노래 파일을 복사하는 대신 어떤 곡이 몇 번째에 들어가는지 기록한다.

| 구성 | 쉬운 설명 | 이 앱에서 맡는 일 |
|---|---|---|
| Flutter 앱 | 사용자가 조작하는 화면 | 녹음하고 곡·메모를 입력한다 |
| 휴대폰 로컬 DB | 휴대폰 안의 장부 | 인터넷 없이 기록하고 나중에 동기화한다. P04-08 이후 연결 예정 |
| Spring Boot 서버 | 요청을 확인하고 처리하는 담당자 | 로그인, 소유권, 수정 규칙을 검사하고 서버 DB에 기록한다 |
| MySQL | 서버의 장부 | 회원·곡·녹음 정보·목록과 관계를 보관한다 |
| 휴대폰 저장공간과 R2 | 녹음 파일 보관함 | 휴대폰에 원본을 두고, 선정된 파일을 비공개 R2에 보관한다. R2 연동은 후속 작업 |

녹음 제목·메모·길이 같은 정보와 실제 M4A 파일은 다르다. 서버 파일 공간이 부족해도 기록과 메모를 남길 수 있도록 두 가지를 분리한다.

## 이번 P04 작업

P04는 장부의 칸과 연결 규칙을 만드는 단계다. 이를 스키마라고 부른다. 테이블은 장부의 종류, 행은 기록 하나, 열은 이름·날짜 같은 항목이다.

P04-01은 회원과 로그인 수단, P04-02는 내 곡, P04-03은 녹음과 파일 정보의 구조를 만들었다. P04-04는 플레이리스트와 태그·컨디션을 추가한다. 이 단계만으로 앱 화면에서 해당 기능을 전부 사용할 수 있게 되는 것은 아니다. 요청 처리와 화면 연결은 후속 단계에서 진행한다.

DB에도 규칙을 넣는다. 예를 들어 한 목록에 같은 곡이 두 번 들어가거나, 다른 회원의 곡을 내 목록에 연결하려 하면 DB가 거절한다. 화면이나 서버의 실수가 있더라도 마지막 저장 지점에서 잘못된 관계를 막는다.

## 2026년 9월 21일 수정 내용

| 기존 문제 | 쉬운 예 | 수정 결과 |
|---|---|---|
| 키 정보의 일부 누락 허용 | 남성 키라고만 적고 몇 반음인지 비워 둠 | 필요한 두 값이 모두 있어야 저장 |
| 활성 업로드의 빈 슬롯 허용 | 번호표 없이 대기열에 들어가 동시 2개 제한을 피함 | 진행 중 업로드는 0번 또는 1번 슬롯 필수 |
| 파일 세대 번호 형식 불일치 | 파일의 교체 이력을 단순 숫자로 구분 | 설계대로 UUID를 사용하고 기존 숫자 대응도 보존 |
| 저장과 파일 명세 삭제의 동시 처리 | 한쪽에서 저장을 확정하는 동안 다른 쪽에서 필요한 파일 정보를 삭제 | 서로 순서를 맞춰 저장된 명세를 보호 |

P04-04에서는 같은 곡을 서로 다른 플레이리스트에 넣을 수 있다. 한 플레이리스트 안의 중복은 막는다. 금영 검색 결과는 곧바로 개인 목록에 저장하지 않고, 후속 화면에서 TJ 결과를 선택하는 정책을 유지한다.

태그는 여러 개 선택할 수 있고, 태그 이름을 바꾸거나 보관 처리해도 과거 녹음의 당시 이름이 유지된다. 컨디션은 매우 좋음·좋음·보통·안 좋음 중 하나 또는 미선택이다.

## DB를 바꾸는 방법

개발자가 DB를 매번 지우고 다시 만드는 대신, 변경 지시서를 순서대로 추가한다. 이 지시서를 마이그레이션이라고 부른다. Flyway가 적용 이력을 확인하고 아직 실행하지 않은 지시서만 실행한다.

| 파일 | 내용 |
|---|---|
| V1 | DB 변경 이력을 위한 기본 구조 |
| V2 | 회원·곡·녹음 구조 |
| V3 | 이번에 발견한 기존 제약과 파일 세대 문제 수정 |
| V4 | 플레이리스트·태그·컨디션 구조 |
| V5 | 보관 역할·고정 자리·파일 보호·정리 작업·개인 및 전체 사용량 구조 |
| V6 | 기기 간 변경 기록·중복 요청 영수증·삭제 묶음과 이력·작업 대기열 구조 |
| V7 | 공용 인기 차트 게시본·개인 임시 사본·용량 예약·내보내기 세션 구조 |

이미 V2까지 적용된 DB라면 다음에 개발용 서버가 정상 시작될 때 V3~V7을 차례로 적용한다. V7까지 적용했다면 재시작 시 같은 변경을 반복하지 않고 기존 파일과 이력이 일치하는지 검사한다. 기존 지시서를 수정하지 않은 이유도 이미 실행한 지시서의 내용을 바꾸지 않기 위해서다. 실제 적용 전 백업과 현재 데이터 점검이 먼저다.

단, 이 자동 적용은 DB에 연결하도록 설정한 `dev` 프로필에서 일어난다. 이 프로젝트의 기본 `bootstrap` 프로필은 DB 없는 서버 골격용이다. GitHub 업로드나 앱 실행만으로 모든 DB가 자동 변경되는 것은 아니다.

## 실제 적용 순서와 현재 상태

1. **코드 기록:** 변경 파일과 설명을 GitHub에 저장한다.
2. **자동 검사:** GitHub Actions가 임시 환경에서 앱·서버 빌드와 DB 검사를 실행한다. 테스트용 DB는 실제 개발 DB와 분리된다.
3. **적용 준비:** PC의 기존 DB 상태와 필요한 백업을 확인한다. 서버에 입력할 접속 정보는 기존 MySQL 설정과 일치시킨다.
4. **개발 DB 적용:** 최신 코드를 받은 뒤 Docker의 MySQL을 켜고 Spring Boot를 `dev` 프로필로 시작한다. Flyway가 남은 변경을 실행한다.
5. **결과 확인:** 서버가 정상 시작했고 Flyway 이력에 V1~V7이 성공으로 기록됐는지, 기존 곡·녹음이 유지되는지 확인한다.

이번 P04-05 작업에서는 별도 MySQL 8.4.11에서 기존 확장 검사 63개, 데이터가 있는 DB의 업그레이드 검사 72개, 빈 DB 설치 검사 70개를 통과했다. 재실행 시 이력 검증도 확인했다. GitHub에서도 기존 22개·63개와 새 72개 검사를 통과했다. 사용자 PC의 기존 개발 DB에는 이번 V5를 적용하지 않았다.

변경 코드는 GitHub main의 [9d73f72](https://github.com/ksh321/Song_Record/commit/9d73f723bdf907e56e9255f0dc06b9c17096a59b)에 반영했다. [GitHub 자동 검사](https://github.com/ksh321/Song_Record/actions/runs/35588779189)에서 서버 전체 빌드·테스트와 DB 검사를 통과했다. DB 검사 통과와 전체 앱 완성은 다른 의미다. 최신 검증 상태는 [진행 기록](progress.md)과 [P04-05 검증 보고서](verification/P04-05-retention-storage.md)를 확인한다.

## 오류가 나면

이미 잘못된 키나 빈 슬롯 데이터가 있다면 V3가 멈출 수 있다. 이때 사용자 값을 추측해서 채우거나 DB 전체를 초기화하지 않는다. 어떤 행이 어떤 규칙을 어겼는지 확인한 뒤 보정 방법을 결정한다. MySQL의 구조 변경은 여러 단계가 한꺼번에 원상복구되지 않을 수 있어 실제 적용 상태와 Flyway 이력을 함께 확인해야 한다.

검증 스크립트는 합성 데이터를 넣는 시험 도구이므로 일상적으로 쓰는 DB에 그대로 실행하지 않는다. Docker의 `down -v`는 DB 저장공간까지 삭제하므로 단순 종료에는 사용하지 않는다. 정상 종료는 `docker compose stop`으로 충분하다.

구체적인 실행 명령은 [MySQL 개발 환경 안내](../infra/README.md)에 있다. 이미 `.env`가 있으면 새 예시 파일로 덮어쓰지 않는다. 비밀번호를 GitHub나 채팅에 올릴 필요는 없다.

## 이번 P04 06에서 추가한 장부

여러 기기가 같은 계정의 기록을 다루려면 ‘무엇이 몇 번째로 바뀌었는지’를 알아야 한다. 그래서 계정별 변경 번호와 변경 기록을 만들었다. 통신이 끊겨 같은 저장 요청을 다시 보낼 때를 위해, 요청 번호와 최초 결과를 보관하는 영수증도 추가했다.

삭제는 별도로 구분한다. ‘곡만 휴지통으로 옮기기’와 ‘녹음까지 함께 옮기기’의 대상들을 묶고, 원래 연결을 남겨 복원 판단에 쓴다. 반면 영구 삭제된 항목과 서버 파일 사본만 정리한 경우는 별도의 최소 이력을 남긴다. 변경 기록의 90일 보관 기간이 끝났다고 이 삭제 이력까지 같이 지우지는 않는다.

작업 대기열은 오래 걸리는 정리를 위한 할 일 목록이다. 어떤 작업을 누가 처리 중인지, 맡은 시간이 만료됐는지, 다시 시도할지를 기록한다. 담당자가 바뀌었는데 예전 담당자가 뒤늦게 완료했다고 잘못 덮어쓰지 않도록 임대 토큰을 저장한다. 실제로 이 규칙을 사용해 작업하는 서버 기능은 후속 단계에서 연결한다.

별도 시험용 DB에서 기존 검사 22개·63개·72개, 새 업그레이드 검사 88개·빈 DB 검사 86개가 통과했다. 이후 사용자가 `0b1cbae`를 업로드했고 [GitHub 자동 검사](https://github.com/ksh321/Song_Record/actions/runs/35594256348)도 전부 통과했다. 실제 개발 DB와 파일에는 적용하지 않았다.

## 이번 P04 07에서 추가한 두 종류의 사본

**공용 인기 차트**는 모든 사람이 같이 보는 자료다. TJ·KY와 일간·주간·월간을 조합한 여섯 칸을 만들었다. 새 차트를 다 받기 전에는 준비 칸에 두고, 내용을 확인한 뒤 공개 칸이 가리키는 대상을 한 번에 바꾼다. 준비 중에는 이전 정상 목록이 보이므로 절반만 바뀐 목록이 나오지 않는다. 이 자료는 개인 녹음 기록이나 개인 백업에 섞지 않는다. 수집 시각과 제공자가 자료를 갱신한 시각도 같은 뜻으로 취급하지 않는다.

**개인 임시 사본**은 여러 기기가 많은 기록을 나눠 받을 때 쓰는 고정된 자료 묶음이다. 첫 페이지를 받은 뒤 다른 기기에서 곡을 수정해도 뒤 페이지가 다른 시점의 자료로 바뀌지 않게 하는 용도다. 음성 파일을 복사하는 것이 아니라 곡·녹음 설명과 파일 명세 같은 정보를 담는다.

- 준비가 끝난 때부터 30분 동안 쓴다. 다시 요청해도 시간이 늘어나지 않는다.
- 계정당 준비 중이거나 사용 가능한 사본은 최대 2개다. 초기 한도는 사본당 100MiB, 전체 예약 1GiB다.
- 만료는 ‘더 이상 열 수 없음’, 정리는 ‘저장된 사본을 실제로 치움’이다. 아직 내용이 남아 있으면 공간을 사용 중인 것으로 계산한다. 원래 곡·녹음을 지우는 작업은 아니다.
- 준비 도중 실패하면 부분 자료를 새 시점의 자료와 섞지 않고, 해당 시도 전체를 버린 뒤 다시 만든다.
- 온라인 내보내기도 같은 사본과 만료 시간을 사용한다. ZIP 만들기와 음성 파일 복사는 별도 후속 기능이다.

이번에 만든 것은 이 규칙을 저장하고 지키기 위한 DB 구조다. 실제로 사본을 만들어 앱에 보내는 기능·로그인 확인·매 요청의 만료 차단은 P07/P10, 실제 차트 수집과 화면은 P16에서 연결한다. 차트 검사는 가짜 시험 자료만 썼으며 제공자 실데이터 수집·저장·재배포는 이용 조건 확인 전 활성화하지 않는다.

P04-07은 사용자가 `7212fec`로 업로드했고 [GitHub 자동 검사](https://github.com/ksh321/Song_Record/actions/runs/35596556685) 세 작업이 모두 성공했다. 기존 개발 DB에 적용했다는 뜻은 아니다.

## 이번 P04 08: 휴대폰 안의 계정별 보관함

지금까지 만든 MySQL은 **서버의 장부**다. 이번 SQLite는 **휴대폰 안에 두는 작은 장부**다. 인터넷이 끊겨도 편집 내용을 기억하고, 연결이 돌아오면 보낼 일을 남기는 데 사용한다. 휴대폰에 MySQL을 설치하거나 사용자가 DB 프로그램을 켤 필요는 없다.

앱 전용 저장 공간 안에서 개발/시험/운영 환경을 나누고, 그 안에 계정별 보관함을 만든다. A 계정으로 녹음한 파일과 B 계정의 파일은 서로 다른 폴더다. DB 안에도 주인 번호를 남겨서 A의 DB를 B 폴더에 복사해 놓아도 B 계정으로 열리지 않게 한다. 서버 파일의 주소를 휴대폰 파일 위치로 잘못 사용하는 것도 막는다.

예를 들어 오프라인에서 곡 제목을 고치면 두 가지를 **한꺼번에** 저장한다.

1. 휴대폰에서 볼 수정된 제목.
2. 나중에 서버에 보낼 ‘제목 수정 요청’.

둘 중 하나라도 저장에 실패하면 둘 다 취소한다. ‘화면에서는 바뀌었는데 서버에 보낼 기록은 없는’ 상황을 막기 위해서다. 같은 요청을 재시도해도 두 번 추가하지 않고, 오래된 재시도가 더 최근에 쓴 제목을 덮어쓰지도 않는다.

로그아웃은 보관함을 지우는 것이 아니라 **닫는 것**이다. 아직 보내지 못한 수정, 녹음 파일, 중단된 가져오기 작업은 남긴다. 다른 계정으로 로그인하면 다른 보관함만 열고, 원래 계정으로 돌아왔을 때 남아 있던 내용을 다시 읽을 수 있는 기반이다. 실제 로그인 확인과 화면 연결은 P06 이후에 붙인다. 계정 번호 자체가 비밀번호 역할을 하는 것은 아니다.

녹음은 파일 자체와 파일 설명을 구분한다. 파일 설명에는 어느 녹음인지, 휴대폰 안의 위치, 크기, 내용이 바뀌지 않았는지 확인할 해시를 보관한다. 녹음 도중 어디까지 했는지 적는 복구 메모도 남긴다. 이번 작업은 이 메모의 저장 구조까지이며, 실제 M4A 검사·녹음 서비스 연결·중단 복구는 P18에서 완성한다.

### 지금 실제로 바뀐 것과 안 바뀐 것

- 코드와 시험용 저장소를 만들고 검사했다. 실제 개발 MySQL에는 새 명령을 실행하지 않았다.
- 기존 녹음 시제품의 음성·복구 메모는 이동하거나 삭제하지 않았다. 아직 로그인과 연결되지 않은 기록을 임의의 계정 소유로 정하지 않았다.
- 앱 화면은 아직 새 저장소를 사용하지 않는다. GitHub에 올렸다고 기존 앱의 데이터가 자동으로 옮겨지는 것도 아니다.
- 앱 전용 폴더를 이용한 분리이며 DB 암호화 기능은 이번 범위가 아니다. 기기 관리자·루팅 공격까지 막는다는 뜻은 아니다.

### 어떻게 검사했고 다음에는 무엇을 하나

가짜 계정과 가짜 파일만 사용해 계정 분리, 로그아웃 후 재접속, 오류 시 전체 저장 취소, 파일 변경 감지 등을 확인했다. 기존 앱 검사까지 57개 통과했으며 Windows 권한 때문에 파일 링크 검사 1개는 GitHub의 Linux 검사로 넘겼다. 로컬에서 기본 SQLite 바이너리를 내려받지 못해 시험용 복사본만 Windows 시스템 SQLite를 사용했다. 실제 앱 설정은 바꾸지 않았으므로 기본 바이너리와 Android 빌드는 업로드 후 GitHub에서 추가 확인해야 한다.

다음 P04-09는 **장부 양식이 바뀌어도 기존 내용이 그대로 남는지 검사하는 단계**다. 새 DB 설치, 기존 데이터가 있는 DB의 업그레이드, 다시 시작한 뒤 보존을 확인한다. 오류가 났다고 앱 데이터 삭제·재설치·DB 초기화부터 하지 않는다. 상세 결과는 [P04-08 검증 기록](verification/P04-08-account-local-storage.md)에 남긴다.
