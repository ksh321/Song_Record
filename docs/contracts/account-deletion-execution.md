# P23-08 계정 삭제 실행 계약

원본 계획 p01027–p01029, 설계 p00560–p00561, R100·R101, D11의 구현 경계다. 개인 계정 삭제·운영 배포 승인을 뜻하지 않는다.

### 관측 식별자 정리 — P25-06 보완

`operations_observation`은 `user_id` 대신 행위자·대상·작업 UUID를 사용하므로 일반 소유 테이블 순회와 별도로 정리한다. 계정 데이터 제거 트랜잭션에서 해당 행위자/소유 작업의 관측 행을 제거하고, 다른 계정의 관측 행은 보존하면서 삭제 대상 계정·소유 객체를 가리키는 현재/이전 대상 UUID만 비운다. 소유 객체가 남아 있을 때 연결을 확인하며, 제거 중 DB 트리거가 남긴 행도 커밋 전에 다시 정리한다. 서비스 제거 완료 근거는 이 직접 참조 부재도 포함한다.

늦게 종료된 HTTP 관측은 계정의 authoritative `ACTIVE` 행을 잠금 확인한 경우에만 행위자/검증 성공 대상 UUID를 남긴다. 삭제 중·삭제 후·익명·실패 경로의 대상 UUID를 다시 남기지 않는다. 작업 관측은 실제 영속 작업의 소유자가 활성 상태인지 확인하고, 전역 작업에는 임의 집계 대상 UUID를 남기지 않는다. 이 탈퇴 계약은 개인 계정 시험 삭제 승인이 아니다. 활성 계정 관측의 기간 만료는 별도로 USER160·161이 선택·허용한30일 정책을 따르며 운영 관측 runbook에 적용 범위를 기록한다.

## 서버 실행 순서

접수 트랜잭션은 USER 삭제 원장, 소유자별 작업, 기존 기기의 refresh 증명 해시와 ACCOUNT_DELETE 작업을 함께 등록한다. 다른 작업의 lease와 발급 업로드 URL 수명이 끝나고 추가 120초가 지난 뒤 삭제한다. 대기는 코드 오류 실패 횟수가 아니다.

별도 비공개 영속 USER 원장을 먼저 기록·재독 확인한다. worker 권한으로 해당 UUID의 temporary/·recordings/ 접두사만 열거·삭제하고 부재를 확인한다. 객체 확인 실패 때 DB와 사용량을 완료 처리하지 않는다. DB는 검토된 소유자 테이블만 실제 FK 순서로 제거하고 불명확한 새 테이블은 실패 처리한다. 불변 컨디션 이력은 기존 소유 녹음 FK cascade로 제거한다. 전역 저장 사용량·예약량과 스냅샷 용량은 트랜잭션·기존 트리거로 한 번만 반환한다.

서비스 데이터 제거 근거 뒤 BACKUP_CLEANUP으로 이동한다. 단독 소유 운영 백업은 해시 확인 후 정리한다. 다른 계정을 포함한 공유 백업은 다른 계정 사본을 삭제하지 않고 기존 보관 만료를 기다린다. 전체 authoritative 목록에서 부재가 확인돼야 COMPLETED가 된다. 7일 초과는 재시도·운영 복구 대상이며 시간만으로 완료되지 않는다. 실행 오류 5회면 작업을 실패 상태로 남기고 운영 오류 로그를 남긴다. 이는 AI 수정의 동일 원인 3회 정책과 별개다.

완료·백업 부재가 확인되고 접수 후 30일이 지난 항목만 확인증·기기 증명·최소 제어 원장 정리 대상이다. 미완료 항목은 자동 은폐하지 않는다. 외부 ZIP·M4A 사본은 회수하지 않는다.

## 오프라인 기기

POST /v1/account/deletion-device-confirmations는 기존 기기의 refresh 증명 해시·소유자·기기·30일 유효기간·USER 원장을 함께 확인한다. 성공 응답은 deletion_confirmed: true 하나뿐이다. 로그인·파일 접근·삭제 취소 권한이 없고 증명을 URL·로그에 넣지 않는다. 일반 401·404·통신 실패는 삭제 근거가 아니다.

앱은 같은 서버의 검증된 응답 또는 보호 확인증으로 검증한 접수 상태만 로컬 정리에 사용한다. 소유 UUID·환경·서버 origin을 포함한 정리 의도를 먼저 저장한 뒤 해당 계정의 DB·앱 내부 파일만 제거한다. 링크·경로 이탈을 거부하고 다른 계정·외부 내보내기·보호 확인증은 보존한다. 중단된 정리는 재시작 때 재개하며 삭제된 UUID는 다시 열지 않는다. 정리 실패는 재시도 안내로 표시하고 부분 삭제 계정의 일반 동작을 재개하지 않는다.

## P24 운영 연결 전제

worker는 기본 비활성화다. 배포 담당자는 아래 조건을 갖춘 뒤 명시적으로 활성화해야 한다.

- worker R2 권한과 별도 영속 ledger-directory·backup-directory. 운영 볼륨은 디렉터리 fsync를 지원해야 한다. 개발 Windows 대체 동작은 전원 차단 내구성의 운영 증거가 아니다.
- 실제 운영 백업 전체를 대표하는 .catalog.json(schema 1, format song-record-operational-backups-v1, 일치하는 environment, retention_days 7, authoritative true, 고유 instance_id).
- 각 백업은 UUID 디렉터리의 manifest.json과 payload.zip으로 등록한다. manifest는 artifact_id·subjects·created_at·sha256을 포함한다. 손상·미분류 목록은 완료 근거로 쓰지 않는다.
- 백업 생성/게시와 삭제 검사를 조정하여 삭제된 사용자가 다시 포함되지 않도록 한다. 게시·복구 전에 별도 USER 원장의 requireRestorable을 적용한다. worker만 켜고 실제 백업 게시·복구 연결을 생략하지 않는다.
- 공유 백업 만료·7일 초과·실패 작업의 운영 알림/복구, 운영 백업 복구 훈련은 배포 준비에서 실제 검증한다.

P23의 합성 R2·DB·설치본 검사는 위 운영 배포 실적을 대신하지 않는다.
