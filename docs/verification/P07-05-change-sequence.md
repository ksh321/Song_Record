# P07-05 계정 변경 순번 발급

## 왜 필요한가

revision은 자료 하나의 버전이고 change_seq는 한 계정 전체의 변경 순서다.
예: 곡 수정은 change_seq=1, 재생목록 수정은 2, 녹음 수정은 3이다.
순번만 먼저 발급하고 따로 저장하면 2번이 먼저 커밋되고 1번이 나중에 커밋될 수 있다. 기기가 2번까지 읽었다고 기억하면 나중에 나타난 1번을 놓친다.

AccountChanges는 기존 V6 user_sync_state를 FOR UPDATE로 잠그고, 업무 변경과 change_log 저장을 같은 트랜잭션에서 처리한다. 계정 잠금은 바깥 트랜잭션이 커밋/롤백할 때까지 유지된다. 뒤 요청은 앞 요청의 완료를 기다린 뒤 번호를 이어받으므로 이 누락을 막는다.

## 구성

- AccountChanges.write: 살아 있는 세션을 재확인하고 해당 계정의 순번 행을 잠근 뒤 업무 콜백 실행.
- Batch: 콜백이 변경 결과와 하나 이상의 서버 생성 Change를 반환.
- Change: 자료 종류/UUID/변경 후 revision/UPSERT 또는 DELETE/JSON 객체 payload.
- change_log: 연속 순번과 변경 정보, 정확히 90일 뒤의 expires_at 저장.
- user_sync_state: 해당 배치의 마지막 순번과 updated_at 반영. retained_from_seq는 바꾸지 않는다.
- Recorded: 결과와 마지막 순번을 반환. 메서드가 반환됐더라도 바깥 트랜잭션 커밋 전에는 확정이 아니다.

기존 SQL 마이그레이션과 모바일 코드는 변경하지 않는다. 아직 동기화 조회 API, 커서 페이지 처리, 만료 로그 정리, 모바일 적용을 구현한 것은 아니다.

## 호출 순서

```text
IdempotentMutations.execute (멱등 요청/트랜잭션 경계)
  필요하다면 전역 용량 행 잠금
  AccountChanges.write (UserSyncState 잠금)
    RevisionChanges.change (소유권/버전 확인 후 업무 변경)
    변경 후 상태로 Change/Batch 생성
  change_log와 last_change_seq 저장
  멱등 응답 기록
전체 커밋
```

- 모든 해당 계정 쓰기 경로가 이 경계를 사용해야 순번 보장이 성립한다. 서비스를 우회한 직접 쓰기는 자동 추적되지 않는다.
- UserSyncState 전에 하위 도메인 잠금을 잡지 않는다. 전역 용량 잠금이 필요한 작업은 설계서 순서대로 먼저 잡는다.
- 콜백 내부 REQUIRES_NEW, 다른 데이터소스, 외부 네트워크/파일 작업을 사용하지 않는다.
- 자료 소유권/관계/상태 검증과 DB 변경은 도메인 콜백이 수행한다. Change를 클라이언트 입력 그대로 만들지 않는다. 서버에서 확인한 계정 소유 자료만 기록한다.
- payload에는 동기화에 필요한 메타데이터만 넣는다. 토큰, 임시 다운로드 URL, 내부 저장소 키를 넣지 않는다. DELETE도 정의된 삭제 메타데이터 객체를 기록한다.
- 배치의 기록 순서는 콜백이 반환한 목록 순서를 따른다. 빈 배치는 실수로 기록을 빠뜨리는 것을 막기 위해 거절한다. 변경 없는 조회/재시도는 write를 호출하지 않는다.
- 같은 키의 성공 요청 재시도는 P07-03에서 결과를 재사용하므로 추가 순번/로그를 만들지 않는다.
- 버전 충돌/업무 실패/로그 저장 실패/순번 범위 초과는 업무 변경, revision, 순번, 로그, 멱등 기록을 함께 롤백한다.
- 상태 행은 가입 과정에서 이미 생성된다. 누락됐다면 번호 0으로 임의 재생성하지 않고 실패시킨다.

## 테스트

H2와 실제 계정/세션을 이용해 P07-03/04와 함께 수행한다.
- 업무 변경 + revision + 멱등 기록 + 순번 + 로그의 일괄 저장.
- 동일 요청 재시도 시 로그 추가 없음, 버전 충돌 시 순번 증가 없음.
- 로그 저장 실패/바깥 트랜잭션 실패 시 전체 취소.
- 계정별 독립 순번, 배치 연속 순번, 90일 보존 시각, 잘못된 payload/빈 배치/범위 초과/폐기 세션 거절.
- 첫 변경을 일부러 대기시켜 두 번째 변경이 콜백에 들어가지 못하는지 확인.
- 1번 커밋 후 2번이 아직 미커밋일 때 1번만 보이고, 이후 change_seq>1 조회로 2번을 찾는지 확인.

기존 MySqlIdempotencyTests에도 V6 실제 user_sync_state/change_log DDL로 순번 잠금·커밋 순서와 로그 실패 시 전체 롤백 테스트를 추가한다. 기존 Idempotency MySQL Actions에서 자동 실행한다.
이 작업 환경에서는 Docker를 사용할 수 없어 MySQL 전용 테스트 5개는 건너뛴다. 사용자 PC의 일반 적용 테스트도 동일하며, CI의 실제 MySQL 성공 확인이 필요하다.
