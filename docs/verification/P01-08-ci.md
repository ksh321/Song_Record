# P01-08 최소 자동 검증

## 목적

새로 받은 저장소에서도 Flutter, Spring Boot, MySQL 개발 환경이 같은 순서로 준비되는지 GitHub Actions가 자동 확인한다. 개발자의 PC 상태에 의존하지 않고 저장소 자체가 다시 실행 가능한지 검사하는 것이 목적이다.

## 자동 검사

| 작업 | 실행 내용 | 성공 기준 |
|---|---|---|
| Flutter | Flutter 3.47.4 설치, lockfile 기반 의존성 해결, `flutter analyze`, `flutter test` | 분석 오류와 테스트 실패 없음 |
| Spring Boot | Temurin Java 21 설치, Gradle Wrapper 9.7.1로 `clean build` | 컴파일과 전체 테스트 성공 |
| MySQL | Compose 설정 검사, digest 고정 MySQL 기동, `SELECT 1` 실행 | 컨테이너 healthy와 쿼리 성공 |

세 작업은 서로 독립적으로 실행된다. 하나가 실패해도 어느 영역이 실패했는지 GitHub Actions 화면에서 바로 구분할 수 있다.

## 보안과 재현성

- 외부 GitHub Action은 확인한 커밋 SHA로 고정한다.
- 실제 개발 비밀번호나 GitHub Secret을 사용하지 않는다.
- MySQL 비밀번호는 CI 가상 컴퓨터 안에서만 사용하는 임시값이다.
- CI가 끝나면 컨테이너와 named volume을 제거한다.
- Flutter는 `pubspec.lock`, 서버는 Gradle Wrapper와 `gradle.lockfile`, MySQL은 이미지 digest를 사용한다.

## 실행 조건

다음 상황에서 `.github/workflows/ci.yml`이 실행된다.

- `main` 브랜치에 push
- Pull Request 생성 또는 변경
- GitHub Actions 화면에서 수동 실행

## 새 체크아웃 수동 확인 순서

1. 루트 README의 준비 도구를 확인한다.
2. `apps/mobile`에서 `flutter pub get --enforce-lockfile`, `flutter analyze`, `flutter test`를 실행한다.
3. `services/api`에서 Java 21을 확인하고 `gradlew.bat clean build`를 실행한다.
4. `infra`에서 `.env.example`을 `.env`로 복사해 로컬 비밀번호를 입력한 후 MySQL을 실행한다.
5. Spring Boot를 `dev` 프로필로 실행하고 Flutter에서 health 응답을 확인한다.

CI 성공은 실제 Android 녹음 기능까지 검증했다는 뜻이 아니다. 녹음 실기 검증은 P02에서 수행한다.
