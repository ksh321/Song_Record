## 실제 연결

- 내 곡 상세의 곡 삭제 → 서버 미리보기 → 곡만 삭제·녹음 유지 / 곡과 녹음 함께 삭제 → 기존 immutable TRASH 대기열. 취소는 큐를 만들지 않는다. 개별 녹음 상세의 삭제는 고정 해제를 명시적으로 확인한다.
- 서버 확정부터7일, 오프라인 삭제 동기화 대기, 대표·고정 재선택, 원본 파일 보존을 별도로 안내한다. 기기 시각에 의한 삭제나 실제 사용자 파일 정리는 수행하지 않는다.
- 설정 → 휴지통 목록·서버 삭제/만료 시각·일부 선택 복원·영구 삭제 확인·다음 페이지·실패/응답 미확인·같은 요청 재확인을 연결한다. 202는 완료가 아니라 영구 삭제 처리 중이다.
- HTTP는 기존 세션을 공급하고 전후 계정/기기 epoch를 확인한다. 토큰 갱신은 같은 scope, 계정이 떠났다가 돌아와도 기존 요청 scope는 폐기된다. HTTPS 또는 명시적 dev local HTTP만 허용하며 redirect·무제한 응답·자동 네트워크 재시도를 허용하지 않는다.
- 복원/영구 삭제 명령의 path·base_revision·선택 UUID·멱등 UUID만 환경/계정별 기존 FlutterSecureStorage에 보관한다. 인증값·원본 파일·객체 키는 기록하지 않는다. 응답 유실은 재개 시 같은 body/op로 확인하며 인증 거절은 기존 요청을 유지한다. 동일 journal의 중복 진행은 메모리 잠금으로 막는다. 결과는 서버 change feed로 받으며 복원 응답을 임의의 로컬 성공 상태로 덮어쓰지 않는다.
- 휴지통의 TJ 번호는 기존 곡 복원을 안내하고 PURGE_PENDING은 완료 동기화를 기다린다. PURGED tombstone 이후 새 UUID의 등록 흐름만 기존 서버 검증으로 진행한다. 후보 추가도 같은 예약을 우회하지 않는다.
- 별도 검토에서 부분 영구 삭제 묶음을 통째로 계속 막는 표시 위험을 확인했다. 목록에 현재 서버 lifecycle_state를 선택적 필드로 제공하고 항목별 TRASHED만 선택, PURGE_PENDING 표시, 남은 항목 복원을 허용한다. 누락 행을 임의 PURGED로 간주하지 않으며 소유 객체 키는 반환하지 않는다.

## 학습 개념

- 삭제 의도, 서버 휴지통 확정, 파일 삭제 확인은 다른 상태다. 일부 항목 처리 중인 묶음에서도 다른 복원 가능한 항목은 계속 선택할 수 있어야 하며, 계정 변경과 응답 유실은 데이터 삭제 완료 근거가 아니다.
