# P20-08 목록 항목 복원 (원수)

- 원본 계획922~924, 설계556, R097·V20. 요청/관측 6.1 Sol/medium. 현재 모델 직접 구현·별도 검토.
- 선택 곡의 같은 삭제 묶음 목록 항목을 연결해 복원한다. 개별 목록 항목 선택도 같은 묶음/계정/원래 목록·곡 범위 안에서만 가능하다.
- 기존 목록이 활성이고 원래 곡이 ACTIVE일 때만 숨김을 해제한다. 같은 entry_key의 활성 항목이 있으면 기존 항목과 위치를 유지하고 복원 중복은 건너뛴다. 이미 활성인 원래 항목도 위치를 바꾸지 않는다.
- 숨김 항목은 현재 활성 항목 뒤에 이어 붙인다. 목록 버전을 한 번 증가시키고 전체 aggregate 변경을 송신한다. 삭제된 목록·없는 목록은 재생성하지 않는다. 원래 고유키 제약을 유지한다.
- 모든 관련 곡→녹음→목록 집계 잠금을 정렬해 먼저 확보한 뒤 파일 정책/작업 잠금으로 진행한다. 순서 범위 초과는 전체 복원 트랜잭션을 롤백한다.
- 변경: TrashRestoration, PlaylistService, 목록 복원 H2/실제 MySQL 회귀 검사, OpenAPI.
- 함께 보존한 운영 수정: 같은 초의 취소 push를 전체 dispatch가 대체한 경우를 CI 선택기에 반영했다. 실제 실패·나중 취소·이전 성공 은폐 금지를 유지한다. 운영 실패/완료 검사106개 PASS. 기존 감시 오판·정정 증거는 P20-07 기록에 보존한다.

## 검사·별도 검토

- 전체 서버/계약과 보완된 순서 초과 영향 검사 결과는 실행 후 기록한다. 실제 MySQL은 최종 SHA의 필수 CI에서 확인한다.
- 현재 모델 별도 검토: 계정/묶음 범위·선택 곡 자동 연결·현재 연결 검증·기존 활성 위치·entry_key 중복·삭제 목록 불변·부모 버전·전체 aggregate 이벤트·잠금 순서·파일 보존·멱등 재실행·범위 초과 롤백 대조.
- 이 단계 설치 실기 해당 없음. 실제 UI 삭제·복원 확인은 P20-10에서 수행한다. CI 진행 중은 완료가 아니다.

## 학습 개념

- 복원은 삭제 전 위치를 무조건 되돌리는 작업이 아니다. 이후 사용자 정렬을 보존하면서 누락된 항목만 현재 끝에 넣어야 한다.

- gradlew build --offline 전체 PASS(1분8초), 보완 후 복원 영향9개 PASS(11초), OpenAPI143 경계 PASS, 운영106개 PASS, diff 공백 검사 PASS. 실제 MySQL은 로컬 조건부 제외이며 최종 CI 근거를 별도로 기록한다.
