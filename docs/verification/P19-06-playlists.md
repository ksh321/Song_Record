## 구현
- 기존 SongRow/MySong 재사용 다중 선택 시트. 검색 중 선택 유지, 취소는 저장하지 않으며 포함 판정은 대상 목록의 song_id/entry_key로만 한다. TJ 후보가 같은 키이면 추가됨으로 표시한다.
- 여러 곡을 개별 부모 revision 요청으로 나누면 두 번째 요청이 낡은 revision을 갖게 된다. 이를 자동 재기준화하지 않고 기존 POST items 계약에 song_ids 배열을 추가하여 한 요청·한 트랜잭션·한 부모 revision으로 처리한다. UUID·중복·최대100개·계정/ACTIVE 상태 검증, 정렬된 Song 잠금, 기존 항목 ID 반환, 모두 기존이면 revision/change_seq 변경 없음.
- 클라이언트는 불변 요청·부모 revision과 모든 Song 의존성을 보존한다. 다른 미확정 목록 변경 중에는 새 다중 변경을 막는다. 오프라인 생성의 base0만 기존 CREATE 후속 새 op_id 경로로 해결하고 양수 base는 재작성하지 않는다.
- 응답의 항목 ID 개수·고유성·전체 집합·요청 순서별 entry_key·소유자를 검증한 뒤 로컬 aggregate/ACK를 함께 적용한다. 잘못된 매핑은 트랜잭션을 롤백하고 원 요청 그대로 재시도한다.
