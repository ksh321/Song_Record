# P19-03 — TJ 후보 추가

## 범위·원본
- 원본 계획서 문단875~877, 설계서681·682·831·1048을 직접 대조했다. 원본 해시는 manifest와 일치한다.
- R079·V38: 검증된 TJ 토큰으로 곡 미등록 후보를 담는다. KY·임의 수동 후보·송신자 번호/키 덮어쓰기는 거절하며 항목·순서가 바뀌지 않아야 한다.

## 구현·검토
- 기존 TjCandidates/LiveCandidates와 멱등성 executePrepared를 재사용한다. 토큰 준비·만료 TJ 재조회는 트랜잭션 밖에서, 브랜드 재확인과 소유 목록·revision 검증은 쓰기 전에 수행한다. 완료된 동일 요청 재전송은 제공자를 다시 호출하지 않는다.
- 후보 브랜드·번호·원본 제목/가수는 검증 결과로만 만든다. 요청은 song_id 또는 source_token 중 하나와 base_revision이며 추가 번호·키·제목은 허용하지 않는다.
- 후보/등록 TJ는 같은 서버 중복 키를 사용한다. 기존 항목 ID·순서·부모 revision을 유지하며 새 후보만 부모·항목·변경 피드에 원자 저장한다.
- 모바일 기존 목록 큐에 후보 요청·전체 항목 응답 검증을 연결한다. 미등록 후보는 Song을 생성하지 않는다. KY 거절에도 기존 항목을 유지한다. 오프라인 목록 생성 직후의 후보 요청은 기존 선행 완료 근거로 새 요청을 만들며 원래 요청을 수정하지 않는다.
- 현재 모델 직접 별도 검토(gpt-6.1-sol/medium 사용자 고정). 토큰/소유 권한 구분, 잠금 밖 준비, 중복·원자 저장·불변 재시도·기존 등록곡 회귀를 대조한다.
- 이 번호는 서버·큐 경계 작업이다. 실제 검색/차트에서 목적 목록으로 돌아오는 화면 검사는 원본 P19-07의 완료 조건으로 확인한다. P19-02 설치본 완료 근거는 보존한다.

## 검사
- 서버 영향7개 PASS: 후보·등록곡 중복, KY·위조·키 덮어쓰기·자유 입력 거절 후 모든 항목 필드/순서 보존 및 기존 CRUD/등록곡 검사.
- H2의 문자열 JSON 바인딩이 MySQL과 달라 테스트 저장 타입을 MySQL getString 반환과 맞췄다. 실제 JSON 타입·P04 트리거·유일 키·암호화된 TJ/KY 토큰·응답 유실 재전송의 준비 생략은 CI 전용 MySQL 검사에 추가했다. 아직 CI 실행 전이며 통과로 계산하지 않는다.
- 모바일 영향4개 PASS: 오프라인 생성 선행, 미등록 후보·중복·KY 거절·재시작, 잘못된 계정 응답 취소, 등록곡·이름 변경·응답 유실 회귀.
- 전체 묶음 `.local/workflow/p19-03/checks.ps1` 실행 중. 실제 결과·커밋·대상 SHA 필수 CI는 완료 후 아래에 기록한다.
