# P21-01 내보내기 기준 시점

## 범위와 근거
- 원수, 사용자 승인 P21-01부터 P21-09까지 순차 실행. 요청 모델 6.1 Sol/medium, 현재 대화에서 직접 구현·별도 검토한다.
- 계획서 원본 [p00936–p00938], 설계서 10.1·12.6, R102, D09 일관된 사본, D10 오프라인 부분 백업을 대조했다.
- 기존 P20 완료 SHA 6536991491002388576f03239e4690361004338a와 원격 main이 일치함을 시작 시 새로 확인했다. 이전 관리 문서·도구의 미커밋 변경은 보존했다.

## 구현
- `ExportController`의 인증된 POST /v1/exports와 GET /v1/exports/{id}/manifest를 추가했다. 요청은 include_trash 불리언 하나만 받으며 기존 멱등 응답·EXPORT 사본·작업을 같은 트랜잭션으로 저장한다.
- 기존 서버 사본 생성기와 일관된 읽기 뷰를 재사용한다. SYNC와 EXPORT는 공통 용량·슬롯·만료 제한을 사용하되 공개 조회 경로는 purpose로 분리한다. 페이지 커서는 계정·사본·엔티티에 묶인다.
- 앱은 모든 19종 페이지의 개수·순서·최종 해시·만료를 검증한 다음 해당 계정의 로컬 초안과 미전송·충돌 요청을 한 SQLite 읽기 트랜잭션에서 복사한다. 충돌의 기준 revision·기준 payload·로컬 payload·서버 응답을 함께 보존한다.
- 서버 captured_at/snapshot_cursor와 로컬 local_cutoff_at은 서로 다른 기준이다. 고정한 결과는 이후 수정으로 바뀌지 않는다. 동기화 커서 설치·큐 ACK·파일 삭제를 수행하지 않는다.
- 오프라인은 새 export_id와 마지막 확인 로컬 기준을 기록한다. 서버 사본이 없으면 온라인 최신 사본으로 주장하지 않으며 미확인 커서는 null로 남긴다.
- 현재 내부 기준 데이터는 내보내기 자료의 입력이다. manifest/data/CSV 작성, 녹음 안전 종료, 음성 수집, ZIP·파일 선택기·진행 화면은 다음 원본 P21 번호에서 연결한다. include_trash는 파일 수집 선택으로 유지하며 개인 데이터의 삭제 상태를 없애지 않는다.

## 검증 및 별도 검토
- 관련 SQLite 회귀: 온라인 기준 이후 변경 제외, 오프라인 미전송 보존·null 커서, BUILDING/해시 오류의 부분 결과 차단, 저장된 충돌 보존·큐 미변경, 계정 전환 차단을 검사한다.
- 서버 HTTP 회귀: 미인증/허용되지 않은 메서드·잘못된 요청이 영수증·DB 작업 전에 차단되는지 검사한다.
- 실제 MySQL 전용 회귀를 추가했다: EXPORT 생성·동일 요청 재사용·선택 변경 거절, SYNC 조회 격리, 페이지·만료, 공통 2슬롯 제한. 로컬 MySQL이 없어 조건부 skip이며 원격 MySQL CI로 최종 확인한다.
- 별도 검토는 현재 모델이 원본 완료 조건과 실제 diff·검사 결과를 대조한다. 계정/목적 분리, 트랜잭션 경계, TTL 유지, 로컬 데이터 보존, 기준 이후 변경 제외를 확인한다. 독립 에이전트 검수는 아니다.
- 새 사용자 화면이나 재생·녹음 조작이 없는 내부 작업이므로 이 번호에서 폰 조작은 요구하지 않는다. 실제 백업 저장·취소·삭제 경쟁은 P21-08/09에서 설치본으로 확인한다.
- 최종 일괄 로컬 검사와 대상 SHA의 필수 CI는 진행 중이다. 통과 개수와 SHA는 실제 결과 확인 후 추가한다.

## 학습 개념
- 일관된 백업은 서버 기준과 로컬 기준을 숨기지 않고 따로 기록한다. 충돌은 서버값이나 로컬값 중 한쪽을 버리지 않고 복원 판단에 필요한 두 값과 기준 revision을 남긴다.
