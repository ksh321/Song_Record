# P09-08 녹음 정보와 파일 보관 오류 분리

기준 커밋: P09-07b `39493693a6e4eadcd7e0999ff91354c31f5a449a`.
이번 단계는 P09의 마지막 서버 경계 검증이다. 새 화면·파일 업로드 기능·마이그레이션은 추가하지 않는다.

## 보장하는 경계

recording 및 recording_file_spec는 녹음 정보와 기기에서 완료한 파일의 명세다.
recording_asset는 서버 파일의 보관 상태다. SAVED 성공은 서버 파일의 STORED/검증 완료를 뜻하지 않는다.
용량·고정·예산 제한은 파일 보관 승인에 적용되며 정상적인 녹음 메타정보 저장을 차단하지 않는다.
인증·소유권·revision·필수 입력·파일 명세 유효성 검사는 계속 적용한다.
기존 구현이 이 경계를 만족하므로 동작을 바꾸는 우회 코드 대신 회귀 테스트를 추가한다.

## 새 검증

H2와 전체 Flyway를 적용한 MySQL에서 같은 시나리오를 실행한다.

| 상황 | 테스트 설정 | 기대 결과 |
| --- | --- | --- |
| QUOTA | 사용자 quota=100, used=100 | DRAFT/SAVED/수정/티어/연결 성공 |
| PIN_LIMIT | pinned_limit=0 | 같은 메타정보 경로 성공, 슬롯 자동 생성 없음 |
| BUDGET | global_storage_usage.upload_locked=true | 같은 메타정보 경로 성공, 잠금 유지 |

각 경우 제목 없는 DRAFT를 생성하고 키·버전·메모를 수정한 다음 곡을 연결한다.
곡의 기본값이 입력 중인 값을 덮어쓰지 않고 제목 미입력도 그대로 유지되는지 검사한다.
완료 파일 명세와 제목·가수를 보내 SAVED로 전환한 후, 동일 멱등 키의 응답 재사용과
티어·메모·버전 수정을 검증한다. 목록에도 SAVED 녹음이 표시되어야 한다.
최종 asset는 QUEUED와 원래 blocked_reason을 유지하고 stored=false여야 한다.
recording_file_spec, 연결 곡, entitlement, 사용자 사용량, 전체 사용량·잠금은 변경되지 않는다.
녹음 변경 로그는 중복 없이 6개이고 파일 정책 재계산 작업은 큐에 등록한다. 작업 실행은 이 테스트 범위가 아니다.

추가 HTTP 테스트는 업로드 잠금 상태에서도 제목 누락을 400으로 거절하고,
제목을 채우면 ORIGINAL/0으로 SAVED 성공하는지 검사한다.
SAVED의 키를 null로 변경하는 요청은 계속 거절하며, 서버 asset 없이 명세만 저장된다.

## 설계 검증 사례와 범위

- V05: 제목 없는 DRAFT 보존, SAVED 필수값과 원키 0, SAVED 키 null 차단.
- V06: 연결 복구 후 서버가 파일 없이 정보·티어 요청을 처리할 수 있는 경계만 검증한다.
  모바일 오프라인 저장·재실행·전송 큐·로컬 재생은 P10/P14/P18에서 구현·검증한다.
- V07: 용량 부족/잠금 상태에서 정보 저장 성공 및 파일 대기 상태 보존.
- V36: 녹음의 LIVE→MR 변경이 연결 곡 NORMAL을 바꾸지 않음.
- V45: 키·버전 직접 변경 후 곡 연결이 입력값을 덮어쓰지 않음.
  모바일의 명시적 기본값 적용 버튼은 후속 화면 작업이다.

보관 승인·오브젝트 업로드·예산 계산 자체는 P11/P12의 범위다.
이번 테스트는 유효한 제한/대기 상태를 DB에 설정하여 메타정보 경로의 독립성을 검증한다.
