# WORKFLOW-09 자동 복구 연결 — 2026-10-07

사용자 요청: ‘자동복구 구현해’. 기존 단일 실행기·기존 작업 스레드·구독 인증을 사용한다. 이번 유지보수는 제품 다음 번호 실행 승인이 아니다.

## 변경과 완료 기준

- `tools/workflow_recovery.py`: 등록 명령 복구, 같은 중단의 읽기 전용 AI 확인 1회, 기존 원인별 실패 이력 보존, 해결 불가·사용자 행동의 기존 폰 알림 연결.
- `tools/sequential_runner.py`: 승인 대기와 실행 예외를 복구에 연결. `recover` 입구에서 설치본·실행 순서·잠금을 확인한다. 원래 호출이 완료됐으면 저장 결과를 재사용하고 실행 중·불확실한 호출은 중복 실행하지 않는다.
- `tools/workflow_status.py`: 30초 독립 감시가 종료를 감지하면 한 번 복구를 시작한다. 복구 중 동작·실제 AI 요청 설정을 표시한다. 사용자 중지·완료·실기/사용자 대기·한도 대기는 재개하지 않는다.
- `tools/workflow_usage.py`: 복구 AI 호출을 ‘자동 복구 확인’으로 집계한다. 알려진 명령 처리는 AI 호출을 만들지 않는다.
- 기존 요청의 실행시간 표시와 PLAN Astra/medium 변경도 유지한다. 핵심 구현·검토와 원인별 3+3 규칙은 변경하지 않는다.

등록 명령은 허용된 실행 파일·작업 경로·계획의 검사 대상·옵션을 대조한 뒤 인자 목록으로 재구성한다. 임의 셸 문자열·미등록 대상·불필요한 삭제 옵션을 실행하지 않는다. 복구 명령 exit 0은 제품 완료가 아니며 기존 검증·검토·실기·CI 관문은 그대로다.

## 현재 모델 코드 검토

등록 범위 밖 실행, 명령 삽입, 중복 요청 ID 변경, 복구 중 종료 후 재호출, 사용자 중지, 남은 실패 횟수, 미등록 AI 검사 제안, 읽기 전용 진단의 소스 변경, 알림 중복을 대조했다. 복구 성공과 재개 사이에 중지가 도착해도 stop 파일을 유지하도록 수정하고 회귀 검사했다. 정상 완료·필수 대기 상태를 비정상 복구 대상으로 바꾸지 않는다.

## 적용과 한계

통과한 설치본의 controller hash를 `.local/workflow/runner-verification.json`에 갱신한다. 다음 승인된 제품 실행부터 이 복구 경로가 적용된다. 기존 P10-07 COMPLETE/RUN_FINISHED 및 완료 근거는 보존한다. P10-08은 시작하지 않는다.

프로세스 감시는 실행기가 살아 있지만 멈춰 있는 모든 종류의 교착을 판정하지 않는다. 도구에는 기존 실행 시간 제한을 적용한다. PC 종료·절전, 감시기까지 동시 종료, 네트워크 단절 중 복구·알림을 보장하지 않는다. 권한이 실제로 거절되면 자동 확장/보안 우회하지 않고 근거를 저장한다. 불확실한 커밋·푸시나 진행 중 호출은 무조건 재실행하지 않는다.

제품 소스·의존성 변경이 없는 개발 도구/운영 문서 변경이므로 원격 앱·서버·DB CI는 NOT_REQUIRED다. 로컬 검증 결과를 원격 CI 통과로 표시하지 않는다. Spaces 설계 Page는 이번 작업에서 수정하지 않았다.
