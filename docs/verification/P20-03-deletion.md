# P20-03 승인 업로드의 미연결 보존 (원수)

- 원본 계획908~909, 설계549~551, R064/R093. 요청·관측6.1 Sol/medium, 현재 모델 직접 구현·별도 검토.
- P20-02 곡만 삭제 거래에서 기존 STORED 및 유효한 승인 업로드에 ORPHAN_KEEP을 적용한다. 정확한 계정/녹음의 RESERVED·UPLOADING·VERIFYING, 만료 전, 현재 정책 revision과 일치하는 시도만 포착한다. 삭제로 올린 정책 버전에 그 시도를 연결하며 시도 ID·URL·만료 시각·예약·일일 예산은 새로 만들거나 늘리지 않는다.
- 기존 완료 작업의 파일 검증·최종 객체 쓰기·거래 내 현재 상태 재검사·예약→used 회계를 재사용한다. 이후 동시 삭제/상태·파일 규격·정책 변화는 기존 펜스로 거절한다. 완료된 파일과 원래 고정은 유지되며 추가 고정 슬롯을 소비하지 않는다.
- 미연결 보존 사유만으로 새 업로드를 승인하지 않는다. 기존 유효 승인 재사용, 이미 STORED 사본 조회, 실제 고정 또는 재연결 후 자동 선정은 기존 정상 경로를 따른다. 오래된 승인 정책을 보존 예외로 되살리지 않는다.
- 변경: OrphanUploads, SongTrash, UploadApproval, SongTrashTests, 공유 UploadApproval/FinalizationDatabaseChecks 및 시험 스키마.

## 검사·별도 검토
- 최종 API build --offline 전체 PASS(1분23초). 실제 MySQL 전용 검사는 로컬 조건부 skip이며 최종 SHA CI에서 필수 확인한다.
- 곡 삭제 검사: 승인 정책 이관·동일 만료·업로드 상태 유지·ORPHAN_KEEP, 오래된 정책 부활 차단 포함. 기존 메타데이터·파일·고정 보존 회귀도 유지.
- H2/실제 MySQL 공유 검사에 최종 객체 검증 시작→자동 보호 제거→삭제 시 정책 이관→완료 경쟁을 추가했다. 파일 STORED, reserved 0/used 3, 고정 슬롯 추가 없음, ORPHAN_KEEP 유지 대조. 미승인 미연결 보존 사유만으로는 NOT_CLOUD_TARGET인 것도 대조.
- 첫 전체 검사 실패는 공유 H2 시험 스키마 확장 후 PinCompletionTests가 같은 열을 다시 추가한 중복 설정(원인 P20-03-FIXTURE-01)이다. 중복 등록만 제거하고 제약/검사를 유지, 최종 전체 재통과. 제품 동작 실패나 다른 원인과 합산하지 않는다.
- 별도 현재 모델 검토: 계정 sync 잠금·동일 거래·이전 승인 판정·정책 변경 펜스·URL/시도/만료/예산 불변·실제 V2/V5/V19 제약·기존 녹음 ACTIVE 요구 대조. 기존 P13-09 완료 및 재연결 보호 이관 경로 보존.

## 학습 개념
- 사본을 보존할 이유와 새 업로드를 승인할 권한은 다르다. 삭제 전 유효한 승인만 이어주고, 보존 예외만으로 새 용량 예약을 만들지 않아야 한다.
