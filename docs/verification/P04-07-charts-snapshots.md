## 공용 차트 게시

차트에는 user_id가 없으며 개인 변경 로그나 사본에 자동으로 넣지 않는다. 과거 연월·정확 집계 기간·완료 월 같은 제공되지 않은 값을 만들지 않는다. fetched_at은 서버 수집 시각이며 제공자 갱신 시각이 아니다. 번호는 VARCHAR로 보관해 앞자리 0을 보존한다. 현재 번호 제약은 1~20자리 숫자 문자열이다.

항목은 STAGING에서만 추가·제거할 수 있고 PUBLISHED 이후에는 내용을 바꾸지 못한다. 게시 전 양수 순번이 1부터 연속인지, 실제 개수와 선언 개수가 일치하는지, 비어 있지 않은지 확인한다. 100개라는 고정 개수는 강제하지 않는다. 항목 추가와 게시 검사는 부모 행 잠금으로 직렬화한다. 게시 검사는 오래된 REPEATABLE READ 뷰가 아니라 현재 행을 읽는다.

전체 스냅샷 게시와 포인터 교체는 P16에서 하나의 트랜잭션으로 수행한다. 사용자 조회는 포인터를 통해 게시본만 읽어야 한다. 실패하면 같은 브랜드·기간의 이전 포인터를 유지하며, 오래됨 표시·503 응답·source_token·외부 JSON 수신 완결성·수집 중복 실행 제어는 P16 범위다. DB는 외부 응답이 실제로 완전히 수신됐는지 알 수 없다.

## 개인 사본과 정리

사본은 BUILDING에서 시작한다. 같은 계정의 BUILDING/READY 자리는 0·1 두 개이며 중복 자리는 유일 제약으로 차단한다. 요청 번호도 계정 안에서 유일하다. 용량은 사본당 100MiB, 전체 1GiB를 예약할 수 있다. 생성 임대는 해당 시도 시작 후 최대 10분이다.

현재 attempt에서만 행을 추가할 수 있다. 추가·제거 시 헤더의 행/바이트 수를 함께 반영하고, 예약한 바이트보다 큰 본문을 추가하면 거절한다. READY 전에는 실제 행 수·바이트 수·엔터티별 순번을 다시 대조한다. READY의 cursor·내용·시도·manifest 해시·시각은 불변이며 만료는 ready_at+30분이다. 재요청으로 연장하지 않는다.

실패한 BUILDING을 다시 만들려면 먼저 그 시도의 부분 행 전체를 버리고 새 attempt_id와 증가한 attempt_count로 시작한다. 이전 읽기 뷰를 다른 연결에서 이어 읽을 수 있다는 의미가 아니다. P07에서 새 일관 읽기 트랜잭션으로 전체 원본을 다시 읽어야 한다.

EXPIRED/FAILED는 사용자 자리를 반환하지만 남아 있는 payload의 바이트까지 즉시 무료로 취급하지 않는다. 저장된 바이트 이상을 계속 예약하고, 헤더와 사본 행을 실제 제거하는 트랜잭션에서 남은 예약을 환급한다. 정리는 원본 Song/Recording이나 음성 파일을 삭제하지 않는다. 용량 초과로 실패한 INSERT도 예약을 남기지 않는다. 예약 변경 트랜잭션은 snapshot_capacity → snapshot_header 순서로 잠그고, 원본 일관 읽기 트랜잭션에는 이러한 잠금 읽기를 섞지 않는다.

이는 논리 JSON payload 한도이며 실제 디스크·인덱스·로그 비용까지 1GiB로 제한하는 것은 아니다. payload_hash와 payload_bytes는 MySQL의 정규화된 UTF-8 JSON 텍스트 기준이다. API/ZIP 직렬화의 정규화·manifest 해시 계산/검증은 P07/P21에서 별도 계약과 시험이 필요하다. 내부 예약·행 수 장부는 신뢰된 서버만 갱신해야 한다.

사본 엔터티 코드에서 공용 차트·인증 세션은 거절한다. 그러나 JSON 본문의 실제 소유권·필드별 비밀 제외·필수 엔터티 완결성은 P07의 인증된 원본 조회와 필드 허용 목록이 검사해야 한다. 다른 계정 JSON을 임의 SQL로 넣는 것까지 DB가 자동 판별한다는 뜻은 아니다. 모든 페이지 요청은 계정 소유권·ACTIVE 상태·READY 상태·서버 현재 시각이 expires_at보다 이른지를 확인해야 한다. 토큰만으로 인증하거나 청소 작업의 실행 여부에 접근 차단을 맡기지 않는다.

## 실제 검증

별도 Windows MySQL 8.4.11, 127.0.0.1:33316, 저장소 잠금 버전 Flyway 12.4.0·Connector/J 9.7.0을 사용했다. 시험 DB는 `p0407_upgrade_7b995fa8`, `p0407_fresh_7b995fa8`이며 실제 개발 DB·음성 파일은 사용하지 않았다. 차트는 합성 자료만 사용하고 외부 제공자를 호출하지 않았다.

| 검사 | 결과 |
|---|---|
| V1→V2 기존 핵심 제약 | 22개 통과 |
| V4 기존 확장 제약 | 63개 통과 |
| V5 보관/용량 업그레이드 | 72개 통과 |
| V6 동기화/삭제 업그레이드 | 88개 통과 |

실제 두 연결을 사용해 차트 게시 전후 전체 목록 전환, 오래된 읽기 뷰로 게시 검증 우회 차단, 원본 수정 중 동일 읽기 뷰의 곡과 기준 cursor 일치, 전체 예약 한도 경쟁을 확인했다. 예약 경쟁은 900MiB를 예약한 뒤 두 연결이 각각 100MiB를 요청해 하나만 성공하는 조건이다. 초기 한도는 1GiB=1024MiB이므로 성공 뒤 24MiB는 남는다.

만료 직전/정확한 경계·타 계정·탈퇴 상태의 조회 조건, READY 후 내용·만료 불변, 기존 attempt의 추가 저장 거절, 내보내기 목적/계정 FK, 만료 후 저장량 유지·실제 정리 환급도 확인했다. 이는 실제 MySQL의 제약과 SQL 프로토콜 검증이며 앱 화면·HTTP 오류 응답·장애 후 서버 프로세스 재개를 검증한 것은 아니다.

## 재실행과 후속 단계

`infra/scripts/verify_p04_migrations.sh`는 V1 → V2 → V4 → V5 → V6 → V7과 서버 재시작을 실행하도록 확장했다. 새 `verify_p04_snapshot_schema.py --seed-upgrade`는 V6 보존 확인 자료를 만들고, 옵션 없는 실행은 V7 검사다. `P04_DISPOSABLE_DB=1`이 필수이며 매번 새 시험 DB에서만 실행한다.

- P07/P10: 일관 원본 읽기·인증·30분 요청 차단·완전성/manifest 검증·5분 주기 청소·재시작/부하·앱 staging 교체.
- P16: 제공자 이용 조건 확인, 실제 수집·전체 응답 검사·게시·stale/오류 응답·TJ source_token·화면 연결. 이용 조건 확인 전 실데이터 저장/재배포를 활성화하지 않는다.
- P21/P22: 실제 ZIP 작성과 파일 복사·가져오기. 이번 사본 테이블은 음성 사본을 만들지 않는다.
- 다음 구현 순서: P04-07 커밋·CI 확인 후 P04-08 계정별 로컬 저장 구조.

이번에도 로컬 Git index.lock 생성이 권한 제한으로 거절됐다. 권한 요청 후 한 번 재확인했으며 권한 설정을 우회하거나 원격 main만 따로 변경하지 않았다. P04-07 파일과 설명을 로컬에 준비한 상태로 GitHub Desktop 커밋·push가 필요하다.
