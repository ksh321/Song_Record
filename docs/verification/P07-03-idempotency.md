# P07-03 멱등 요청 접수

## 동작

IdempotentMutations는 P07-02 AccountAccess로 인증된 계정을 재검증하고,
기존 V6 mutation_receipt의 (user_id, op_id) 기본 키를 이용한다.
Idempotency-Key는 소문자 정규 UUID다. 같은 계정과 키의 요청은 다음 규칙을 따른다.

- 같은 HTTP 메서드·대상 경로·정규화 JSON 본문: 기존 HTTP 상태와 JSON 결과를 재사용한다.
- 다른 메서드·대상 경로·본문: 409 IDEMPOTENCY_CONFLICT. 기존 결과/요청 내용은 노출하지 않는다.
- 다른 계정의 같은 키: 별개 요청이다. 기기 ID는 해시에 포함하지 않아 같은 계정의 유효한 다른 기기에서도 재시도할 수 있다.
- 로그아웃·만료 등 인증 실패: 결과 재사용 이전에 거절한다.

## 원자성과 동시성

1. 독립적인 READ_COMMITTED 트랜잭션을 시작한다. 외부 트랜잭션 안의 호출은 거절한다.
2. 처리 기록을 먼저 INSERT한다. 같은 키의 동시 INSERT는 DB 유일 키로 직렬화된다.
3. 업무 콜백에서 같은 DB/트랜잭션의 변경을 수행한다.
4. 성공 응답을 기록에 반영하고 업무 변경과 함께 커밋한다.
5. 다른 요청이 이미 커밋했다면 중복 INSERT 트랜잭션을 롤백한 뒤 기존 기록을 조회한다.

처음 INSERT한 임시 상태는 커밋 전 다른 요청에 보이지 않는다. 업무 코드나 결과 저장 중 예외가 발생하면 기록과 업무 변경이 모두 취소된다. 업무 테이블에서 발생한 DuplicateKeyException은 기록 중복으로 오인하지 않는다.
성공한 2xx 상태/JSON 본문만 저장한다. 예외/4xx/5xx는 캐시하지 않고 재시도를 허용한다.

외부 API 호출·파일 전송·메일 등 DB 밖의 효과는 콜백에 넣지 않는다. 비동기 작업은 향후 P07-06의 Job 등록과 함께 커밋한다.
이 경계에 들어오기 전에 도메인 잠금을 잡지 않는다. 이후 필요한 도메인 잠금은 설계서의 순서를 따른다. 잠금 실패·교착으로 롤백되면 동일 키로 전체 명령을 재시도한다.

## JSON 정규화

객체 키를 재귀 정렬하고 공백·문자 이스케이프 표현 차이를 제거한다. 수치는 정밀도를 유지하는 BigDecimal로 정규화해 1, 1.0, 1e0을 동일하게 취급한다.
배열 순서, 문자열 내 공백/대소문자, null과 누락은 유지한다. 중복 키·뒤따르는 JSON·과도한 크기/깊이는 거절한다. SHA-256 해시에는 메서드와 구체적인 대상 경로도 들어간다.
이는 앱 전용 규칙이며 RFC 8785 구현이라고 주장하지 않는다.

## 후속 API에서 사용하는 방법

먼저 본문 형식/업무 입력을 검증하고, 서버 라우트 어댑터가 메서드와 구체적 경로를 결정한다. 클라이언트가 임의의 operation name을 정하도록 하지 않는다.
쿼리로 변경 의미를 전달하지 않는다. 모든 의미 있는 입력은 해시에 포함되는 본문/경로에 있어야 한다. 본문 없는 명령은 어댑터에서 {}로 통일한다.

```java
var account = access.authenticate(authorization, deviceId);
var reply = mutations.execute(account, idempotencyKey, "POST", "/v1/songs", body, () -> {
    // 같은 데이터소스에서 소유권·상태·revision 확인 후 업무 변경.
    // 기존 트랜잭션에 참여하며 REQUIRES_NEW로 분리하지 않는다.
    return new IdempotentMutations.Reply(201, responseJson);
});
return ResponseEntity.status(reply.status())
    .contentType(MediaType.APPLICATION_JSON).body(reply.body());
```

인증 토큰, 임시 서명 URL, 일회성 비밀은 결과 기록에 저장하지 않는다. 이러한 값은 별도 인증된 조회 API에서 발급한다. 응답 헤더는 저장하지 않으므로 Location 등이 필요한 API는 기록된 안정적 ID에서 다시 구성한다.
현재는 공통 서비스와 테스트 전용 HTTP 경로를 구현했다. 실제 곡 저장 API/모바일 재시도 연결은 후속 단계다. 기존 로그인/갱신 경로의 계약을 임의로 바꾸지 않는다.

## 보존

created_at과 expires_at을 정확히 90일 간격으로 저장한다. 정리 작업은 아직 구현하지 않았다. 만료 시각이 지난 기록도 실제 정리 전에는 재사용해 불필요한 중복 실행을 막는다.
기록 삭제 후에는 최초 요청으로 처리될 수 있으므로 후속 도메인 API의 생성 UUID 유일성·base_revision·영구 삭제 표식 검사를 반드시 유지한다. 90일을 넘는 영구적인 중복 방지를 이 서비스만으로 보장하지 않는다.

## 검증과 적용

- H2 + 실제 계정/세션: 순차/동시 재요청, 충돌, 계정 격리, 재시작 후 조회, JSON 정규화, 로그아웃, 업무/결과 저장 실패 시 롤백, 202/204, HTTP 오류 계약.
- MySQL 전용 테스트: V6의 실제 mutation_receipt DDL, InnoDB 동시 INSERT, JSON 왕복, 롤백 후 재시도. 별도 Idempotency MySQL workflow가 일회용 MySQL 8.4에서 실행한다. 무작위 이름의 테스트 DB만 생성/삭제한다.
- 이 작업 환경에는 Docker가 없어 MySQL 테스트는 로컬 실행하지 못했다. CI 성공 확인이 필요하다. 일반 로컬 테스트에서는 이 2개만 건너뛴다.
- 기존 SQL 마이그레이션이나 Flutter 파일은 바꾸지 않는다. Windows 적용은 gradlew.bat test bootJar로 검증한다.
- 푸시 후 CI, API contract, Idempotency MySQL 세 워크플로를 확인한다.

## 이해 확인

요청 키는 로그인 토큰과 다르다. 로그인 토큰은 누가 요청했는지, 요청 키는 어떤 작업의 재시도인지 구분한다.
앱은 논리적인 작업을 처음 만들 때 UUID 키를 한 번 생성하고 재시도 때 그대로 사용해야 한다. 매번 새 키를 만들면 중복 방지가 되지 않는다.
다음 질문을 코드에서 확인한다: 결과를 저장하기 전에 서버가 종료되면? 저장 후 응답 전달만 실패하면? 같은 키로 제목을 바꾸면?
