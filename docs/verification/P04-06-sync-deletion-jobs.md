2026-09-21, 시작 커밋 `93922f8`. 구현계획서 P04-06, 설계서 4·9·11.6, 확정 D07·D11을 기준으로 V6를 추가했다. 기존 V1~V5는 수정하지 않았다. 서버 DB 구조와 실제 MySQL 검사까지의 범위이며, 동기화 API·작업 실행기·실제 파일 삭제 기능을 완성했다는 뜻은 아니다.

변경 로그의 UPSERT는 수정·휴지통 상태 등을 전달하는 본문이고 DELETE는 제거 표식을 뜻한다. 문자열 코드 형식만 DB가 제한하며 허용 엔터티·소유권·응답의 의미는 P07 업무 계층에서 정한다. 요청 재시도 시 같은 해시이면 원래 응답, 다른 해시이면 409로 응답하는 처리는 P07에서 구현한다. DB의 유일 제약만으로 HTTP 처리가 완료되는 것은 아니다.

삭제 묶음은 SONG_ONLY·SONG_AND_RECORDINGS·RECORDING 모드를 사용한다. 목록 자체 영구 삭제는 D07에 따라 7일 휴지통 묶음에 넣지 않고 별도 표식·Job으로 처리한다. preview_version은 서버가 만드는 불투명 식별자로 저장하며 산출 방식은 P20에서 연결한다.

## 관계와 이력 보존

Recording의 delete_batch_id와 PlaylistItem의 hidden_by_batch_id에 계정까지 일치하는 외래키를 연결했다. 다른 계정의 묶음이나 존재하지 않는 묶음을 지정하면 실패한다. 기존 값이 잘못돼 있어도 임의로 NULL로 바꾸거나 묶음을 만들어 맞추지 않는다.

DeletionItem은 실제 삭제 전에 같은 트랜잭션에서 등록한다. 원래 연결은 현재 엔터티와 대조하고 original_deleted_at은 DB가 실제 대상에서 가져온다. 이후 녹음이 사라지거나 원래 목록이 삭제돼도 복원 판단용 이력이 남아야 하므로 대상과 과거 연결에는 생존 테이블 외래키를 두지 않는다. 묶음에 대한 계정 복합 외래키는 유지한다. 다른 곡 재연결을 덮어쓰지 않는 복원 판단과 같은 묶음만 복원하는 처리는 P20 범위다.

DeletionLedger는 RECORDING과 RECORDING_ASSET을 구분한다. RECORDING_ASSET에는 0이 아닌 세대 UUID가 필수이며, 정보 자체의 삭제 표식에는 세대가 없어야 한다. 한 녹음에 정보 삭제 표식과 여러 과거 파일 세대 표식이 공존할 수 있다. 사용자의 현재 파일을 지우거나 녹음 상태를 바꾸는 트리거는 없다.

DeletionLedger와 Job은 계정 행이 제거된 뒤에도 계정 삭제·백업 정리를 이어가야 하므로 생존 AppUser 외래키를 두지 않는다. 내부 서버 전용 기록이며 클라이언트의 임의 계정·대상 ID를 신뢰해서는 안 된다. 다형 대상과 계정 소유권은 P07/P23의 인증된 작업 생성 경로에서 검사한다. 활성 계정의 영구 삭제 UUID에는 90일 자동 만료를 두지 않는다. 탈퇴 계정의 백업 제거 확인과 최대 30일 정리는 P23/P24에서 연결한다.

88개 검사는 계정 격리, change_seq·op_id·묶음·작업 중복, 90일/7일 기한 불변, 과거 연결 보존, NULL 세대 중복, 삭제 계정 이력 보존, 작업 임대·재시도·완료 필드 등을 확인한다. 실제 두 연결로 계정 번호 잠금과 SKIP LOCKED 작업 선점도 검사했다. 새 임대 토큰을 받은 후 이전 토큰으로 완료 처리하는 조건부 UPDATE가 0행인 것을 확인했다.

동시성 검사는 P07에서 사용할 SQL 트랜잭션 방식의 검증이다. 스키마가 모든 임의 SQL의 커밋 순서나 작업 실행 횟수를 자동 보장한다는 뜻이 아니다. 업무 수정·번호 증가·로그·영수증·Job 등록을 한 트랜잭션에 넣었다가 롤백해 모두 함께 취소되는 것도 확인했다.

## 재실행과 적용 주의

CI 스크립트는 V1 → V2 22개 → V4 63개 → V5 72개 → V6 88개 → 서버 재시작으로 확장했다. 새 스크립트는 `P04_DISPOSABLE_DB=1`을 요구한다. `infra` 폴더에서 `python3 scripts/verify_p04_sync_schema.py --seed-upgrade`는 V5의 합성 데이터 준비, 옵션 없는 실행은 V6 검증이다. 매번 새로운 시험용 DB를 사용한다.

실제 적용 전에는 백업하고 다른 서버·작업자의 쓰기를 중지한 상태에서 기존 묶음 참조를 확인한다. MySQL DDL은 전체 파일을 한 번에 롤백하지 않으므로 실패 시 실제 구조와 Flyway 이력을 함께 점검한다. 이 검사의 잘못된 값은 시험용 데이터였으며 사용자 데이터 보정 절차로 사용하면 안 된다.

P07은 번호 할당·업무 트랜잭션·409 응답·인증·작업 선점/임대 토큰 재검사·합법적인 상태 전이를 구현한다. 임대 토큰 조건 없이 UPDATE하면 오래된 작업자를 차단할 수 없으므로 모든 작업자 갱신에 토큰과 현재 상태를 검사해야 한다. P10은 만료 커서와 재동기화, P20은 삭제/복원 범위와 만료 시각 유지, P23/P24는 계정·객체·백업 삭제 및 이력 정리를 구현한다. 외부 파일 I/O를 DB 잠금 중에 수행하지 않는다.

이번에는 로컬 Git의 index.lock 생성이 권한 제한으로 막혔다. 이전 Pull 충돌을 재발시키지 않도록 원격 main을 별도로 변경하지 않았다. 코드·검증·진행 문서를 준비한 상태이며 GitHub Desktop에서 커밋·push 후 원격 CI 결과를 확인해야 한다.
