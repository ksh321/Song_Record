# 검증 환경 암호화 운영 백업

P24-05는 노트북의 독립 검증 MySQL과 확정 R2 파일을 매일 암호화한다. 서비스 운영 배포·삭제 실행기 활성화·복원은 수행하지 않는다. 삭제 원장 재적용은 P24-06, 실제 복구와 재생 훈련은 P24-07, 운영 실패 알림은 P24-10에서 연결한다.

## 역할과 비밀 보관

- `song-record-staging-backup`은 비공개 Standard 버킷이다. `staging.backup`은 이 버킷 하나의 Object Read & Write만 가진다. 기존 API·worker·playback 역할은 백업 버킷의 목록 읽기와 객체 삭제를 거부해야 등록된다. 백업 키도 기존 개발·운영·검증 6개 버킷 목록 읽기를 거부해야 한다. 읽기·쓰기 역할의 백업 삭제 권한 자체를 없앤다는 의미는 아니다.
- 확정 원본을 읽는 별도 `staging.playback` 키는 복사에만 사용한다. 앱·정리 작업자에 백업 키나 암호화 키를 주입하지 않는다. 임시 업로드 버킷은 복사하지 않는다.
- 기존 Windows DPAPI와 현재 사용자·SYSTEM ACL을 재사용한다. 등록 창은 마스킹되며 키·복구 암호·DB/녹음 원문을 로그·명령 인수·환경변수·Git에 넣지 않는다. 필요 값은 실행 메모리에 존재하고 Windows 관리자·같은 계정 악성 프로그램까지 차단하는 보장은 아니다.
- 최초 마스터 키는 무작위 256비트다. 키 롤 시 기존 마스터 키를 유지한다. 기존 원격 카탈로그가 있는데 로컬 마스터 키가 없으면 새 키를 만들지 않고 복구를 요구한다. AES-256-GCM의 매 객체 무작위 96비트 nonce와 경로 AAD로 내용·경로 바꿔치기를 거부한다.
- 복구 암호는 16자 이상 길고 임의적으로 만들고 프로그램 밖에서 안전하게 보관한다. scrypt N=131072/r=8/p=1과 무작위 salt로 마스터 키의 복구 봉투를 암호화한다. 암호화된 `recovery-key.enc`는 로컬 및 같은 비공개 백업 버킷에 보관하고 원격에서 다시 읽어 일치 여부를 확인한다. 노트북 분실 시 새로 발급한 백업 접근 키와 복구 암호가 필요하며 실제 새 환경 복구는 P24-07에서 검증한다. 사용자 암호 보관을 자동 완료로 간주하지 않는다.

## 스냅샷과 완료 게시

`backup_runtime.py once`는 검증 Compose 프로젝트와 고정 DB 이름을 확인한다. MySQL의 root-only tmpfs 설정을 사용해 전역 읽기 잠금을 얻고, 모든 기본 테이블이 InnoDB인지 확인한 뒤 같은 잠금 동안 확정 파일 목록과 `mysqldump --single-transaction`을 수집한다. 잠금은 최대 30초, 세션 유휴 제한도 30초이며 실패 시 성공 게시를 하지 않는다. 이 동안 쓰기가 잠시 대기할 수 있다. 읽기와 원본 데이터는 보존한다.

DB 출력은 최대 256MiB, 파일 목록은 최대 100,000개·32MiB, 파일은 개당 6MiB로 제한한다. 평문 DB는 디스크에 쓰지 않는다. 파일 목록의 UUID·세대·서버 객체 경로·바이트 크기·SHA-256을 확인하며 없는 파일·해시 불일치는 전체 지점 실패다. `STORED` 및 아직 확정 파일이 남아 있는 `DELETING` 자산을 대상으로 하며, 원본 삭제와 경합해 파일이 사라지면 성공으로 표시하지 않는다.

동일 세대·해시의 사본은 다시 읽어 확인한 후 재사용한다. DB·파일 목록·매니페스트는 암호화해 R2에 쓰고 실제로 다시 읽어 인증·체크섬을 확인한다. 새 지점과 보존될 지점을 모두 검증해야 암호화 카탈로그를 게시한다. 일일 중복 실행은 당일 지점을 재검증하고 추가 생성하지 않는다. 최근 7개 일일 지점만 카탈로그에 유지하고, 제외된 지점의 DB·매니페스트만 전용 경로에서 정리한다. 활성 파일 사본은 삭제하지 않는다. 공유 파일의 영구 삭제 후 최대 7일 정리·복원 전 삭제 원장은 P24-06의 범위다.

카탈로그는 P24-05 전용 암호화 형식이다. P23의 authoritative 탈퇴 백업 목록과 연결되기 전에는 탈퇴 정리 작업자를 켜지 않는다. 객체 생성·날짜·현재 PASS만으로 실제 복원이나 RPO/RTO 24시간을 보장하지 않는다.

## 실행과 재개

설치된 Codex 의존성 Python의 `cryptography`를 재사용하며 새 유료 API나 패키지 설치는 필요 없다. AI가 해당 실행 환경에서 `tools/backup_runtime.py once`를 실행하고 고정 상태만 확인한다. 등록 후 검증 환경 재연결은 창 없는 일일 감시를 요청한다. OS 파일 잠금으로 단일 기록자를 유지하고 감시는 1시간마다 날짜를 확인한다. AI 모델을 호출하지 않는다. 노트북 절전·전원 종료 중에는 백업되지 않으며 재개 시 빠진 날짜의 과거 스냅샷을 만들었다고 주장하지 않는다.

실패 시 `status.json`을 FAIL로 기록하고 기존 마지막 정상 지점과 `latest.json`을 보존한다. 실패를 0건/PASS로 바꾸지 않는다. 업로드가 중간에 끊긴 미게시 객체는 정상 지점으로 취급하지 않는다. 실제 복구용 지점은 카탈로그·DB·파일 전체를 다시 확인해야 한다.

백업 버킷의 저장·읽기·쓰기 요청도 기존 R2 비용 감시에 포함한다. 공급자 신규 버킷 통계가 아직 나타나지 않으면 비용은 미확인이며 무료/0원으로 간주하지 않는다. [Cloudflare 버킷별 권한](https://developers.cloudflare.com/r2/api/tokens/)과 [AWS 요청 서명](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html)을 따른다.
