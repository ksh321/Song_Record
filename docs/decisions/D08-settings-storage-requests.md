# D08 — 기기 강조색과 반복 가능한 추가 보관 요청
- 상태: 확정 / P00-06 / 2026-09-16
- 승인: 사용자 강조색 A, 보관 요청 A + 중복 요청 허용
- 관련: R008·R123·R037, P23
- 사례: [P00-06](../contracts/P00-06-examples.md)

## 강조색
기존 UI의 8개 강조색을 기기 로컬 설정에 저장한다. 동일 앱 설치에서 계정 전환·재실행 후에도 기기 선택을 유지한다. 계정 동기화와 서버 설정 API는 추가하지 않는다. 재설치·다른 기기·백업 가져오기에서 복원을 보장하지 않으며 누락/유효하지 않은 색 ID는 UI 기본값으로 돌아간다.

## 요청 화면
PIN_LIMIT(고정 개수 필요), STORAGE_QUOTA(저장 용량 필요)를 하나 이상 선택한다. 둘 다 선택 가능하다. 수량·자유 의견·결제 입력은 받지 않는다.
성공 문구: “요청이 접수됐어요. 현재 보관 한도는 그대로 유지됩니다.”
성공 후 다시 요청할 수 있다. 같은 계정·같은 종류여도 사용자가 새로 제출하면 별도 요청으로 저장한다. 접수 이력이 있다는 이유로 버튼을 영구 비활성화하지 않는다.
전송 중 버튼 연타는 한 제출로 묶는다. 오프라인 새 제출은 각각 새 ID로 대기열에 저장하고 “전송 대기”를 표시한다.

## 반복 제출과 통신 재시도
- 새 사용자 제출: 새 request_id UUID + 새 op_id → 별도 요청 1건.
- 응답 유실·자동 재시도·동일 클릭의 연타: 같은 request_id/op_id → 기존 결과 재사용, 새 건수 추가 없음.
- 같은 op_id에 다른 본문: 409 IDEMPOTENCY_CONFLICT.
- 같은 request_id를 다른 op_id로 재전송: 동일 소유자·같은 종류면 기존 접수 반환, 다른 종류면 409 REQUEST_ID_CONFLICT.
- 두 종류를 한 제출에 선택하면 요청은 1건, 종류별 건수는 각 1건이다.
- 총 요청 건수와 고유 요청 사용자 수를 별도 집계한다. 반복 제출은 건수를 늘리지만 동일 기간의 고유 사용자 수를 중복 증가시키지 않는다.

## 추가 API 계약
모든 경로 기본 /v1. Bearer 인증과 등록 device_id 필요. account_id·서버 접수 시각·사용량은 서버에서 정하고 클라이언트 값을 신뢰하지 않는다.

| 메서드·경로 | 입력 | 성공 |
|---|---|---|
| POST /storage/requests | Idempotency-Key, {id: request_id, types: ["PIN_LIMIT"]} | 최초 201, 기존 ID 재조회 200. {id, types, status:"RECEIVED", revision:1, received_at, updated_at} |
| GET /storage/requests/me | cursor, limit(기본50/최대100) | 200 {items, next_cursor}; 최근 접수순→id, 최근 90일 보존 요청 |
| GET /storage/requests/{id} | 소유 요청 ID | 200 요청 결과. 타인/없는 요청 404 |

생성에는 기존 리소스 base_revision이 없다. 변경·취소 API는 이번 범위에 추가하지 않는다. types는 위 두 enum의 중복 없는 비어 있지 않은 배열이다. 오류는 400 INVALID_REQUEST_TYPES. 인증 실패 401, 비활성/탈퇴 계정의 접수는 차단한다.
현재 한도에 도달하지 않았어도 수요 요청을 받을 수 있다. 요청은 UserEntitlement·고정 상태·업로드 승인·보관 한도를 변경하지 않는다.
동일 op_id 재시도의 HTTP 상태/본문은 공통 MutationReceipt 결과를 그대로 재현한다(원래 201이면 201). 위 200은 다른 op_id로 기존 request_id를 재조회한 경우다.

## 저장·보존 범위
앞선 A안 운영 제안값을 유지한다: 요청 본문은 서버 received_at부터 90일 보관한다. 필드: request_id, 계정 ID, types, received_at, revision, 접수 시 pinned_used/pinned_limit/used_bytes/quota_bytes. 음성·곡명·메모·자유 의견은 수집하지 않는다.
90일 후 계정 연결 요청 본문과 사용량 스냅샷을 제거한다. 이후 목록에서 사라진다. 통계에는 개인 식별자·요청 ID·개별 사용량을 남기지 않고 기간별 요청 총수·종류별 건수·고유 사용자 수의 집계값만 유지한다. 계정 탈퇴 시 연결된 원본 요청을 삭제한다.
MutationReceipt 90일 규칙과 별도로, 오래된 request_id가 새 요청으로 다시 집계되지 않도록 활성 계정 동안 최소 접수 ID 원장(계정, request_id, 접수 시각)을 유지한다. 이는 90일 뒤 내용 조회용이 아니다. 영수증·본문 만료 후 해당 ID 재전송은 409 STORAGE_REQUEST_EXPIRED로 끝내며 자동 새 ID 생성은 하지 않는다. 사용자가 새로 보내기를 선택하면 새 ID로 정상 접수한다. 원장도 탈퇴 시 삭제한다.
이 경로는 D08에서 새로 확정하는 계약이다. 원 설계 14.2의 반복 버튼 사용자 중복 집계 금지는 고유 사용자 수에 유지하며, 의도적인 반복 요청 건수는 추가로 기록하도록 구체화한다.
