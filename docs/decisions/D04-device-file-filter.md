# D04 — 현재 기기 파일 필터와 페이징
- 상태: 확정 / P00-05 / 2026-09-16
- 승인: 사용자 추천 조합 선택
- 선택: A — 전체 동기화 메타정보 + 현재 기기 파일 인덱스를 로컬 DB에서 조회
- 관련: R032·R075, X09, P09-03·P14-01·P18-09
- 공통 사례: [P00-05 사례](../contracts/P00-05-examples.md)

## 처리 위치
로그인 계정의 전체 개인 메타정보를 동기화하고, 미전송 로컬 변경을 포함한 로컬 DB에서 필터·개수·정렬·페이지를 계산한다. 여기서 전체 동기화는 음성 파일 전체 다운로드를 의미하지 않는다.
서버 페이지 하나를 받은 뒤 기기 조건으로 걸러 결과 전체라고 표시하지 않는다. 서버 조회는 서버가 아는 메타정보/서버 파일 조건만 처리한다. 현재 기기 조건을 서버 조건으로 보내 처리된 것처럼 간주하지 않는다. 이 예외는 원 설계 12.1의 서버 필터 원칙을 기기 파일 조건에 대해 구체화한다.

## 파일 상태의 근거
- L: 현재 계정·현재 기기의 완료 파일이 유효함을 확인한 PRESENT 또는 확인된 ABSENT. 조사 전·권한 문제·I/O 오류는 UNKNOWN으로 둔다.
- S: 마지막 동기화된 서버 파일 상태가 STORED이면 true. 업로드 대기·실패는 STORED가 아니다.
- Q: 서버 상태의 보관 대기 이유가 용량 부족인 경우. 서버 실제 필드명은 API 구현 시 이 의미에 매핑한다.
- 경로가 DB에 있다는 이유나 다른 기기 보고만으로 PRESENT라 하지 않는다. 재생·삭제 전 실제 파일을 재확인한다. 임시·손상 파일은 정상 사본으로 세지 않는다.
- 서버 상태는 마지막 동기화 시점 기준이며 오프라인에서 실시간 서버 존재를 보장하지 않는다.

## 기존 UI 필터 매핑
기존 HTML의 다섯 파일 상태 선택지와 용량 부족 선택지를 유지한다(전체 포함 여섯 선택지). 일반 상태와 보관 대기 이유는 내부에서 분리해 보관한다.

| 선택 | 조건 |
|---|---|
| 전체 | 파일 상태로 제한하지 않음. UNKNOWN도 기록은 표시 |
| 이 기기에만 있음 | L=PRESENT AND S=false |
| 서버에 보관됨 | L=ABSENT AND S=true (서버에만 있는 기록) |
| 이 기기와 서버에 있음 | L=PRESENT AND S=true |
| 현재 기기에 파일 없음 | L=ABSENT AND S=false (기존 HTML의 복원 안내 상태) |
| 서버 보관 대기 · 용량 부족 | Q=true, 기기 파일 유무와 독립 |

‘현재 기기에 파일 없음’ 선택지는 이 계약에서 “이 기기·서버 모두 없음”이라는 설명을 함께 제공한다. 다른 기기의 파일까지 없다고 단정하지 않는다. 서버 사본이 있는 기기 파일 부재는 ‘서버에 보관됨’에서 찾는다.
추천 설명의 일반적인 “이 기기에 있음/서버에 있음”과 기존 UI의 구체적인 “이 기기에만 있음/서버에 보관됨”을 혼동하지 않는다. 위 표가 실제 필터 계약이다.
용량 부족은 위치 상태와 겹칠 수 있다. 예: L=PRESENT, S=false, Q=true는 ‘이 기기에만 있음’과 ‘용량 부족’ 어느 선택에도 해당한다. UI는 파일 상태 한 개를 선택하므로 중복 행이 발생하지 않는다. HTML의 표시 문자열 우선순위로 필터를 계산하지 않는다.

## 조회·개수·미확인 처리
1. 계정과 ACTIVE·SAVED 범위를 정하고 현재 연결 곡/미연결·기간·키·버전·티어·컨디션·태그 등 적용 조건을 AND로 결합한다.
2. 파일 조건을 전체 대상 집합에 적용한 후 D02/D03으로 정렬하고 페이지를 나눈다.
3. 결과 개수는 limit 전 같은 집합의 COUNT다. 키 모드와 반음 0, 미정 티어와 조건 없음, 미연결과 전체를 구별한다.
4. 최초 동기화가 끝나지 않았으면 “동기화 중 · 현재 확인된 N개”로 표시한다. 완전한 0건/전체 개수라고 표시하지 않는다.
5. 파일 위치 조건 사용 시 다른 조건에 맞는 UNKNOWN을 확인한다. 확인 중이면 잠정 개수와 확인 중 안내, 실패하면 확인 불가 안내를 제공한다. UNKNOWN을 ABSENT로 바꾸거나 거짓 0건으로 확정하지 않는다.
6. 오프라인에서는 로컬 정보 기준 결과와 마지막 동기화 시각을 표시한다. 실제 파일 변경은 인덱스·결과 개수·목록을 갱신한다.
7. 다운로드/삭제/동기화 완료 등 집합 변경은 아래 조회 세대 규칙으로 처리한다.

## 공통 페이징 계약
- 기본 limit=50, 최대=100, 양의 정수만 허용한다. 1~100 밖의 명시 값은 오류로 처리한다.
- 비교 튜플 마지막은 UUID다. 다음 페이지는 마지막 반환 튜플 다음부터 읽는 keyset 방식이며 offset으로 대체하지 않는다.
- 불투명 cursor는 계정, 조건 fingerprint, 정렬·키 규격, 마지막 튜플, 조회 세대와 결합한다. 서버 cursor는 변조를 검증하며 다른 계정에서 재사용할 수 없다.
- 조회 세대는 결과·정렬·개수에 영향을 주는 데이터 변경을 감지한다. 로컬은 메타정보와 파일 인덱스의 조회 revision, 서버는 해당 조회의 변경 revision을 사용한다. 구체 필드와 인덱스는 P07에서 구현한다.
- 동일 세대의 COUNT와 첫 페이지는 같은 DB 읽기 트랜잭션에서 산출한다. 중간 페이지 조회 시 세대가 바뀌었으면 낡은 cursor를 거절하고 첫 페이지·개수를 다시 조회한다. 서로 다른 세대의 결과를 이어 붙이지 않는다.
- 계정·검색·정렬·적용 필터·보기 모드 변경도 cursor와 기존 페이지를 초기화한다. 취소한 필터 초안은 영향을 주지 않는다.
- 내 곡 티어별 보기는 그룹 순위를 비교 튜플 맨 앞에 넣는다.
- 빈 결과는 items=[], count=0, next_cursor 없음. 정확성 상태가 잠정이면 별도 안내한다. 마지막 페이지도 next_cursor 없음.
- 이 계약은 목록 조회의 안정성이다. 백업/전체 동기화 스냅샷의 D09 결정을 대체하지 않는다.

## 대안과 검증
서버 페이지를 끝까지 순회하며 로컬 후처리하는 안은 개수·응답 시간 부담이 크다. 기기 상태를 서버에 보고하는 안은 오프라인/삭제 후 오래된 보고 문제로 정확한 현재 기기 필터의 기준으로 채택하지 않는다.
P00-05 문서 계약 완료와 P14/P18의 실제 기기 검사·X09 통과는 구분한다.
