[p00001] 노래 기록 앱 구현 설계서
[p00002] 버전 1.11 최종본 · Android 우선 · 2026년 9월 15일
[p00003] 이 문서는 Flutter 앱과 Spring Boot 서버를 구현하기 위한 기능, 데이터, API, 파일 보관 및 검증 기준을 정의한다. 모든 녹음 정보는 서버에 동기화하고, 녹음 파일은 휴대폰에 먼저 저장한다. 서버에는 곡별 자동 보관 대상과 사용자가 고정한 파일을 선별 보관한다. 기기를 바꿀 때는 서버 동기화와 백업 파일 가져오기를 함께 사용한다.
[p00004] 확정 정책  곡별 대표 1개·최신 1개·최저 티어 1개를 중복 없이 자동 보관하고, 계정 전체에서 무료 고정 10개를 제공한다. 서버 총용량은 계정당 1GB로 제한한다. 한도가 차면 새 파일을 대기시키며 기존 고정 파일은 자동 삭제하지 않는다. 결제는 후속 확장으로 남긴다.
[p00005] 문서 사용  본문의 규칙과 API 계약을 구현 기준으로 사용한다. 수치가 있는 초기 운영값은 서버 설정으로 관리한다. 15장의 통과 기준은 구현 후 확인해야 할 항목이며, 기능 구현이나 실기 검증 완료를 의미하지 않는다.

[p00023] 1.1 첫 출시 범위
[p00024] Android용 Flutter 앱, Spring Boot 서버, MySQL, 비공개 Cloudflare R2를 사용한다. 첫 로그인에는 네트워크가 필요하다. 로그인한 계정의 데이터는 로컬 DB에도 보관하여 오프라인 조회·녹음·입력이 가능하게 한다. 모든 개인 데이터와 파일 접근은 계정 소유권을 확인한다.
[p00025] 하단 탭은 왼쪽부터 내 곡, 인기 차트, 녹음, 플레이리스트, 검색이다. 설정은 공통 화면의 오른쪽 상단 버튼으로 제공한다. 오늘 부를 곡 전용 기능은 두지 않고 사용자가 일반 플레이리스트를 만들어 사용한다. 녹음 시작은 녹음 탭에서만 제공한다. 공개 공유 링크는 제공하지 않으며 사용자가 M4A 파일을 내보내 직접 전달한다.
[p00026] 검색과 인기 차트의 브랜드 선택은 TJ와 금영(KY)이다. TJ와 태진은 같은 브랜드로 취급한다. 개인 곡·녹음은 TJ 번호를 기준으로 관리하고 TJ에서 찾지 못한 곡만 직접 등록한다. 금영은 검색·번호 확인을 지원한다. 금영 결과에서 내 곡 또는 플레이리스트로 등록하려면 ‘TJ에서 이 곡 찾기’로 이동하여 TJ 결과를 사용자가 선택해야 한다. 외부 검색·차트에서 플레이리스트로 직접 추가할 수 있는 결과는 TJ뿐이다. TJ에 없어 직접 등록한 내 곡은 기존 예외로 내 곡에서 플레이리스트에 추가할 수 있다.
[p00027] 초기에는 결제, 자동 음성 분석, 공개 피드, 실시간 공동 편집, 개인 드라이브 자동 백업을 구현하지 않는다. 무료 한도와 보관 정책은 서버에서 내려주어 이후 요금제 확장이 가능하게 한다.

[p00118] 2.1.1 내 곡 검색 범위
[p00119] 내 곡 탭의 검색창은 현재 로그인한 계정의 ACTIVE 상태 Song만 검색한다. 곡명 또는 가수명의 부분 일치를 사용하며 앞뒤 공백과 영문 대소문자 차이를 정리한다. 검색어가 비어 있으면 현재 필터에 맞는 내 곡 전체를 표시한다. 휴지통 곡, 다른 계정의 곡, 아직 등록하지 않은 TJ 후보, 플레이리스트에만 담긴 미등록 후보는 검색 결과에 포함하지 않는다.
[p00120] 내 곡 검색은 계정별 로컬 DB와 GET /songs를 사용하며 Manana를 호출하지 않는다. 오프라인에서도 같은 범위를 검색한다. 일치하는 내 곡이 없으면 ‘등록된 내 곡이 없습니다’를 표시하고, 별도 ‘새 곡 찾기’ 동작으로 검색 탭에 이동할 수 있다. 외부 검색 결과를 내 곡 결과 사이에 섞지 않는다. 한글·영문 가수명 별칭 자동 확장은 적용하지 않는다.
[p00121] 2.1.2 내 곡 보기와 정렬
[p00122] 내 곡은 전체 목록과 티어별 보기를 제공하고 기본은 전체 목록이다. 정렬 항목은 최근 추가순, 최근 녹음순, 티어순, 곡명순, 가수순의 5개이며 기본은 최근 추가순이다. 두 보기에서 같은 정렬값을 유지한다. 티어별 보기는 S→A→B→C→D→미정 그룹 순서를 고정하고 각 그룹 내부에 선택 정렬을 적용한다.
[p00123] 최근 추가순은 곡 생성 시각 내림차순이다. 최근 녹음순은 연결된 ACTIVE·SAVED 녹음의 가장 최근 recorded_at 내림차순이며 파일 존재 여부와 무관하다. 녹음 없는 곡은 마지막이다. 티어순은 S→A→B→C→D→미정, 동률은 곡명순이다. 곡명순·가수순은 한국어 표시명 기준으로 정렬하고 가수 동률은 곡명순이다. 모든 최종 동률은 Song.id 오름차순으로 결정한다. 서버와 로컬 DB는 동일한 정렬 규칙을 적용한다.
[p00124] GET /songs의 sort는 ADDED_DESC, RECORDED_DESC, TIER, TITLE, ARTIST 중 하나로 받는다. 기본은 ADDED_DESC이며 cursor는 정렬·검색 조건에 종속된다. 조건을 바꾸면 cursor를 초기화한다.

[p00157] 등록곡 여부는 song_id 또는 계정 내 정확히 일치하는 TJ 번호로 판단한다. 제목이나 가수명 유사성으로 연결하지 않는다. 내 곡 수정은 해당 Song을 참조하는 플레이리스트에 반영한다. 녹음의 당시 곡명·가수·키·버전·메모는 독립된 값이므로 곡 수정으로 덮어쓰지 않는다.
[p00158] 내 곡 목록은 Song.version_code, 녹음 기록 목록은 Recording.version_code를 표시한다. 두 목록 모두 일반 반주·MR·LIVE 중 저장된 값을 항상 보여주며 기본값도 생략하지 않는다. 같은 제목의 항목을 구별할 수 있도록 버전은 제목 가까이에 표시한다. 서로 다른 TJ 번호에 같은 버전이 지정된 경우에도 항목을 합치지 않으며 번호 확인은 곡 상세에서 한다.
[p00159] 검색·인기 차트 결과에는 개인 키·티어·별도 버전 필드를 표시하지 않는다. 등록 여부는 ‘내 곡 보기’ 같은 동작으로 구분할 수 있다. 원본 제목에 포함된 괄호·버전 문구는 임의로 삭제하지 않는다. 미등록 플레이리스트 후보는 곡명·가수만 표시하고, 내 곡 등록 후에는 해당 곡의 버전을 포함한 등록곡 표시로 전환한다.
[p00160] 2.3 곡 등록과 중복 방지
[p00161] TJ 결과를 선택하면 번호와 원본 곡명·가수를 서버가 검증한 후보에서 가져온다. 같은 계정의 같은 TJ 번호가 이미 있으면 기존 곡을 열고 다시 만들지 않는다. 다른 TJ 번호는 제목·가수가 같아도 별도 곡이다. 표기 수정이나 버전 수정은 식별 번호를 바꾸지 않는다.
[p00162] 금영 검색·차트 결과의 ‘TJ에서 이 곡 찾기’는 제목을 TJ 검색 입력에 미리 넣는 이동 동작이다. 사용자가 실제 TJ 결과를 선택해야 내 곡 등록 또는 플레이리스트 추가를 진행한다. 이동 전에 플레이리스트를 골랐다면 대상 목록을 유지한다. TJ 결과 선택을 취소하거나 결과를 찾지 못한 상태에서는 아무 항목도 추가하지 않는다. 금영 번호를 TJ 번호로 변환하거나 같은 제목의 TJ 결과에 자동 연결하지 않는다.
[p00163] 직접 등록은 정상적으로 TJ 검색을 시도했으나 원하는 곡을 찾지 못한 사용자가 ‘TJ에서 찾지 못한 곡 직접 등록’을 선택할 때 제공한다. 곡명·가수는 필수, 대표 키는 선택이고 TJ 번호를 직접 입력받지 않는다. 검색 장애는 곡이 없다는 근거로 사용하지 않는다. 장애 중에는 기존 내 곡을 사용하거나 입력을 대기 보관하고 검색을 재시도한다. 이미 TJ에서 찾지 못함을 확인해 시작한 직접 입력은 오프라인에서도 보존·완료할 수 있다.
[p00164] 직접 등록곡은 UUID로 식별한다. 같은 이름의 별도 직접 입력을 자동 합치지 않으며 기존 내 곡 선택을 우선 노출한다. 한글·영문 가수명 별칭 사전, 제목 유사도 병합, 브랜드 간 동일곡 추론은 구현하지 않는다. TJ 원본 검색에서 발생하는 표기별 검색 누락은 허용한다.
[p00165] 버전은 2.6의 선택값으로 저장한다. 같은 TJ 번호의 다른 버전을 별도 내 곡으로 생성하지 않는다. 직접 등록곡을 나중에 TJ 곡으로 연결하려면 새 TJ 곡을 선택·등록한 후 녹음을 명시적으로 재연결한다. 기존 곡의 식별 번호를 일반 수정 API로 바꾸는 기능은 제공하지 않는다.
[p00166] 2.3.1 플레이리스트 추가와 연결
[p00167] 외부 검색·인기 차트에서는 TJ 결과만 플레이리스트에 추가할 수 있다. 같은 계정에 해당 TJ 번호의 내 곡이 있으면 등록곡으로 연결하고, 없으면 TJ 미등록 후보로 담는다. 금영 결과에는 직접 추가를 제공하지 않으며 ‘TJ에서 이 곡 찾기’ 후 사용자가 선택한 TJ 결과로 추가한다. 금영 후보를 먼저 저장하거나 자동 변환하는 중간 단계는 만들지 않는다.
[p00168] 내 곡에서는 등록된 TJ 곡을 추가한다. TJ에서 찾지 못해 직접 등록한 MANUAL 곡도 기존 예외로 추가할 수 있다. 임의 금영 번호나 미등록 수동 후보를 플레이리스트 추가 요청에 넣는 것은 허용하지 않는다. 같은 곡을 서로 다른 플레이리스트에 넣는 것은 허용한다.
[p00169] 같은 플레이리스트의 중복 키는 TJ 후보·등록곡 모두 ‘tj:번호’, 직접 등록곡은 ‘manual:곡 UUID’이다. 동일 키를 다시 추가하면 기존 항목과 위치를 유지한다. 제목·가수·버전이 같아도 TJ 번호가 다르면 별도 항목으로 취급한다. 미등록 TJ 후보를 내 곡에 등록하면 같은 번호의 항목에 song_id만 연결하고 항목 ID·순서는 유지한다.
[p00170] 화면 제어와 별개로 서버는 후보의 검증된 브랜드가 TJ인지 검사한다. 금영 후보 요청은 PLAYLIST_TJ_REQUIRED로 거절하며 항목 생성·순서 변경을 수행하지 않는다. 계정별 동기화와 백업 가져오기에도 같은 후보 제약을 적용한다. 과거 형식의 금영 후보가 들어와도 자동 변환하지 않고 해당 목록 항목을 보류하여 TJ 결과를 다시 선택하도록 안내한다.
[p00171] 목록 항목 제거·플레이리스트 삭제는 내 곡·녹음을 삭제하지 않는다. 곡 삭제는 연결된 목록 항목을 숨기고 9장의 복원 규칙을 적용한다.

[p00235] 곡 등록과 녹음 입력에 같은 목록형 바텀시트를 사용한다. 한 행에 한 버전을 표시하고 현재 선택에 체크한다. 버전을 선택하지 않아도 일반 반주가 들어가므로 ‘미정’ 칸을 만들지 않는다. MV와 자유 입력 버전은 제공하지 않는다. 서버는 세 코드 외의 값을 거절한다.
[p00236] 새 녹음은 선택한 곡의 버전과 대표 키를 초기값으로 복사한다. 곡을 아직 선택하지 않았다면 NORMAL·ORIGINAL·0을 사용한다. 곡 선택이 바뀔 때 사용자가 아직 건드리지 않은 필드만 다시 채운다. 직접 변경한 키·버전은 유지하고 ‘곡의 기본값 적용’을 따로 제공한다.
[p00237] 곡 상세에서는 곡의 기본 버전을, 녹음 상세에서는 그 녹음의 버전을 언제든 수정할 수 있다. 휴지통 항목은 복원 후 수정한다. 두 값은 연쇄 변경하지 않는다. 예를 들어 곡의 기본 버전을 MR로 바꿔도 이전 일반 반주 녹음은 NORMAL을 유지한다. 녹음의 LIVE 선택도 곡 기본값을 바꾸지 않는다. 곡 버전을 수정하면 내 곡 목록과 그 곡에 연결된 플레이리스트 표시를 갱신한다. 녹음 버전을 수정하면 해당 녹음의 목록·상세를 갱신하며 다른 녹음의 표시는 바꾸지 않는다.
[p00238] 버전은 연습 기록을 위한 사용자 분류다. Manana의 구조화된 버전 필드나 모든 TJ 기기의 기능을 의미하지 않는다. MR 선택으로 키 조정 가능 여부를 추정하거나 입력을 잠그지 않는다. 버전 수정은 해당 곡 또는 녹음의 정보 수정이며 새 곡·녹음·음성 파일을 만들지 않는다. 파일이 현재 기기에 없어도 버전을 수정하고 동기화할 수 있다. [R11]
[p00239] 2.7 UI 구현과 소스 적용 기준
[p00240] 곡 상세의 언어 항목은 제거한다. Song의 language 필드는 개인 곡 모델·입력·응답에 두지 않는다. 아쉬운 점은 상세에서 읽고 곡 수정에서 최대 2,000자로 편집한다. 곡명·가수 표기 수정과 함께 저장 또는 취소하며 TJ 식별 번호는 바꾸지 않는다.
[p00241] 녹음 목록에는 곡명, 가수, 녹음 버전, 날짜, 키, 티어, 파일 보관 상태를 표시한다. 녹음 상세는 컨디션·태그·메모와 기록 시각 보정을 별도 녹음 정보 수정 화면에서 제공한다. 연결 곡 변경은 검색 가능한 내 곡 선택기로 진입하며 당시 곡명·가수·키·버전·메모를 덮어쓰지 않는다. 미연결 녹음에도 연결 동작을 제공한다.
[p00242] 전체 녹음 목록의 정렬 옆에 필터 버튼을 둔다. 기간, 곡·미연결, 키 모드·반음, 버전, 티어·미정, 컨디션, 태그, 파일 상태를 조합한다. 적용 전에는 목록을 바꾸지 않으며 취소는 기존 조건을 유지한다. 초기화 후 적용하면 전체 조건을 해제한다. 적용된 조건 수와 결과 개수, 결과 없음 안내를 표시한다.
[p00243] 곡 삭제 확인은 곡만 삭제하고 녹음 유지 또는 곡과 녹음 함께 삭제 중 선택한다. 7일 휴지통과 플레이리스트 숨김을 안내한다. 삭제 묶음과 이전 연결을 보존하고 9장의 조건으로 복원한다. 휴지통의 TJ 번호로 등록·목록 추가를 시도하면 복원을 먼저 안내한다.
[p00244] 설계서는 기능·데이터·API·보관 정책의 기준이고 HTML은 화면과 상호작용의 참고다. UI_REFERENCE.md와 ui_reference_palette.json은 같은 HTML 해시를 가리킨다. HTML의 샘플 로그인·녹음·서버 파일·검색·업로드·시간 진행은 실제 구현을 대체하지 않는다. 검수 패널은 앱 화면에 포함하지 않는다.

[p00274] 3.2 공통 불변 조건
[p00275] 1. 녹음 정보 동기화는 음성 파일 업로드 성공, 고정 개수, 서버 파일 용량에 의존하지 않는다.
[p00276] 2. 서버 파일이 준비되기 전에도 로컬 저장이 끝난 녹음은 재생·평가·메모 수정이 가능하다.
[p00277] 3. 보관 대상이라는 사실과 검증된 서버 파일이 있다는 사실을 다른 필드로 관리한다.
[p00278] 4. 어떤 자동 정리도 고정 파일을 삭제하지 않는다. 사용자의 명시적 녹음 삭제·고정 해제는 별도 동작이다.
[p00279] 5. 기기별 파일 존재 여부를 전역 has_local_file 값 하나로 표현하지 않는다.
[p00280] 6. 서버의 user_id는 인증 정보에서 결정한다. 요청 본문·백업 파일의 소유자 주장을 신뢰하지 않는다.
[p00281] 7. TJ 개인 곡은 계정과 번호로 유일하며 버전·가수명 표기는 유일 키가 아니다.
[p00282] 8. 버전별·키별로 자동 보관 3역할을 추가 배정하지 않는다.
[p00283] 9. 월별 차트는 요청한 브랜드·연월과 실제 집계 기간이 일치한 자료만 표시한다.
[p00284] 4 계정과 정보 동기화
[p00285] 4.1 로그인과 명시적 계정 연결
[p00286] User와 AuthIdentity를 분리하고 (provider, provider_user_id)를 유일하게 저장한다. Google·카카오 이메일은 참고 정보이며 같다는 이유로 계정을 연결하지 않는다. 서버는 각 공급자의 토큰·인증 결과에서 발급자, 앱 대상, 만료, 서명 또는 공급자 검증 응답을 확인한다. 클라이언트가 보낸 사용자 ID만으로 로그인시키지 않는다. [R4, R5]
[p00287] 계정 연결은 로그인 상태에서 기존 계정을 최근 재인증한 뒤 새 공급자 인증까지 완료해야 한다. 다른 User에 연결된 수단은 IDENTITY_IN_USE로 거절하고 자동 병합하지 않는다. 마지막 로그인 수단의 해제는 막는다. 인증 방식에 맞게 state·nonce와 해당 SDK가 지원하는 PKCE를 적용하고, 연결 도전값은 5분·1회 사용으로 제한한다.
[p00288] 앱 세션은 짧은 접근 토큰과 교체되는 갱신 토큰으로 관리한다. 초기 만료값은 접근 15분, 갱신 30일이며 서버 설정으로 둔다. 갱신 토큰은 서버에 해시로, 기기에는 OS 보안 저장소에 보관한다. 재사용이 감지된 갱신 토큰의 세션은 폐기한다. 로그아웃은 해당 기기 세션을 종료한다.
[p00289] 로그아웃해도 로컬 원본을 자동 삭제하지 않는다. 데이터는 원래 계정의 디렉터리와 DB 영역에 남겨 같은 계정으로 재로그인하면 다시 사용할 수 있게 한다. 다른 계정에서는 조회·재생·업로드하지 않는다. 미동기화 데이터가 있으면 로그아웃 전에 백업 경로를 제공한다.
[p00290] 4.2 오프라인 기록과 변경 전송
[p00291] 앱은 곡·녹음·목록 항목을 만들 때 UUID를 발급한다. 확정된 UUID를 로컬 DB, 서버, 백업에서 유지한다. 동일 TJ 번호의 동시 생성은 아래의 기존 곡 매핑 규칙을 먼저 적용한다. 로컬 저장과 전송할 변경 큐 등록을 한 트랜잭션으로 수행한다. 동기화 순서는 사용자 정의 항목·곡 생성, 녹음 정보 생성, 목록·관계 변경, 파일 업로드 순으로 처리한다.
[p00292] 녹음 정보는 DRAFT와 SAVED로 구분한다. DRAFT는 곡명 등이 비어 있어도 파일 상태와 입력 중 정보를 서버에 저장할 수 있다. SAVED 전환은 곡명·가수·키·유효한 버전과 재생 가능한 완료 파일의 크기·길이·체크섬을 검사한다. 서버 파일을 요구하지 않는다. 네트워크가 없으면 로컬에서 같은 조건으로 저장하고 이후 정보만 먼저 전송한다.
[p00293] 다른 기기가 서로 다른 UUID로 같은 TJ 곡을 먼저 만들었다면 서버는 기존 canonical_song_id를 반환한다. 앱은 새 UUID를 기존 UUID에 매핑하고 대기 중 녹음·목록 참조를 로컬 트랜잭션으로 함께 변경한다. 새 녹음 UUID와 파일은 유지한다. 중복 생성 요청의 메모·키·버전으로 서버 값을 덮어쓰지 않으며, 값이 다르면 사용자 선택이 필요한 편집으로 보존한다.
[p00294] 각 변경은 op_id, 대상 id, base_revision을 포함한다. 같은 작업 재전송은 중복 반영하지 않는다. 서버가 승인한 변경만 로컬 동기화 완료로 표시한다. 응답 유실 시 상태 조회 또는 같은 op_id 재시도로 결과를 확인한다.

[p00311] 서버는 계정별 증가 change_seq와 변경 로그를 제공한다. 쓰기 트랜잭션은 계정의 동기화 행을 잠근 뒤 번호를 부여하고 업무 변경과 함께 커밋하여, 커밋되지 않은 번호를 건너뛰는 문제가 없게 한다. 앱은 성공적으로 반영한 마지막 커서만 저장한다.
[p00312] 최초 동기화는 일관된 서버 스냅샷과 그 기준 커서를 받는다. 큰 목록의 여러 페이지가 같은 시점을 나타내도록 스냅샷 토큰을 사용한다. 변경 로그는 90일 보관하고 만료 커서는 CURSOR_EXPIRED로 전체 재동기화를 요구한다. 로컬 미전송 변경은 별도 보존해 재적용한다. 일반 변경 로그와 별개로 영구 삭제 UUID 표식은 계정이 유지되는 동안 남겨 오래된 백업의 자동 부활을 막는다.
[p00313] 5 녹음과 상태 모델
[p00314] 5.1 녹음의 시작과 완료
[p00315] 녹음 탭에는 ‘최대 녹음 시간 6분’을 항상 표시한다. 마이크 권한과 저장 공간을 확인하고 화면이 보이는 상태에서 microphone 포그라운드 서비스를 시작한다. Android 버전에 맞는 RECORD_AUDIO, FOREGROUND_SERVICE 및 마이크 서비스 권한·알림 처리를 구현한다. 앱이 백그라운드에 있다는 이유로 새 녹음을 자동 시작하지 않는다. [R1]
[p00316] AAC-LC 96kbps, 48kHz, 모노, M4A로 녹음한다. 경과 시간은 서비스의 단조 증가 시계를 기준으로 계산한다. 5분 30초와 5분 50초에 화면과 소리 없는 진행 알림으로 종료 임박을 알리고 6분에 종료한다. 안내음과 진동은 사용하지 않는다. 진행 알림에서 수동 종료할 수 있다.
[p00317] 녹음 시작 전에 recording_id와 복구 저널을 기록한다. 종료 후 파일을 마무리하고 재생 가능 여부·길이·크기·SHA-256을 확인한 뒤 영속 경로로 이동한다. 파일과 DB 사이에 중단이 발생하면 저널을 이용해 같은 ID로 복구한다. 필수 정보가 부족하면 입력 대기로 남기며, 화면을 닫아도 파일을 보존한다.
[p00318] 원본 경로는 계정 전용 영속 디렉터리 아래에 두고 캐시를 사용하지 않는다. 휴대폰 원본을 기간 기준으로 자동 삭제하지 않는다. 앱 삭제 시 앱 전용 데이터가 제거될 수 있으므로 앱 밖에 저장한 백업이 필요하다. [R2]

[p00340] 사용자 삭제와 영구 삭제 상태
[p00342] STORED는 최종 객체가 검증되고 DB 확정까지 끝난 상태다. QUEUED는 대상 선정만 끝난 상태이며 파일 보관 완료를 뜻하지 않는다. 기존 STORED 파일의 안전한 정리 대기는 CloudHold로 표현하고 파일을 지우기 시작할 때만 DELETING으로 바꾼다. 업로드 개별 시도의 실패·만료는 RecordingUpload에 기록한다.
[p00343] 로컬 입력이 끝난 SAVED 녹음 상세에서는 오프라인으로도 티어를 지정할 수 있다. 서버 API는 metadata_state=SAVED, lifecycle_state=ACTIVE를 검사한다. 녹음 중·필수 정보 입력 화면에서는 티어 입력을 제공하지 않는다.
[p00344] 5.3 중단과 재시도

[p00346] 동작

[p00363] 6 자동 보관과 무료 고정
[p00364] 6.1 자동 보관 대상 선정
[p00365] 선정 단위는 사용자 소유의 곡 1개이며 키별·버전별로 따로 3개씩 보관하지 않는다. 다른 TJ 번호로 등록된 별도 곡은 각각 선정하되 계정 전체 1GB 제한을 함께 적용한다. 후보는 해당 곡에 연결된 ACTIVE·SAVED 녹음 중 완료 파일 정보가 유효한 기록이다. 입력 대기·손상·휴지통 기록은 제외한다. 파일이 다른 기기에만 있어도 대상 선정은 가능하지만 실제 업로드는 파일을 가진 기기나 백업 복원 후 진행한다.

[p00379] 세 역할의 recording_id를 집합으로 합친다. 한 녹음이 세 역할을 모두 충족하면 파일은 1개만 보관한다. 겹친 역할을 다른 차순위 파일로 채워 3개를 맞추지 않는다. 곡 티어는 이 계산에 사용하지 않는다.
[p00380] 새 녹음 저장, 녹음 티어·기록 시각 보정, 대표 지정·해제, 삭제·복원, 곡 재연결 때 선정 결과와 selection_revision을 갱신한다. 기록 시각은 자동 입력을 기본으로 하되 기기 시각 오류를 사용자가 상세에서 보정할 수 있게 하며 변경 이력을 남긴다. 서버는 같은 입력에 항상 같은 결과를 내야 한다.
[p00381] 6.2 계정 전체 무료 고정 10개
[p00382] 고정은 자동 선정에서 빠져도 서버에 남기려는 사용자의 선택이다. 계정 전체에 10개를 제공하며 곡마다 10개가 아니다. 곡 미연결 녹음도 고정할 수 있다. 고정 대상은 ACTIVE·SAVED 녹음으로 제한한다.
[p00383] 고정한 녹음이 자동 역할도 갖고 있으면 실제 파일과 사용 바이트는 1번만 센다. 고정 슬롯은 1개 사용한다. 자동 역할이 나중에 사라져도 고정 사유가 남는다. 고정을 해제해도 자동 사유가 남아 있으면 서버 파일을 유지한다.
[p00384] 고정 요청을 승인한 시점부터 슬롯을 예약한다. 업로드 대기·실패 중에도 그 슬롯을 차지하며 사용자는 대기 고정을 취소할 수 있다. 남은 슬롯 검사는 서버 트랜잭션으로 수행한다. 9개에서 두 기기가 동시에 다른 파일을 고정해도 한 요청만 10번째 슬롯을 얻는다.

[p00423] 7 안전한 교체와 용량 제한
[p00424] 7.1 자동 대상이 바뀔 때
[p00425] 새 최신 녹음이나 티어 변경으로 자동 대상이 바뀌어도 이전 서버 파일을 먼저 삭제하지 않는다. 서버는 새 선정 결과를 저장하고 필요한 업로드를 요청한다. 교체될 기존 객체에는 PENDING_REPLACEMENT 보존 사유를 둔다.
[p00426] 1. 최신 selection_revision으로 새 대상을 계산하고 중복을 제거한다.
[p00427] 2. 새 파일이 이미 STORED이면 재사용한다. 없으면 파일을 가진 기기에 업로드 대기를 표시한다.
[p00428] 3. 새 파일의 검증·DB 확정을 끝낸 후 관련 보존 사유를 다시 계산한다.
[p00429] 4. 이전 파일에 고정·다른 자동 역할·미연결 보존 사유가 있으면 그대로 유지한다.
[p00430] 5. 아무 보관 사유도 남지 않은 파일은 아래의 로컬 보존 확인을 거친 뒤 서버 사본만 정리한다.
[p00431] 업로드 실패, 파일 부재, 예산 잠금, 용량 부족이면 기존 파일을 유지하고 새 파일을 대기시킨다. 이후 더 최신 대상이 생기면 오래된 미시작 업로드는 취소하되 원본과 녹음 정보는 남긴다. 지연 도착한 작업은 현재 정책 버전을 다시 확인한다.
[p00432] 7.2 서버 사본 정리 전 로컬 보존 확인
[p00433] 정리 후보는 WAITING_LOCAL_CONFIRM으로 보존한다. 로그인한 기기가 같은 recording_id·SHA-256의 파일을 영속 디렉터리에 가지고 있는지 실제로 확인해야 한다. 파일이 없으면 서버에서 먼저 다운로드하고 체크섬을 검증한다. 원래 녹음했던 기기가 온라인이었다는 과거 보고만으로 정리하지 않는다.
[p00434] 앱은 자동 대상이 바뀌면 로컬 사본을 확인한 뒤 서버 사본을 정리한다는 정책을 보관 설정에 설명한다. 자동 확인이 불가능한 파일은 계속 서버에 남기고 설정에서 확인·다운로드·정리를 제공한다. 사용자는 별도 확인 화면에서 서버 사본 손실을 이해하고 수동으로 정리할 수도 있다. 이 확인 없이 서버에만 남은 마지막 사본을 자동 삭제하지 않는다.
[p00435] 정리 확인은 객체 generation, checksum, cloud_revision에 묶은 15분 유효 토큰으로 처리한다. 앱은 확인한 로컬 파일을 정리 결과가 확정될 때까지 자체 파일 정리에서 제외한다. 서버는 삭제 직전에 같은 버전·무보호 상태를 잠금으로 재검사하고 DELETING으로 전환한다. 만료된 확인으로 새 삭제를 시작하지 않는다.
[p00436] DELETING 중 새 고정 요청은 FILE_CLEANUP_IN_PROGRESS로 대기시킨다. 완료 후 로컬 사본으로 다시 보관할 수 있다. 삭제 시작 전에 고정이 승인됐다면 삭제 작업은 취소된다. 삭제 실패·응답 유실 시 파일 존재를 재확인하고 결과가 확정될 때까지 사용량을 줄이지 않는다.
[p00437] 정리 확인으로 자동 역할이나 고정을 강제로 해제하지 않는다. PENDING_REPLACEMENT는 현재 대체 대상이 모두 STORED이거나 해당 역할 자체가 해제된 뒤에만 끝낸다. WAITING_LOCAL_CONFIRM과 정리 가능한 ORPHAN_KEEP은 유효한 로컬 보존 확인 또는 사용자 손실 확인을 받은 트랜잭션에서 해제하고 DELETING으로 전환한다. 원래 계정과 객체 generation이 일치해야 하며 정리 가능한 파일이 없으면 공간 확보를 약속하지 않고 대기 상태를 유지한다.
[p00438] 7.3 고정 대상 교체
[p00439] 고정 10개를 모두 사용한 경우 ‘고정 교체’에서 기존 1개와 새 1개를 선택한다. 같은 슬롯에 current_recording_id와 pending_recording_id를 저장한다. 교체 중에도 슬롯 사용 수는 1개다. 기존 파일의 고정 보호는 새 파일이 STORED가 될 때까지 유지한다.
[p00440] 새 파일 보관이 확정되면 슬롯 대상을 원자적으로 바꾸고 기존 파일의 사유를 다시 계산한다. 기존 파일에 자동 역할이 있으면 계속 보관한다. 고정만 해제된 파일은 7.2의 정리를 따른다. 실패·용량 부족 시 이전 고정이 유지되며 사용자가 교체를 취소하거나 나중에 재시도할 수 있다.
[p00441] 기존 파일을 지우면 자리가 생기더라도 교체 중에 한도를 초과하도록 자동 허용하지 않는다. 필요한 여유가 없으면 안전하게 대기한다. 사용자가 별도 파일을 내보내고 서버 사본을 명시적으로 정리하여 공간을 확보할 수 있다.

[p00494] 서명 URL은 만료 전 재사용될 수 있다. 따라서 임시 객체를 한 번 HEAD로 확인한 뒤 그대로 최종 파일로 믿지 않는다. 작업자가 내려받은 바이트를 검사하고 그 바이트를 최종 경로에 작성한다. 확정 파일이 기존 PUT URL로 덮어써지지 않아야 한다. [R6]
[p00495] 8.2 검증 조건과 작업 제한
[p00496] 서버는 실제 바이트 수가 신고값과 같고 6MiB 이하인지 확인한다. 다운로드 중에도 6MiB를 넘으면 읽기를 중단하여 과대 파일을 무제한 적재하지 않는다. SHA-256은 앱 명세와 서버 계산값이 일치해야 한다. 확장자와 Content-Type만 믿지 않고 M4A 컨테이너, AAC-LC, 모노, 48kHz, 0초 초과·361초 이하, 전체 디코딩 가능 여부를 확인한다. 비트레이트는 녹음기 목표값 96kbps이며 컨테이너 오버헤드와 인코더 편차 때문에 계산상 정확히 96kbps여야 한다고 검사하지 않는다. [R7]
[p00497] 검증 도구는 제한된 작업 환경에서 시간·메모리·출력 크기 제한을 두고 실행한다. 초기 작업 제한은 파일당 60초, 동시 검증 2개다. 제한 초과는 FILE_VALIDATION_TIMEOUT으로 분류하고 파일을 정상으로 확정하지 않는다.
[p00498] 예약 시점에는 보관 대상이었으나 검증 중 대상에서 빠진 경우 현재 정책과 삭제 상태를 재검사한다. 더 이상 필요한 사유가 없으면 최종 확정하지 않고 임시·미확정 객체를 정리한다. 그 요청 때문에 기존 보관 파일이나 로컬 원본을 삭제하지 않는다.
[p00499] 8.3 만료와 장애 복구
[p00500] 시도 상태는 RESERVED→UPLOADING→VERIFYING→COMMITTED이며 FAILED·EXPIRED·CANCELLED가 종료 상태다. 생성 후 24시간 동안 완료되지 않은 시도는 만료한다. URL 재발급은 같은 시도에서 가능하지만 전체 만료일은 연장하지 않는다. 만료 후에는 파일 존재·검증 작업 여부를 대조한 뒤 새 시도를 허용한다.
[p00501] 업로드 URL로 파일 상한을 완전히 강제했다고 가정하지 않는다. 임시 저장량을 따로 감시하고 과대 객체는 삭제한다. 늦은 PUT이 가능한 임시 경로는 URL 만료가 지난 뒤 다시 검사한다. 임시 객체에는 2일 정리 규칙을 보조 수단으로 두되 활성 검증 작업과 충돌하지 않게 한다.
[p00502] 최종 객체 기록 후 DB 응답이 실패하면 같은 attempt_id와 미리 기록한 최종 키로 재검사하여 COMMITTED를 복구한다. 같은 확정·예약 해제·삭제를 반복해도 바이트는 한 번만 반영한다. 매일 DB 사용량과 실제 최종 객체, 임시 객체, 미완료 작업을 대조한다.
[p00503] 8.4 재생과 파일 내보내기
[p00504] 재생은 체크섬이 일치하는 로컬 파일을 우선한다. 로컬 파일이 없고 STORED이면 서버가 인증·소유권·수명 상태를 검사한 뒤 5분 내부 GET URL을 발급한다. 만료 시 새로 요청하며 URL을 제품의 공유 링크로 노출하지 않는다. 발급된 URL은 만료까지 유효할 수 있음을 접근 회수 설계에 반영한다. [R6]
[p00505] M4A 내보내기는 시스템 파일 선택기로 앱 밖의 사용자 지정 위치에 저장한다. 임시 보관함의 재생 가능한 완료 파일도 내보낼 수 있다. 곡명·가수는 파일명에 사용할 수 있지만 경로 구분자 등을 제거하고 중복 파일명은 구분한다. 내보낸 독립 사본은 앱의 삭제·탈퇴로 회수되지 않는다.

[p00549] 곡만 삭제하면 대표 지정을 해제하고 미연결 목록에 녹음을 모은다. 당시 곡명·가수·키·버전·티어·컨디션·메모는 남긴다. 이미 서버에 보관 중인 파일에는 ORPHAN_KEEP 사유를 추가하여 곡의 자동 역할이 사라져도 파일을 지우지 않는다. 이 사유는 고정 슬롯을 소비하지 않지만 총용량에는 포함한다. 원래 고정된 파일의 고정도 유지한다.
[p00550] 곡 삭제 시 진행 중이던 승인 업로드도 녹음 유지 선택이면 ORPHAN_KEEP 대상으로 완료할 수 있다. 아직 승인된 업로드가 없던 미연결 파일은 로컬에 남고, 새 서버 업로드는 고정 또는 곡 재연결 후 선정될 때 수행한다.
[p00551] 다른 곡에 재연결하면 원래 녹음 키·버전과 스냅샷은 유지하고 새 곡의 보관 대상을 다시 계산한다. ORPHAN_KEEP 파일이 새 자동·고정 사유로 보호되면 예외 사유를 제거한다. 해당하지 않는 파일은 7.2의 보존 확인·정리를 거치기 전까지 유지한다.
[p00552] 9.3 휴지통과 복원
[p00553] 휴지통 기간은 서버가 확정한 deleted_at부터 7일이다. 기존 휴지통 항목을 다시 삭제 묶음에 넣어 만료일을 늘리지 않는다. 로컬에서 오프라인 삭제한 항목은 전송 전까지 ‘삭제 동기화 대기’로 숨기고 원본은 유지한다.
[p00554] TRASHED 녹음의 로컬 파일은 휴지통 표시로 보존한다. 서버에서 복원되면 같은 파일을 다시 연결하고, PURGED를 동기화한 뒤 해당 계정의 원본을 제거한다. 장기간 오프라인인 기기는 휴지통 기간이 지났다는 기기 시각만으로 원본을 지우지 않는다. 사용자가 ‘이 기기 파일 정리’를 따로 확인한 경우는 그 선택을 따른다.
[p00555] 곡만 삭제 후 복원하면 같은 묶음에서 분리됐고 이후 연결을 변경하지 않은 활성 녹음만 원래 곡에 재연결한다. 다른 곡에 연결한 녹음을 덮어쓰지 않는다. 함께 삭제한 경우 같은 묶음에서 삭제한 항목만 복원한다. 곡이 영구 삭제됐으면 녹음은 미연결로 복원할 수 있다.
[p00556] 남아 있는 플레이리스트에는 entry_key 중복 없이 끝에 복원한다. 같은 키의 활성 항목이 이미 있으면 기존 항목과 위치를 유지하고 숨겨진 중복 항목은 되살리지 않는다. 삭제 시 해제한 대표 녹음은 자동 재지정하지 않는다. 녹음 삭제 시 고정 슬롯은 해제하며 복원 시 자동으로 고정을 되살리지 않는다. 복원 결과에 ‘고정은 다시 선택해야 함’을 표시한다. 실제 서버 파일이 남아 있으면 복원 후 보관 사유를 재계산하고 안전하게 정리한다.
[p00557] 휴지통 곡의 TJ 번호도 같은 계정에서 예약된 상태로 유지한다. 같은 번호를 다시 등록하거나 그 번호의 후보를 목록에 추가하려면 기존 곡의 복원을 안내한다. 휴지통 예약을 미등록 후보 생성으로 우회하지 않는다. PURGE_PENDING이면 완료를 기다리고, PURGED 확정 뒤에는 새 UUID로 다시 등록할 수 있다. 이전 UUID의 삭제 표식은 유지하여 오래된 백업이 예전 곡을 부활시키지 못하게 한다.
[p00558] 9.4 영구 삭제와 계정 삭제
[p00559] 영구 삭제는 PURGE_PENDING과 삭제 작업을 DB에 먼저 기록한다. 업로드 완료 요청은 수명 상태를 재확인하여 기록을 되살리지 않는다. R2 객체 삭제가 확인된 뒤 사용량을 한 번만 차감하고 PURGED로 확정한다. 곡 영구 삭제는 보존하기로 한 녹음을 연쇄 삭제하지 않는다. PURGED 확정 시 그 곡 삭제 묶음 때문에 숨겨진 PlaylistItem을 제거하여 entry_key를 해제한다. 이후 같은 TJ 번호의 새 곡을 목록에 추가할 수 있다.
[p00560] 계정 삭제는 최근 재인증 후 요청한다. 앱 내부와 외부 웹 경로에서 요청할 수 있게 하고 요청 완료·처리 상태를 제공한다. 요청 즉시 세션·새 URL 발급·업로드를 막고 개인 데이터와 파일 삭제 작업을 시작한다. 운영 백업에는 최대 7일 잔존할 수 있다는 실제 정책을 안내한다. [R9]
[p00561] 삭제 원장은 별도 보관하여 서버 복구 전에 재적용한다. 살아 있는 계정의 영구 삭제 UUID는 재생성 방지에 필요한 최소 정보만 유지한다. 탈퇴 계정의 삭제 원장은 관련 백업 소멸을 확인한 뒤 최대 30일 내 정리한다. 오프라인 기기에는 재연결 시 계정별 삭제 상태를 적용하며, 오프라인 파일이나 앱 밖 사본까지 원격 삭제됐다고 표시하지 않는다.
[p00562] 10 백업과 기기 이전
[p00563] 10.1 사용자 백업 만들기
[p00564] 첫 출시부터 백업 내보내기와 가져오기를 제공한다. 설정에서 대상과 필요한 임시 공간을 확인하고 시스템 파일 선택기로 ZIP을 앱 밖에 저장한다. 기기 분실까지 대비하려면 백업을 별도 기기나 사용자의 저장 서비스에도 옮겨 두도록 안내한다.
[p00565] 백업은 서버 스냅샷에 로컬 미전송 변경과 파일을 합쳐 만든다. 충돌 중인 값은 한쪽을 버리지 않고 기준 revision과 로컬 변경을 별도 영역에 기록한다. 진행 중 녹음은 안전하게 종료한 뒤 백업하며, 백업 중 새로 생긴 데이터는 포함 기준 시각 이후임을 결과에 표시한다.

[p00581] 활성 녹음과 미연결 녹음, 입력 대기의 완료 파일을 포함한다. 휴지통 포함은 별도 선택이다. 이 기기에 없는 STORED 파일은 순차 다운로드 후 체크섬을 검사하여 포함한다. 다른 기기에만 있고 서버에도 없는 파일은 포함할 수 없으므로 누락으로 명시한다. 일부 누락을 ‘전체 백업 완료’로 표시하지 않는다.
[p00582] 공용 검색 캐시·월별 차트는 개인 백업 대상에서 제외한다. ZIP에는 인증 토큰·서버 비밀키를 넣지 않는다. 초기 사용자 ZIP은 일반 파일이므로 개인정보와 녹음이 포함됨을 내보내기 화면에 안내한다. 운영 백업의 암호화 정책과 사용자 ZIP 형식을 혼동하지 않는다. CSV 문자열의 수식 시작 문자는 안전하게 이스케이프한다.
[p00583] 10.2 새 기기에서 가져오기
[p00584] 1. 원래 사용하던 동일 계정으로 로그인해 서버 정보와 삭제 표식을 먼저 받는다.
[p00585] 2. 백업 ZIP의 형식 버전과 계정 일치를 확인한다. 계정이 다르면 가져오기를 거절한다.
[p00586] 3. 압축 경로, 중복 경로, 크기, 체크섬과 파일 형식을 검증하고 임시 영역에서 미리보기를 만든다.
[p00587] 4. 기존 recording_id는 같은 녹음에 파일을 연결하고, 서버에 없는 미전송 UUID는 삭제 표식이 없는 경우 새 정보로 등록한다.
[p00588] 5. 더 최신 서버 정보가 있으면 유지한다. 같은 필드의 로컬 변경은 충돌로 남겨 사용자가 선택한다.
[p00589] 6. 파일 연결과 로컬 DB 반영 후 누락·충돌·실패 집계를 보여준다. 서버 업로드 대상은 현재 정책으로 다시 계산한다.
[p00590] 가져오기 사전 검사에서는 곡 UUID 외에 source_type과 TJ 번호도 검사한다. 먼저 영구 삭제 UUID를 차단하고, 삭제되지 않은 신규 UUID의 TJ 번호가 기존 활성 곡과 같으면 그 곡에 매핑한다. 참조하는 녹음·목록도 함께 매핑하되 녹음 UUID와 당시 버전·키·메모는 유지한다. 기존 곡의 메모·버전은 자동 덮어쓰지 않는다. 같은 번호가 휴지통·삭제 대기라면 해당 항목을 보류하고 복원 또는 삭제 완료 후 처리한다.
[p00591] 플레이리스트 후보도 TJ 브랜드·출처·번호를 검사한다. 구조와 파일이 정상인 백업에 이전 금영 후보가 있으면 그 목록 항목만 보류하고 미리보기·결과에 사유와 TJ 검색 경로를 표시한다. 후보를 자동 변환하거나 전체 녹음 파일을 버리지 않는다. 잘못된 ZIP 구조나 파일 해시의 처리에는 10.3을 적용한다.
[p00592] 같은 백업을 다시 가져와도 곡·녹음·목록이 중복 생성되지 않아야 한다. 존재하는 로컬 파일은 체크섬이 같으면 재사용하고 다르면 자동 덮어쓰지 않는다. 녹음 정보의 당시 스냅샷과 파일 설명이 다른 경우도 충돌로 분류한다. 복구된 로컬 파일을 전부 서버에 올리지 않는다.
[p00593] 기존 서버의 대표·고정 선택은 백업의 과거 값으로 자동 덮어쓰지 않는다. 서버에 없는 새 곡의 대표 연결은 소유권·후보 조건을 검사해 복원할 수 있다. 백업의 고정 목록은 복원 미리보기에 제시하고 사용자가 선택하면 현재 10개 한도 안에서 신청한다. 오래된 ZIP 때문에 한도를 넘거나 서버의 고정 해제가 취소되지 않아야 한다.
[p00594] 10.3 잘못된 백업과 중단 대응
[p00595] 압축 해제 시 절대 경로, 상위 경로 이동, 심볼릭 링크, 중복 경로를 거절한다. 선언된 크기뿐 아니라 실제 추출 바이트 수를 제한한다. 초기 한도는 항목 100,000개, JSON 합계 100MiB, 음성 파일당 6MiB이며 디스크 여유가 부족하면 시작하지 않는다. 음성은 이미 압축된 형식이므로 과도한 압축 비율도 거절한다.
[p00596] 백업 전체의 구조·필수 JSON·파일 해시 검증을 끝내기 전에는 기존 데이터를 변경하지 않는다. 손상 파일이 있으면 전체 복원을 중단하고 오류 목록을 보여준다. 정상 파일만 가져오는 동작은 별도 선택으로 실행한다. 승인된 가져오기는 import_job_id와 항목별 결과로 재개하며, 실패해도 기존 정상 파일을 덮어쓰거나 삭제하지 않는다.
[p00597] 서버에 영구 삭제 표식이 있는 UUID는 자동 복원하지 않는다. 새 기기에서 정보 100개 중 파일 25개만 복원됐다면 두 수치를 구분한다. 최근 백업 날짜만으로 누락 파일이 없다고 판단하지 않는다.
[p00598] 10.4 서비스 장애 복구용 백업
[p00599] MySQL은 매일 일관된 스냅샷을 암호화하여 최근 7개 일일 복구 지점을 보관한다. 확정 파일은 운영 삭제 권한과 분리된 계정·자격 증명의 백업 영역에 증분 복사한다. DB 시점의 파일 목록·체크섬과 일치한 묶음만 복구 가능한 백업으로 표시한다. 임시 업로드 객체는 백업하지 않는다.
[p00600] 활성 파일은 사본을 유지하고 최종 삭제 파일은 최대 7일 이내 백업에서도 정리한다. 복구 전에 삭제 원장을 반영하여 탈퇴·영구 삭제 파일이 다시 노출되지 않게 한다. 손실 범위와 서비스 복구 시간은 각각 24시간 이내를 초기 목표로 두며 검증 전 보장값으로 안내하지 않는다.
[p00601] 출시 전 1회, 이후 월 1회 별도 환경에서 DB 복원, 파일 대조, 체크섬·재생, 삭제 원장 재적용을 시험한다. 백업 실패는 운영 경고로 처리하며 백업 파일이 생성됐다는 사실만으로 성공 판정하지 않는다.
[p00602] 11 데이터 모델과 제약
[p00603] 11.1 공통 데이터 규약
[p00604] 서버 UUID는 BINARY(16), API·백업은 하이픈이 있는 UUID 문자열로 표현한다. 사용자 입력 문자열은 utf8mb4를 사용한다. 시각은 UTC DATETIME(3), 바이트는 BIGINT, revision과 change_seq는 양의 BIGINT로 저장한다. 클라이언트 시각은 업무 기록이고 수정 순서의 기준은 서버 revision이다.
[p00605] 아래 표에서 NN은 NOT NULL, UQ는 UNIQUE를 뜻한다. id가 있는 개인 업무 테이블은 (user_id,id)에도 유일 인덱스를 두어 복합 외래키로 소유자 일치를 강제한다. 복합 PK 테이블은 같은 방식으로 소유자와 대상 키를 묶는다. 소유권 API 검사도 함께 적용한다. soft delete가 필요한 관계에는 물리 CASCADE DELETE를 사용하지 않는다. 사용자 편집 대상에는 created_at·updated_at·revision을 공통으로 두며 표에는 반복 표기를 생략할 수 있다.

[p00679] PK(chart_month_id,position), UQ(chart_month_id,number). 순위 동률은 허용
[p00681] PlaylistItem의 song_id가 있으면 같은 사용자의 Song을 참조하고 버전·키·표시 정보를 그 곡에서 읽는다. 새 연결은 ACTIVE 곡만 허용하며, 휴지통으로 이동한 곡의 기존 항목은 관계를 유지한 채 숨긴다. song_id가 없으면 candidate_brand=TJ, candidate_number, candidate_snapshot이 필수다. candidate_brand는 null 또는 TJ만 허용하는 DB 제약을 둔다. 연결 후에도 TJ 후보 원본은 출처로 보존할 수 있지만 표시 기준은 Song이다. MANUAL 연결곡은 후보 필드를 비워 둔다. 임의 자유 입력 미등록 후보는 만들지 않고 직접 등록곡을 생성한 뒤 목록에 추가한다.
[p00682] entry_key는 서버가 계산한다. TJ 연결곡과 TJ 후보는 동일한 ‘tj:번호’, MANUAL 연결곡은 ‘manual:곡 UUID’를 쓴다. 금영 entry_key는 생성하지 않는다. 송신자가 임의 키로 중복 검사를 우회할 수 없다. 후보 번호와 동일한 TJ 곡을 생성하면 해당 사용자의 미등록 TJ 항목을 연결하고 변경 로그에 반영한다. 이미 연결된 항목이나 다른 번호의 후보는 변경하지 않는다.
[p00683] 목록 순서 변경은 Playlist revision과 전체 활성 항목 ID 순서를 제출하여 한 트랜잭션으로 position을 재부여한다. 누락·중복 ID와 다른 목록 ID는 거절한다. 후보 연결·추가·제거도 Playlist revision을 갱신한다. 태그·컨디션 삭제는 archived_at으로 신규 선택에서 숨기고 과거 관계·표시명은 유지한다.
[p00684] 월별 차트는 계정별 데이터가 아니며 개인 동기화 로그·백업에 넣지 않는다. 한 연월의 항목 전체를 검증한 뒤 게시 revision을 원자적으로 교체한다. 수집 도중의 일부 목록은 조회에 노출하지 않는다. ChartItem의 number는 브랜드 내 후보 식별용이며 개인 Song 생성 시 TJ 규칙을 다시 적용한다.
[p00685] 11.5 보관 정책과 사용량

[p00742] 12 API 계약
[p00743] 12.1 공통 요청과 응답
[p00744] 기본 경로는 /v1이다. 개인 데이터 API에는 Bearer 토큰과 등록한 device_id를 사용한다. 생성·변경·삭제 명령은 Idempotency-Key 헤더의 UUID를 op_id로 사용하고 변경 대상의 base_revision을 보낸다. 같은 키·같은 본문은 같은 결과를 반환하고, 같은 키·다른 본문은 IDEMPOTENCY_CONFLICT다.
[p00745] 생성 UUID가 이미 존재하면 소유권 확인 후 기존 정보를 반환하며 다른 내용으로 덮어쓰지 않는다. 변경은 PATCH와 현재 revision을 사용한다. 영구 삭제 UUID의 재생성은 거절한다. MutationReceipt 보존 기간이 지나도 UUID 유일성·base_revision 검사를 유지한다. 목록 항목 추가·삭제·순서 변경의 base_revision은 해당 Playlist 버전이다.
[p00746] 생성은 201, 조회·즉시 변경은 200, 비동기 작업 접수는 202로 반환한다. 비동기 응답에는 operation_id와 조회 경로를 포함한다. 리소스에는 id, revision, updated_at을 포함하고 서버 파일 상태는 녹음 정보와 별도 필드로 반환한다. 다른 사용자의 리소스 ID는 존재 여부가 드러나지 않도록 404로 처리한다.
[p00747] 목록 조회는 불투명 cursor와 limit를 사용한다. 기본 50개, 최대 100개다. 서버에서 정렬과 필터를 적용하고 안정적인 ID 동률 정렬을 포함한다. 누락 필드는 유지, 명시적 null은 허용된 필드의 해제라는 PATCH 규칙을 따른다.

[p00828] GET /songs는 인증에서 user_id를 결정하고 ACTIVE Song의 곡명·가수에서 q를 검색한다. 제목·가수의 부분 일치와 공백·대소문자 처리 기준은 2.1.1과 같고 로컬 검색에도 동일하게 적용한다. 외부 API나 미등록 플레이리스트 후보를 조회하지 않는다. 응답은 version_code와 목록 표시 필드를 포함한다.
[p00829] TJ 신규 곡 생성은 201과 song_id를 반환한다. 동일 번호의 ACTIVE 곡이 있으면 200, created=false, canonical_song_id, 최신 revision을 반환하고 요청의 편집값으로 기존 곡을 덮어쓰지 않는다. TRASHED는 SONG_RESTORE_REQUIRED, PURGE_PENDING은 SONG_PURGE_PENDING으로 거절한다. 같은 요청 UUID가 PURGED이면 번호 재사용 가능 여부보다 UUID 삭제 표식 검사를 우선한다.
[p00830] TJ 곡 생성의 후보 증명은 13.1의 source_token 또는 서버가 확인한 번호 조회 결과다. 클라이언트가 brand만 TJ라고 보내 금영 결과를 등록할 수 없게 한다. MANUAL은 title·artist와 manual_reason=TJ_NOT_FOUND를 요구하고 tj_number를 거절한다. 이 사유는 사용자의 검색 결과 확인이며 전 세계 목록에 없음을 보증하는 값은 아니다.
[p00831] 플레이리스트 후보 추가는 서버가 검증한 source_token의 브랜드가 TJ일 때만 허용한다. 유효한 금영 토큰도 400 PLAYLIST_TJ_REQUIRED로 거절한다. song_id 방식은 같은 사용자의 ACTIVE TJ 또는 MANUAL 곡만 허용한다. 후보 연결 API는 candidate_number와 대상 Song의 tj_number가 같아야 하며, 다른 번호·MANUAL 곡으로 바꾸는 요청은 VALIDATION_FAILED로 거절한다. 이미 같은 곡에 연결되어 있으면 기존 항목을 반환한다.
[p00832] 목록 추가의 중복이면 200과 기존 item_id·현재 Playlist revision을 반환하고 위치를 바꾸지 않는다. 같은 TJ 번호의 후보와 등록곡은 entry_key가 같으므로 별도 두 항목을 만들지 않는다. 후보 연결·생성과 revision 검사는 한 트랜잭션으로 처리하고 금영 항목의 교체 API는 제공하지 않는다.
[p00833] 태그·컨디션은 /tags, /conditions에서 GET·POST·PATCH와 POST /{id}/archive를 제공한다. 오늘 목록 API와 곡의 브랜드별 번호 연결 API는 제공하지 않는다.

[p01044] 13.1 Manana 검색
[p01045] Flutter는 Spring Boot 중계를 통해 선택한 브랜드만 검색한다. 앱·서버 코드는 TJ/KY를 쓰고 Manana 어댑터에서 각각 tj/kumyoung으로 변환한다. 입력 종류 TITLE·ARTIST·NUMBER를 제공하고 각 종류를 제공자의 대응 검색 경로에 연결한다. 기본은 곡명 검색이다. 한글·영문 가수명 별칭을 확장하거나 다른 브랜드를 동시에 검색하지 않는다. [R10, R11]
[p01046] 입력 디바운스 400ms, 외부 요청 제한 시간 3초, 계정당 검색 분당 30회를 초기값으로 둔다. 번호 검색은 앞뒤 공백만 제거하고 선행 0을 유지한다. 앱은 요청 ID·브랜드·검색 조건을 함께 비교하여 이전 응답이 새 화면을 덮어쓰지 않게 한다. 빈 결과와 통신 오류는 다른 상태로 표시한다.
[p01047] 서버 응답은 brand, number, title, artist, provider, source_ref, source_token, expires_at, matched_song_id를 포함한다. matched_song_id는 TJ 번호가 계정의 ACTIVE 곡과 정확히 일치할 때만 제공한다. 금영은 null이다. 제목·가수·버전으로 별도의 병합 계산을 하지 않는다.
[p01048] source_token은 서버가 확인한 provider·brand·number·원본 정보·발급 시각에 묶은 위조 방지 토큰이며 초기 유효기간은 24시간이다. 곡 등록과 플레이리스트 후보 추가에서 서명·번호뿐 아니라 TJ 브랜드 조건도 검증한다. 금영 토큰은 조회 출처이며 곡·목록의 직접 등록 증명으로 사용할 수 없다. TJ에서 다시 선택한 결과의 토큰을 사용해야 한다. TJ 토큰이 만료되면 같은 TJ 번호를 재조회하여 검증하고, 외부 장애이면 로컬 입력·대기 큐를 유지한다. 응답을 임의 번호로 조작한 요청은 거절한다. 토큰이 사용자 자료 접근 권한을 대신하지 않는다.
[p01049] Manana의 필드는 브랜드·번호·곡명·가수·작곡가·작사가·수록 시점 등이며 구조화된 버전 코드가 없다. NORMAL·MR·LIVE는 개인 기록에서 선택한 값으로 저장한다. 곡 제목의 괄호만 보고 번호를 병합하거나 버전을 확정하지 않는다. [R11]
[p01050] 상업적 이용, 선택한 곡 정보의 보관, 검색 응답 캐시 허용 범위는 첫 배포 전에 제공자 조건으로 확인한다. 전체 곡 DB 복제는 수행하지 않는다. 검색 응답 캐시는 초기 비활성으로 두고 허용 확인 후 브랜드·검색 종류·검색어를 키로 TTL을 설정한다. 공용 캐시에는 사용자별 matched_song_id를 저장하지 않고 응답 시 계정 데이터로 계산한다. 검색 장애가 기존 곡 조회·로컬 녹음·기존 기록 수정을 막지 않게 한다. [R10]
[p01051] 13.2 월별 인기 차트
[p01052] 화면에서는 TJ·금영과 연월을 선택한다. 최초 진입은 해당 브랜드에서 게시된 가장 최근 연월을 사용하고, 브랜드를 바꿀 때 이전 연월이 없으면 사용 가능한 최신 연월로 선택값을 명시적으로 바꾼다. 이용자가 특정 월을 선택한 뒤 자료가 없으면 그 월의 빈 상태와 다른 월 선택을 제공한다. 선택한 월 표시를 그대로 둔 채 다른 기간의 순위를 내보내지 않는다.
[p01053] Manana 문서는 popular/{brand}/{period}.json에서 daily·weekly·monthly를 안내한다. monthly 지원만으로 임의의 과거 YYYY-MM 조회가 가능하다고 가정하지 않는다. 또한 개별 곡의 release 값을 차트 집계 월로 사용하지 않는다. TJ 공식 웹 차트는 최근 2년 범위의 기간 조회를 제공하지만, 웹 화면 기능이 앱에서 호출 가능한 공개 API나 데이터 재사용 허가를 의미하지는 않는다. [R12, R15]
[p01054] 차트 어댑터는 brand, year_month, period_start, period_end, is_final, source_url, fetched_at, items를 반환해야 한다. 완료 월은 해당 달 첫날부터 다음 달 첫날 직전까지의 집계다. 시간대와 기간 경계는 원본 기준을 기록한다. 현재 월 자료는 실제 월초부터 집계한 값일 때만 ‘집계 중’으로 게시한다. 최근 30일 이동 순위를 달력상의 특정 월 차트로 변환하지 않는다.
[p01055] 수집 작업은 원본의 브랜드·기간·순위 순서·전체 페이지 수집 여부·중복 번호를 검증하여 STAGING에 저장한다. 일부 페이지 실패 시 새 결과를 게시하지 않고 이전의 동일 월 게시본을 유지한다. 정상 결과만 ChartMonth와 ChartItem의 revision을 한 번에 교체한다. 원본 갱신 정책에 맞게 주기 작업을 설정하며 사용자 조회마다 원본 사이트를 수집하지 않는다.
[p01056] 조회 API는 서버에 게시된 스냅샷을 사용한다. TJ 항목의 곡 등록·목록 추가에는 13.1과 같은 source_token을 제공하고 서버에서 검증한다. 금영 차트는 직접 등록·추가를 허용하지 않고 ‘TJ에서 이 곡 찾기’로 이어진다. 응답에 선택 연월·집계 기간·최종 여부·갱신 시각·출처·revision을 포함하고 앱은 브랜드·월·요청 ID를 확인한다. 자료가 없는 월은 CHART_MONTH_UNAVAILABLE을 반환한다. 출처 장애 중에도 기존의 같은 월 자료를 갱신 시각과 함께 조회할 수 있다.
[p01057] 차트 연동 완료 조건: TJ·금영 각각에서 과거 월을 지정해 가져올 수 있는 출처·실제 요청 방식·집계 기간·이용 허용 범위를 확인하고 서로 다른 완료 월 2개 이상을 대조한다. Manana만으로 이 조건을 충족하지 못하면 허용된 공식 데이터 경로 또는 정식 제공 방식으로 어댑터를 연결한다. 허용된 수집 개시 이후의 월만 확보됐다면 그 연월만 선택 가능하게 한다. 월별 데이터 검증 없이 실시간·최근 인기 결과를 월별 차트로 대체하여 출시하지 않는다.

[p01093] R2 예상 월 비용
[p01094] 5만원 알림, 6만원 경고, 7만원 신규 업로드 잠금
[p01095] 기존 조회·재생·삭제·내보내기 유지
[p01097] 자동 대상 업로드도 사용자별 업로드량 제한을 적용한다. 한도가 초과되면 로컬 원본과 기존 서버 파일은 유지한다. 정책 재계산·정보 동기화·고정 해제·백업 다운로드는 음성 업로드 잠금과 분리한다. 자동·고정 업로드 대기열은 고정·고정 교체를 우선하고 그 안에서는 요청 시각순으로 처리한다.
[p01098] 6분 파일은 96,000bit/s × 360초 ÷ 8로 약 4.32MB이며 실제 용량은 컨테이너 등을 포함해 달라진다. 용량은 파일 수가 아닌 실제 바이트로 계산한다. R2는 저장량과 요청별 과금이 있고 직접 인터넷 송신은 무료로 안내되지만, 함께 사용하는 다른 서비스의 비용은 별개다. [R8]
[p01099] R2 월 10만원은 운영 목표이며 청구 상한 보장이 아니다. 업로드를 막아도 기존 저장·읽기 비용은 발생한다. 서버·MySQL·운영 백업·모니터링·세금과 실제 환율을 별도로 집계한다. 임시 파일과 백업 사본은 개인 1GB에서 제외되더라도 운영비에서는 포함한다. 기준 요금과 추정 비용은 매일 대조한다.

[p01120] 14.3 운영 보안과 데이터 처리
[p01121] R2 버킷은 비공개로 유지하고 최종 객체의 쓰기 권한은 검증 작업자에게만 준다. 서버 비밀값은 앱에 넣지 않는다. 파일·계정·연결·다운로드 API 모두 소유권을 검사하고 사용자 입력으로 임의 객체 키를 지정하게 하지 않는다.
[p01122] 계정 삭제·고정 교체·파일 정리의 감사 기록에는 작업자, 대상 UUID, 시각, 결과를 남긴다. 마이크 원본, 메모, 토큰, 서명 URL 전체를 로그·분석 이벤트에 남기지 않는다. 개인정보처리방침과 스토어 데이터 보안 표시는 실제 계정 정보·녹음 메타정보·파일·분석 데이터 수집과 보관 정책에 맞춘다. [R9]

[p01304] 15.3 출시 전 완료 조건
[p01305] V01–V48을 통과해야 한다. 데이터 손실·소유권·한도·기기 이전·TJ 식별·월별 차트 기간 관련 실패는 출시를 차단한다. Manana 데이터 이용 조건과 13.2의 양 브랜드 월별 차트 연동 조건, 계정 삭제 경로, 실제 개인정보 표시, 스토어의 현재 SDK·마이크 서비스 요구사항을 확인한다. 서비스 복구 시험을 완료하고 20명 베타와 전체 저장량 설정을 배포 설정에 넣는다.
[p01306] 초기 정책 변경 시 버전을 올려 앱의 보관 안내와 서버 설정을 함께 갱신한다. 무료 한도나 요금제가 바뀌더라도 기존 고정 파일을 자동 삭제하는 방식으로 전환하지 않는다.
