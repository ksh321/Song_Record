## 실행 입구

루트 [내가할일.md](../내가할일.md)는 상단에 사용자 확인 대기 건수와 `AI 현재 작업: [작업 ID] 한두 문장`, `진행 중·검증 대기` 목록을 표시한다(2026-10-01 최신 요청). 목록의 각 줄에는 정확한 작업 ID·한글 작업명·남은 단계/대기 이유와 구현 중·CI 대기·통합 검증 필요·사용자 확인 대기의 구분을 적는다. 다른 작업으로 이동해도 이전 미완료 작업은 남기고, Git·최신 검증·실제 CI를 확인해 갱신한다. 완료된 작업·완료 범위·통과 실적·최근 완료 지점은 내가할일.md에 적지 않는다. 완료 시 목록에서 제거하고 근거는 진행·검증 문서에만 보존한다. 특정 구현 범위를 전체 단계 완료로 확대하거나 미착수 예정 작업을 진행 중으로 세지 않는다. AI 설명은 체크박스/USER ID 없이 사용자 할 일과 구분하고 대기 건수에 포함하지 않는다. 상세 이력·기술 배경은 별도 진행·검증 문서에 둔다. 사용자 행동 제목은 `- [ ] USER-NNN — 작업 ID: 작업 제목`, 내용은 준비·따라 할 순서·정상 결과·회신할 결과만 쓴다. 명령은 복사 가능한 형태로 둔다. 사용자 행동이 없으면 `현재 직접 할 일 없음`을 표시하되 AI 작업 요약은 유지한다. 결과를 받으면 즉시 지우고 AI 검수/수정만 남은 항목은 사용자 목록에서 제거한다.

요청 시각·작업 ID·정확한 대상 커밋·판본·상태·알림 종류/행동·답변·완료 이력은 [요청 기록](verification/user-action-records.md)에 보존한다. 새 요청은 체크리스트와 요청 기록을 먼저 갱신한 뒤 phone-notify의 ItemId/Revision으로 알린다. 동일 항목/판본 중복 전송 금지, 변경 판본은 변경 이유 필수. 서버 접수는 실제 수신/테스트 통과가 아니다. 진행/종료 보고의 대기 수는 직접 할 일 수다.

기존 맥락 상담과 현재 작업의 직접 코드 처리는 아래 ‘상담과 코드 작업의 분리’ 절을 따른다. 각 절차의 승인·자료·연결 권한을 서로 확대하지 않는다.

저장소 루트에서 PowerShell 7로 실행한다. 명령 실행은 AI가 담당하며 로그인·USB 승인·청취만
필요 시 사용자에게 요청한다. 결과 0=해당 자동 검사 통과, 1=실패, 2=미확인/대기다.
명령이 통과해도 수동 검증을 포함한 전체 기능이 완료됐다는 뜻은 아니다.
명시적인 사용자 검증 완료 확인도 완료 근거다. [2026-09-29 사용자 확인](progress.md#user-acceptance-20260929)
범위의 기존 기능은 검증 완료로 유지하고, 과거 문서 부족만으로 실기를 다시 요청하지 않는다.
이후 변경은 변경 부분과 영향 범위만 근거에 맞게 검증한다. 현재 PC 실행 환경 상태는 별도 관리한다.

```powershell
pwsh -NoProfile -File tools/workflow.ps1 -Mode Doctor -SourcePath 'C:\Users\shoon111111\Desktop\source'
pwsh -NoProfile -File tools/workflow.ps1 -Mode Quick
pwsh -NoProfile -File tools/workflow.ps1 -Mode Mobile
pwsh -NoProfile -File tools/workflow.ps1 -Mode Api
pwsh -NoProfile -File tools/workflow.ps1 -Mode Phone
pwsh -NoProfile -File tools/github-check.ps1 -Commit <40자리SHA> -InspectPolicy -Account ksh321
```

- Doctor: 도구·버전·Docker 엔진·구독 로그인·기기·외부 원본 대응 확인. 설치/업그레이드/DB 시작 안 함.
- Quick: 원본/색인 정합성, 자동화 실패 경로 테스트, 변경 공백 오류 확인.
- Mobile: 기존 Flutter 분석과 P10 동기화 관련 테스트만 실행. 의존성 준비는
  `apps/mobile`에서 `flutter pub get --enforce-lockfile`. 잠금 파일을 바꾸는 upgrade는 하지 않는다.
  이후 작업은 범위에 맞는 테스트를 선정하고 명령을 검증 문서에 기록한다.
- Api: 서버 기존 테스트를 offline으로 실행. 캐시에 의존성이 없으면 실패를 기록한 뒤
  필요한 다운로드만 별도 실행한다. DB 생성/삭제·migration 실행을 대신하지 않는다.
- Phone: USB 연결 기기 점검. 현재 runner는 USB 한 대만 연결한 상태를 지원하며 `-DeviceId`로
  해당 기기 일치를 확인할 수 있다. 여러 USB 기기는 대기로 남긴다. 서버가 준비된 후 `-Reverse`로
  휴대폰 localhost:8080을 개발 PC로 연결할 수 있다. 앱 설치/데이터 초기화는 하지 않는다.
  새 변경에 필요한 녹음·청취·로그인 실기는 변경 영향에 맞게 선정한다. 과거 체크리스트의
  대기 문구만으로 사용자 확인이 끝난 기존 기능의 실기를 반복하지 않는다.

raw 로그·프롬프트·기계별 JSON은 `.local/workflow`에 저장하고 Git에서 제외한다.
워크플로우 실행별 로그는 runs의 고유 폴더에 보존하고 mode별 JSON은 최신 결과를 가리킨다.
JSON에는 기준 HEAD, 시작/종료 미커밋 변경, working_tree 범위, 전체 판정과 실행 예외를 남긴다.
Doctor와 Quick 결과는 독립적이다. Docker가 꺼졌어도 문서/로컬 동기화 검증은 진행할 수 있다.

## CI 휴대폰 알림 — WORKFLOW-02

아래의 기존 ‘필수 네 workflow’는 2026-10-01 변경 영향 정책 도입 전 설명이다. 현재는 네 workflow 각각의 실행 필요성을 판단하고 **필요한 검사만** 기다린다. 다음 ‘CI 변경 영향 판정’ 절이 우선한다.

전달 순서: **현재 작업 AI가 커밋·푸시 및 감시 시작 → PC의 일반 감시 스크립트가 GitHub 조회 → ntfy 서버 → 사용자 휴대폰**. GitHub가 이 대화를 자동 호출하는 구조가 아니다. 사용자가 ‘CI 성공’이라고 답해도 알림에 표시된 작업 ID·짧은 SHA와 현재 HEAD를 대조한다. 이전 커밋 성공을 새 커밋 성공으로 확대하지 않는다. 현재 AI 세션은 알림 대기 동안 종료할 수 있고, 감시 프로세스만 계속 실행한다. 이 구조가 AI 자동 재개까지 제공한다고 설명하지 않는다.

사용자는 2026-10-01 휴대폰 소리 알림을 켜고 CI 결과를 ntfy로 받도록 요청했다. AI heartbeat/정기 대화 호출 대신 일반 로컬 프로세스를 사용한다. push 뒤 AI가 현재 PowerShell 7 실행 파일로 다음 스크립트를 시작한다(사용자에게 명령 실행을 넘기지 않는다).

```powershell
# 정확한 SHA/관리 중인 작업 ID로 치환하여 AI가 실행
pwsh -NoProfile -File tools/watch-ci.ps1 -Start -Commit <40자리SHA> -TaskId P10-02 -Account ksh321
```

- 120초 간격, 최대 12시간. 기존 github-check.ps1로 SHA·workflow·필수 job을 대조하며 필수 네 workflow가 모두 판정될 때 성공/실패 알림을 보낸다. 일부 대기 중이면 전체 완료로 알리지 않는다. 조회 오류 연속 3회나 시간 제한은 미확인/감시 중단 알림이다.
- `.local/workflow/ci-watch/<SHA>.json`에 상태/PID, 별도 로그에 조회 결과를 저장한다. AI가 시작 후 실제 프로세스와 상태를 확인한다. 같은 SHA의 동시 실행은 파일 잠금으로 막고 전송 시도 UNKNOWN 또는 SERVER_ACCEPTED가 있으면 재전송하지 않는다. UNKNOWN은 사용자 미수신 확인과 재전송 요청을 받은 뒤에만 해당 기록을 별도로 보존하고 복구한다. 새 재실행 CI 알림도 같은 SHA에는 자동 중복 전송하지 않으므로 필요한 경우 명시적으로 다시 감시한다.
- 통지 내용은 작업 ID·짧은 SHA·고정 결과·대화 재개 요청뿐이다. topic/토큰/계정/기기 로그는 전송하지 않는다. GCM 자격 증명은 기존 조회 도구가 메모리에서 사용하며 ntfy topic은 기존 로컬 설정만 읽는다. 우선순위5, 서버 접수와 사람 수신은 별개다.
- 감시는 AI 토큰을 소비하는 실행이 아니며 기존 GitHub CI 자체의 사용량은 계속 적용된다. PC가 켜져 있고 절전하지 않으며 인터넷이 연결돼 있어야 한다. 자동 로그인/재부팅 후 재시작/AI 대화 자동 재개는 설정하지 않았다. 전송 실패 시 자동 반복 알림도 하지 않는다.
- 알림을 받은 사용자가 ‘CI 확인 후 이어서 진행’이라고 답하면 AI가 실제 Git/정확 SHA CI/진행 문서를 대조해 재개한다. 순차 작업의 CI 대기는 뒤 번호 작업으로 우회하지 않는다. CI 성공은 필수 실기나 전체 요구사항 완료를 대신하지 않는다.

## CI 변경 영향 판정 — WORKFLOW-08 (2026-10-01)

### 모든 작업의 구현·푸시·최종 검증 순서

P10-02에만 한정하지 않고 계획서의 모든 작업에 아래 사용자 확정 7단계 표를 적용한다. ‘제가’는 작업을 수행하는 AI를 뜻하며, 사용자는 필요한 실기 조작과 결과 전달만 담당한다.

| 순서 | 제가 해야 하는 일 | 끝나는 조건 |
|---|---|---|
| 1. 작업 선정 | 계획서 순서에서 현재 미완료 작업 하나를 선택하고 원본 요구사항·완료 기준을 확인 | 이번 작업에서 끝낼 범위가 명확함 |
| 2. 구현 | 해당 작업의 연결된 세부 구현을 끝까지 처리 | 요구사항에 필요한 코드 연결이 끝남 |
| 3. 로컬 검증·검토 | 현재 PC에서 관련 테스트를 실행하고, 실제 변경을 요구사항과 대조. 실패하면 수정 | 변경 부분과 영향 범위에 문제가 없음 |
| 4. 필요한 실기 | 자동 테스트로 확인할 수 없는 폰 조작·청취 등을 구체적으로 요청하고 결과 확인 | 필요한 사용자 확인을 받음. 문제 발생 시 수정·재확인 |
| 5. 커밋·푸시 | 위 단계가 끝난 변경을 작업 단위로 정리해 업로드 | 검증된 변경만 저장소에 반영 |
| 6. 필요한 CI | 최종 커밋의 앱·서버·DB 중 실제 영향받는 검사만 실행 | 해당 검사 성공. 실패하면 수정 후 다시 검증 |
| 7. 완료 판정 | 원본 완료 기준과 로컬·실기·CI 근거를 대조 | 그 작업을 완료로 기록하고 다음 번호로 이동 |

기존 세부 ID·완료 근거는 임의로 바꾸지 않는다. 필요한 실기가 대기 중이면 기본적으로 푸시하지 않는다. 작은 수정·중간 문서 정리마다 푸시/CI를 반복하지 않으며, 정책·문서 변경은 현재 PC의 로컬 검사만 수행한다. 실기나 CI가 필요 없는 작업은 제외 근거를 기록하고 통과 실적으로 꾸미지 않는다.

예외적으로 CI에서 만든 설치 파일로만 가능한 실기는 이유·대상 산출물·남은 완료 조건을 먼저 기록하고 CI 뒤에 수행한다. 편의를 위해 실기를 뒤로 미루지 않으며 확인 전 전체 완료 판정은 금지한다. CI 실패 수정이 실기 범위에 영향을 주면 해당 실기도 재확인한다.

중간 로컬 테스트·실패 수정·재개 기록은 계속 수행한다. 중간 저장은 원격 CI 실행 사유가 아니다. 예외적으로 CI 환경에서만 재현되는 오류 등 원격 확인이 필수라면 근거와 최소 검사 범위를 먼저 기록한다. CI가 실패하면 원인 수정 → 영향받는 로컬 검증 → 수정 커밋·푸시 → 필요한 CI 재확인으로 처리한다. 무관한 검사를 반복하지 않는다.

### 변경 영향별 원격 실행 여부

최신 사용자 확정 기준: **정책·문서 변경은 현재 PC에서 해당 설정만 검사하고, 앱·서버·DB는 실제 영향이 있을 때만 원격 CI로 검증한다.** 로컬 검사는 AI가 실행하며 Actions를 사용하지 않는다. 검사 삭제나 실패 무시는 하지 않는다. 기준 파일은 `tools/ci-policy.json`; 실제 Actions push/PR paths와 로컬 판정의 일치도 테스트한다.

| 변경 범위 | 원격 CI |
|---|---|
| 일반 문서·AGENTS.md·진행 기록·커밋 템플릿만 | 없음. 로컬 diff/내용/비밀값 확인 |
| 알림 스크립트·개발 도구·작업 상태 JSON·자료 색인 | 없음. 현재 PC에서 해당 도구·문법·정합성 검사 |
| Flutter 앱 코드·테스트·의존성·Android 설정 | CI의 Flutter 작업 |
| 서버 코드·테스트·의존성·infra | 서버 빌드·MySQL 마이그레이션·멱등/조회 DB 통합. API 계약 검증 스크립트는 계약 CI도 실행 |
| 공통 fixture/API 계약 | 앱·서버·DB·계약 검증 |
| Actions YAML·CI 선택/판정 정책 | 없음. 현재 PC에서 YAML/PowerShell 문법 및 검사 선택 로직 테스트 |
| 미분류 경로 | 먼저 실제 영향 분석. 이유 없이 전체 Actions를 실행하지 않음 |

여러 종류를 한 push에 포함하면 필요한 검사의 합집합이다. 파일 이동은 이전/새 경로, 삭제도 포함한다. CI 정책 변경 자체는 전체 검증 사유가 아니다. 앞선 c19cbd3의 전체 CI 실행 판단은 과도했으며 사용자 지시로 취소했다. 기존 P10-07 미커밋 변경은 범위에 포함하지 않는다.

1. AI는 push 전에 원격 main의 정확 SHA를 저장한다. 로컬 origin/main이 오래됐다면 fetch/ls-remote로 확인한다. 이 SHA부터 최종 커밋까지의 diff를 판단한다. PR은 merge-base 기준, 수동 workflow_dispatch는 해당 workflow 전체 검증이다.
2. 정확 SHA 확인과 감시에 `-BaseCommit <push전40자리SHA>`를 함께 전달한다. 생략/미확인은 전체 필수로 처리한다. 새 정책 도입 이전 커밋은 기존 네 CI 기준을 유지한다.
3. `NOT_APPLICABLE`은 근거 있는 제외, `NOT_REQUIRED`는 원격 CI가 필요 없는 변경이다. 통과라고 기록하지 않는다. 필요한 job의 skipped/누락은 실패 또는 대기이며 제외된 job의 skipped만 허용한다. 예상 밖 실행이 실제 실패했다면 숨기지 않는다.
4. GitHub 경로 필터의 파일 수 제한이나 비교 오류로 필요한 workflow가 실행되지 않으면 완료 판정하지 않는다. 해당 SHA에 필요한 workflow만 수동 실행하고 근거를 남긴다. 보호 규칙이 제외된 상태 검사를 요구하면 그 요구를 우회하거나 삭제하지 않고 차단을 기록한다.
5. 푸시마다 확인 기록만 추가하는 별도 커밋/전체 CI를 반복하지 않는다. 사후 실행 결과는 다음 관련 기록 커밋에 함께 보존한다. CI 불필요 문서 변경은 로컬 검증 후 기존 권한으로 커밋·푸시한다.

공식 근거: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax — paths의 제외/재포함, job 조건, 필터된 필수 검사 대기. 현재 서버 보호 설정 미확인은 별도로 유지하며 이 정책이 서버 보호 없음의 증거는 아니다.

## 커밋 푸시 CI

GitHub CLI는 설치되어 있지 않아 기존 Git Credential Manager와 GitHub REST 조회를 사용한다.
추가 API 결제는 없다. 로그인 토큰은 메모리에서만 쓰며 API 읽기 실패는 통과로 처리하지 않는다.
현재 계정이 여러 개이므로 runner는 저장소 소유자의 기존 계정을 선택하거나 `-Account`를 받는다.

마스터는 `git diff`/테스트/현재 모델 코드 검토 후 **이번 파일 경로만** add하고 staged diff를 다시 확인한다.
커밋 메시지는 다음 형식을 따른다. 새 세션도 시작 시 이 절과 루트 AGENTS.md를 읽고 동일하게 적용한다.

- 제목: `[작업 번호] 유형: 한글 작업 요약`. 작업 번호는 `docs/reference/search/tasks.json`의 정확한 계획 ID와 최신 작업 기록을 대조한다. 관리 중인 세부 ID가 있으면 `P10-04b-CONNECT`처럼 세부 ID를 쓴다. `P10` 같은 단계 번호만 사용하지 않는다.
- 독립 변경은 가능하면 별도 커밋으로 나눈다. 함께 묶어야 하면 `[ID1][ID2] 유형: 한글 요약`처럼 해당 번호를 모두 표시한다. 계획 외 변경은 기존 workflow-state/진행·검증 기록의 운영 식별자를 확인하고 기존 작업 관리 절차로 범위를 기록한다. 커밋 형식을 맞추려고 번호를 새로 추측하지 않는다.
- 본문: `작업`(ID·계획서 작업명, 세부 범위), `변경 이유와 내용`, `검증`(실제로 실행한 명령·결과, skip 구분), `남은 일`(검토·폰 테스트·CI·차단). 한글로 작성하되 코드 식별자/기술 용어는 원문을 유지한다. 아직 실행 전인 CI는 대기로 적고 이후 정확 SHA의 결과를 진행 기록에 남긴다.
- 공통 템플릿은 루트 `.gitmessage.txt`다. 이 저장소의 Git `commit.template`만 해당 파일의 절대 경로로 설정한다. 새 checkout에서 설정 여부를 확인하고 없으면 다시 연결한다. 전역 Git 설정은 바꾸지 않는다. 비대화형 실행은 같은 형식의 UTF-8 메시지 파일을 `.local/workflow/`에 쓰고 `git commit --file <메시지 파일>`로 전달한다. 템플릿의 자리표시자를 완성 메시지에 남기지 않는다.
- 2026-09-30 사용자 지시 이후 새 커밋부터 적용한다. 푸시한 커밋은 메시지를 바꾸려고 amend/rebase/강제 푸시하지 않는다. 현재 미커밋 변경에도 같은 형식을 적용한다. 구현만 된 세부 단계를 계획 작업 전체 완료라고 쓰지 않는다.
- 진행 보고·최종 보고에도 **작업 번호 — 한글 작업명**을 함께 표시한다. 제품 작업명은 계획서 원문을 유지하고 세부 범위를 덧붙인다.

일반 `git commit`과 `git push origin HEAD:<대상브랜치>`는 승인 범위다. 서버 보호가 거절하면
강제 푸시하지 않고 브랜치/PR 경로를 사용한다. rules/protection 조회 실패도 그대로 기록한다.

정확한 새 SHA에 CI, API contract, Idempotency MySQL, Development workflow 네 workflow가
실제 파일 경로로 대응하고 필수 job이 모두 있어야 한다. API 목록은 페이지 끝까지 확인한다.
각 run의 job도 success여야 하며 skipped/cancelled/missing은 통과가 아니다.
`-InspectPolicy`를 요청했는데 정책 조회가 실패하면 CI가 모두 성공해도 전체는 대기(exit 2)다.
CI 자체의 성공과 서버 보호 규칙을 모두 만족했는지는 구분한다.
기존 main만 push CI가 작동하므로 기능 브랜치는 PR 이벤트 또는 승인된 workflow_dispatch가 필요하다.
`github-check.ps1`은 단발 조회다. 실제 작업 단계가 바뀌었거나 진행 중인 검증 결과를 수집할 시점에 실행한다. 기다리기 위한 고정 간격 반복 조회 대신 충돌하지 않는 구현·검증을 진행하며 의미 있는 결과를 공유한다.
나중의 새 커밋은 이전 커밋 CI 결과로 완료 처리하지 않는다.

## 재개와 학습 기록

재개 시 Git 상태/원격/코드/진행 기록과 실행 중 프로세스를 확인한다. 작업별 구현→관련 테스트→
현재 모델 코드 검토(원본·실제 diff·실행 결과 대조)→필요 통합→커밋/푸시→정확한 SHA 필수 CI→기록 갱신을
완료하면 다음 작업을 선정한다. 난이도·위험도에 따른 모델 기준은 AGENTS.md를 따른다.
일반 작업은 Sol/medium 기본이며 속도 요청과 관측을 구분하고 미노출 속도 탐색은 반복하지 않는다.

progress의 현재 작업 표에는 상태/검증/대기 사유/사용자 요청/다음을 남긴다. 실패는 문제 ID로
누적하며 최대 추론 실패 횟수도 따로 남긴다. 기존 모델 3회 실패는 현재 작업의 실제 상향 가능 여부를 확인하는 지점이고 최대 수준
3회 실패는 해당 작업 중단·ntfy 알림 지점이다. 모델·추론·원인·수정 방법·검증 결과를 기록한다.
분석/수정 없는 동일 명령 반복은 추가 해결 시도로 세지 않는다. 권한·네트워크·도구 부재는 별도
환경 문제로 관리하며 모델 상향으로 해결했다고 하지 않는다. 기존 ENV-GRADLE-LOOPBACK 환경 실패 3회는 유지한다.
중단을 감지할 수 있으면 미커밋 변경·실행 중 프로세스·남은 검증·재개 명령을 추가한다.

폰 조작/청취/테스트, 미승인 정책 선택, 로그인/기기/권한, 최대 추론 3회 실패, 별도 승인이 필요하면
현재 작업을 사용자 응답 대기로 두고 ntfy를 보낸다. 이유/절차/기대 결과/답할 내용을 대화에 적는다.
구체적 결과나 정책 선택은 해당 조건과 대응시켜 재개하고, 결과 없는 “이어서 진행”을 통과로
기록하지 않는다. 현재 번호가 막히면 상태를 보존하고 대기한다. 독립적인 뒤 번호로 우회하지 않는다.

작업별 verification 문서에 작업/요구사항 ID, 선행 조건, 변경 파일, 명령·종료코드·실제 결과,
대상 SHA, 검수 지적과 해결, 수동 대기, 다음 ID를 적고 progress.md 최신 절을 갱신한다.
최대 추론 3회 실패/구독 한도 시 실패 시도와 재개 명령을 남긴다. 상태를 숨기거나 테스트를 약화하지 않는다.

핵심 학습 개념은 트랜잭션과 멱등성이다. 현재 P10 코드는 로컬 입력과 전송 큐를 함께 저장해
부분 저장을 막고, op_id로 같은 작업 재시도를 식별한다. 큐 후보 판정과 실제 서버 승인 반영을
분리했기 때문에 P10-02a 테스트가 성공해도 양방향 동기화 완료는 아니다.

## 후속 점검과 휴대폰 알림

[WORKFLOW-02](verification/WORKFLOW-02-followup.md)에 Docker/USB, 보호 API 제한, 모델 실행과

`tools/phone-notify.ps1`은 무료 ntfy에 작업 ID와 고정 문구만 보낸다.

-AfterReasoning max -FailureCode SchedulerRecovery`로 작업 ID와 상향 전후 모델·추론, 안전한 실패 요약·
판단 요청을 보낸다. 모델 실행 미확인은 AfterReasoning=unconfirmed, FailureCode=ModelUnavailable이다.
열거형 고정 문구만 허용해 로그·키·개인 정보를 알림에 넣지 않는다. 필요한 구체 조치/상세 시도는 대화와 문서에 적는다.
