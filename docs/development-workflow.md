# 개발 자동화 실행 안내

현재 실행 절차를 모은 문서다. **항상 적용하는 승인·금지 규칙은 [AGENTS.md](../AGENTS.md)**, 제품의 현재 위치와 완료 근거는 기존 체크포인트·계획·[진행 기록](progress.md)·작업별 검증 문서를 따른다. 제목의 날짜는 규칙 도입 시점이며 현재 재개 위치나 새 실행 승인이 아니다. 사용자 최신 지시가 우선한다.

시작 때 전체 문서를 읽지 않는다. AGENTS의 상황별 표에 따라 해당 절만 읽고, 근거 부족·충돌·변경 영향이 있으면 범위를 넓힌다. 과거 승인·지원 관측·폐기된 절차는 [운영 변경 이력](verification/WORKFLOW-01-bootstrap.md#운영-문서의-과거-설명-보존--2026-10-07)에 구분해 보존한다. 새로운 수동 진행표·task-summary.json은 만들지 않는다.

## 실행 입구

명령 실행·오류 확인·수정은 AI가 직접 수행한다. 사용자에게 파일 다운로드·수동 스크립트 실행을 넘기지 않으며 로그인·USB 승인·청취 등 실제 사람 조작만 요청한다. 설치·구축 승인은 제품 작업 시작 승인과 구분한다.

`내가할일.md`는 다음 형식으로 유지한다.

- 상단: 사용자 직접 행동 대기 건수, `AI 현재 작업: [ID] 한두 문장`, 진행 중·검증 대기 목록. 각 미완료 항목에 정확한 ID·한글 작업명·남은 단계/대기 이유·구현 중/CI 대기/통합 검증/사용자 확인 구분을 적는다.
- 이전 미완료 항목을 누락하지 않고 미착수 예정 작업을 진행 중으로 표시하지 않는다. 완료 실적·상세 기술 배경은 진행/검증 기록에만 보존한다.
- 사용자 행동만 `- [ ] USER-NNN — 작업 ID: 작업 제목`으로 적고 준비·따라 할 순서·정상 결과·회신할 결과를 구체적으로 쓴다. 필요한 명령은 복사 가능하게 작성한다. AI 작업에는 USER ID/체크박스를 붙이거나 대기 건수에 포함하지 않는다.
- 직접 할 일이 없으면 `현재 직접 할 일 없음`을 표시하고 AI 현재 작업은 유지한다. 사용자 결과 접수 후 직접 행동 항목은 즉시 제거하며 AI 검수/수정만 남은 항목은 사용자에게 남기지 않는다.
- 요청 시각·대상 커밋·ID·판본·알림/응답·완료 이력은 [요청 기록](verification/user-action-records.md)에 남긴다. 알림 전에 두 파일을 갱신한다. 동일 ID/판본 중복 알림 금지, 대상/절차 변경은 판본·이유를 함께 갱신한다. 보고의 대기 건수는 직접 행동 수이며 할 일 파일 링크를 포함한다.

저장소 루트에서 PowerShell 7로 실행한다. 아래 모드는 역할이 다르므로 매번 모두 실행하지 않는다.

| 모드 | 하는 일·한계 |
|---|---|
| Doctor | 도구·Docker 엔진·구독 로그인·USB·외부 원본 확인. 설치/업그레이드/DB 시작 없음. 실제 source 경로 확인 후 `-SourcePath` 지정 |
| Quick | 원본/색인 정합성·개발 도구 회귀·공백 검사 |
| Checks | 기존 계획의 필수 로컬 검사 일괄 실행. 아래 전용 절 참조 |
| Mobile | 기존 Flutter 분석·지정 동기화 테스트. 전체 제품 검사로 간주하지 않음 |
| Api | 서버 테스트를 offline으로 실행. 캐시 누락은 필요한 다운로드만 별도 처리하며 DB 생성/삭제·migration 실행을 대신하지 않음 |
| Phone | USB 한 대 연결 확인. `-DeviceId` 일치 확인, `-Reverse`는 서버 준비 후 localhost:8080 연결. 앱 설치/초기화·실기 판정 없음 |
| Usage | 기존 로그의 단계별 사용량 집계. AI·네트워크·제품 실행 없음 |

필요한 명령 예:

```powershell
pwsh -NoProfile -File tools/workflow.ps1 -Mode Doctor -SourcePath '<현재 확인한 외부 source 경로>'
pwsh -NoProfile -File tools/workflow.ps1 -Mode Quick
pwsh -NoProfile -File tools/workflow.ps1 -Mode Checks
pwsh -NoProfile -File tools/workflow.ps1 -Mode Usage
```

Flutter 의존성 준비는 `apps/mobile`에서 `flutter pub get --enforce-lockfile`을 사용하며 임의 upgrade를 하지 않는다. 제품 검사는 해당 변경/계획에 맞게 선정한다. 일반 검사 결과 0=해당 검사 통과, 1=실패, 2=미확인/대기이며 수동 검증을 포함한 제품 완료와 구분한다.

raw 로그·프롬프트·기계별 JSON은 Git 제외 `.local/workflow/`에 저장한다. 실행별 고유 폴더와 mode별 최신 결과에는 기준 HEAD·시작/종료 변경·실제 종료 코드·예외를 남긴다. Doctor 환경 실패가 무관한 문서/로컬 검증의 실패를 뜻하지 않는다.

## CI 휴대폰 알림 — WORKFLOW-02

**원격 CI가 필요한 일반 push 뒤에만** 아래 절의 영향 판정에 따라 감시한다. 정책·문서·개발 도구만 바뀌면 감시하지 않는다.

```powershell
pwsh -NoProfile -File tools/watch-ci.ps1 -Start -Commit <최종40자리SHA> -BaseCommit <push전40자리SHA> -TaskId <현재작업ID> -Account ksh321
```

- AI가 push와 감시 시작을 수행하고 실제 프로세스·상태를 확인한다. 이후 일반 로컬 프로세스가 기존 github-check로 120초 간격 조회한다. 기다리기 위한 AI 호출·heartbeat는 만들지 않는다.
- 필요한 workflow/job 전부 판정 시 또는 조회 오류 연속 3회/12시간 제한 시 커밋별 알림을 한 번 시도한다. 대기·미확인은 성공이 아니다. 제외된 검사까지 기다리지 않는다.
- `.local/workflow/ci-watch/<SHA>.json`과 로컬 로그에 PID/상태를 보존한다. 같은 SHA 동시 감시는 잠금으로 막는다. UNKNOWN/SERVER_ACCEPTED는 자동 재전송하지 않는다. 미수신 확인과 재전송 요청 후 기존 기록을 보존해 복구한다. 같은 SHA 재실행 CI의 재감시는 명시적으로 처리한다.
- 기존 GCM 인증·ntfy 연결만 사용한다. 작업 ID·짧은 SHA·고정 결과만 보내고 토큰·topic·기기 로그를 노출하지 않는다. 우선순위 5이며 서버 접수와 사람 수신은 별개다.
- PC 종료/절전·네트워크 단절 중 감시, 재부팅 후 자동 시작, AI 대화 자동 재개는 보장하지 않는다. 사용자 회신 후 실제 Git·대상 SHA·필수 CI·진행 근거를 다시 대조한다. CI 대기로 뒤 번호에 착수하지 않는다.

## CI 변경 영향 판정 — WORKFLOW-08 (2026-10-01)

### 모든 작업의 구현·푸시·최종 검증 순서

| 순서 | AI 작업 | 끝나는 조건 |
|---|---|---|
| 1 | 계획 순서에서 현재 미완료 작업 선정 | 범위·선행 조건·원본 완료 기준 확인 |
| 2 | 같은 P번호의 연결 구현 완료 | 필요한 코드·데이터 흐름 연결 완료 |
| 3 | 필요한 로컬 검사 일괄 실행 후 현재 모델의 별도 코드 검토 | 실제 변경·원본 기준·검증 대조, 지적 해결 |
| 4 | 필요한 실기 안내·결과 확인·문제 수정 | 필요한 사람 조작 결과 확인 |
| 5 | 검증한 파일만 커밋·푸시 | staged diff·비밀값·변경 범위 확인 |
| 6 | 최종 SHA의 필요한 CI 확인 | 영향받는 필수 workflow/job 성공 |
| 7 | 모든 완료 근거 대조·기록 | 해당 작업 완료 후 승인 범위의 다음 번호로 이동 |

기존 세부 ID·완료 근거는 유지한다. 작은 편집마다 전체 검사·문서·커밋·CI를 반복하지 않는다. 실제 오류 확인용 중간 검사·최소 재개 기록은 허용한다. 체크포인트/중간 저장 자체는 push·CI 사유가 아니다.

필수 실기가 대기면 기본적으로 푸시하지 않는다. CI 산출물로만 가능한 실기는 이유·대상 산출물·남은 완료 조건을 미리 기록한 경우만 CI 뒤에 수행한다. 미확인 상태는 완료가 아니다. CI에서만 재현되는 오류 등 중간 원격 확인이 필수면 이유·최소 범위·횟수를 기록한다. 실패 수정 후 영향받는 로컬 검사와 필요한 CI를 다시 확인하고, 실기 영향이 있으면 해당 실기도 재확인한다.

### 변경 영향별 원격 실행 여부

판정 기준은 `tools/ci-policy.json`이다. Actions 경로 필터와 로컬 판정의 일치도도 검증한다.

| 변경 범위 | 원격 CI |
|---|---|
| 일반 문서·AGENTS·진행 기록·커밋 템플릿 | 없음. 로컬 내용/diff/비밀값 확인 |
| 개발 도구·알림·작업 상태·자료 색인 | 없음. 해당 도구·문법·정합성 로컬 검사 |
| Actions YAML·선택/판정 정책 | 없음. 로컬 YAML/PowerShell 문법·선택 로직 검사 |
| Flutter 앱·테스트·의존성·Android 설정 | Flutter 관련 작업 |
| 서버·테스트·의존성·infra | 서버·DB 검증. API 계약 검증 스크립트는 계약 CI도 포함 |
| 공통 fixture/API 계약 | 앱·서버·DB·계약 검증 |
| 미분류 | 실제 영향 분석 후 결정. 무조건 전체 실행 근거로 쓰지 않음 |

1. push 전 원격 HEAD를 실제 fetch/ls-remote로 확인해 BaseCommit으로 저장하고 최종 SHA까지 여러 커밋·삭제·이동 전후 경로를 모두 판단한다. PR은 merge-base, 수동 dispatch는 해당 workflow 전체 기준이다.
2. github-check/watch-ci에 `-BaseCommit`을 전달한다. 기준 누락/미확인은 전체 필수이며 마지막 커밋만 비교하지 않는다. 정책 도입 전 커밋의 기존 네 CI 기준은 소급 변경하지 않는다.
3. 범위가 섞이면 필요한 검사의 합집합이다. `NOT_APPLICABLE`은 근거 있는 제외, `NOT_REQUIRED`는 원격 CI 불필요이며 통과 실적이 아니다. 필요한 job의 누락·skipped·취소·실패·진행 중은 완료를 막는다. 제외된 job의 skipped만 허용한다.
4. 경로 필터 제한/비교 오류로 필요한 workflow가 누락되면 해당 SHA의 필요한 실행만 보완하고 근거를 남긴다. 예상 밖 실제 실패도 숨기지 않는다. 서버 보호가 제외된 검사를 요구하면 차단을 기록하고 보호를 삭제/우회하지 않는다.
5. 확인 기록만을 위한 별도 커밋·전체 CI를 반복하지 않는다. 사후 결과는 다음 관련 기록에 함께 보존한다. CI 불필요 변경도 로컬 검증 후 기존 승인 범위로 커밋·푸시한다.

GitHub 필터 근거는 [공식 workflow 문법](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)을 따른다. 로컬 정책은 실제 서버 보호 설정의 증명이 아니다.

## 자료와 변경 계약

[manifest](reference/search/manifest.json)로 원본 6개·외부 파일·해시·검색본을 연결한다. [작업 색인](reference/search/tasks.json), [설계 검색본](reference/search/design.txt), [계획 검색본](reference/search/plan.txt)은 관련 위치를 찾기 위한 자료이며 원본을 대체하지 않는다. Word 표기는 페이지가 아닌 XML 문단 번호다.

```powershell
python tools/index_sources.py --check
python tools/index_sources.py --check --source <실제source경로>
```

텍스트 해시는 CRLF→LF 정규화, DOCX는 원본 바이트 기준이다. 승인된 내용/해시와 다르면 덮어쓰지 않고 확인한다. 원본 변경 승인 후 기준과 색인을 갱신한다. CI 원본 검사는 저장소 파일을 사용하며 개인 PC 경로를 요구하지 않는다. 승인된 결정·계약만 해당 범위에서 원본보다 우선한다.

[사용자 기존 기능 검증](progress.md#user-acceptance-20260929)과 [D06/P09-07b-C1 완료](verification/P09-07b-C1-fixed-conditions.md)는 보존한다. 과거 문서 부족·대기 문구로 되돌리지 않는다. D12 기간별 차트·기존 탭 재선택 등 후속 계약도 승인 범위만 적용하며 기존 데이터 삭제/강제 매핑 권한으로 확대하지 않는다.

## 현재 작업 모델과 속도

현재 모델이 구현·테스트·별도 검토를 직접 수행한다. 단일 제어기는 같은 스레드를 이어가며 호출별 모델을 지정한다. 새 Worker/Reviewer·하위 에이전트·Ultra는 금지하고 폐기된 run-agent 경로를 재사용하지 않는다.

일반 Sol/medium, 복잡한 연결 Sol/high, 인증·계정 격리·동기화·삭제·DB 핵심과 불명확한 판단/핵심 검토 Astra/high 이상을 따른다. 세부 분류는 아래 모델 선택 절, 실패 제한은 B안 절을 따른다. 중요 논리 지적은 실패 한도 전에도 상향 필요성을 검토한다.

`model/list`와 실제 `turn_context`를 대조해 요청·설정 수락·관측값을 구분한다. 미노출은 unknown이며 반복 탐색하지 않는다. 최고 수준 연결 근거 없이는 추가 해결 시도를 열지 않는다. 매 호출 Standard(default), Fast 끔을 유지한다. 현재 채팅의 모델이나 서비스 처리 속도를 바꿨다고 추정하지 않는다. 구독 로그인만 사용하며 결제·리셋 금지는 AGENTS를 따른다.

## 커밋 푸시 CI

- 구현·검사·현재 모델 검토·필수 실기 후 이번 범위 파일만 명시적으로 stage한다. staged diff·비밀값·소스 변경 여부를 다시 확인한다.
- 제목은 `[정확한 작업 ID] 유형: 한글 작업 요약`이다. 계획서와 기존 세부 ID를 대조하며 큰 P단계 번호만 쓰지 않는다. 독립 작업은 가능하면 나누고 함께 묶으면 `[ID1][ID2]`를 표시한다. 계획 외 작업은 기존 관리 ID·승인 범위를 확인/등록하며 메시지를 위해 임의 ID를 만들지 않는다.
- 한글 본문에 작업/계획서 작업명·변경 이유/내용·실제 검증 명령/결과·skip/대기/남은 일을 적는다. `.gitmessage.txt`를 저장소 로컬 템플릿으로 사용하고 전역 설정을 바꾸지 않는다. 비대화형 커밋은 UTF-8 메시지 파일과 `--file`을 사용한다. 자리표시자를 남기지 않는다.
- 일반 commit/push는 승인 범위다. 사용자 변경을 섞거나 이미 푸시한 이력을 메시지 변경 목적으로 amend/rebase/강제 푸시하지 않는다. 서버 거절은 우회하지 않고 필요한 브랜치/PR 경로를 검토한다.
- GitHub 조회는 기존 GCM과 도구를 사용한다. 계정은 ksh321이며 브라우저 로그인만으로 GCM 인증 갱신을 보장하지 않는다. 재로그인 필요 시 먼저 AI가 오류·현재 화면을 확인하고 실제 선택/승인 절차를 준비한다.
- 필요한 CI만 `tools/github-check.ps1 -Commit <SHA> -BaseCommit <기준SHA>`로 확인한다. API 목록/각 run의 job을 끝까지 확인하고 정확 SHA·workflow 경로·필수 job을 대조한다. 이전 커밋 성공을 새 커밋에 적용하지 않는다.
- `-InspectPolicy` 조회 실패는 보호 없음이 아니며 전체는 미확인/대기다. CI 성공과 서버 보호 충족 여부를 구분한다. 현재 저장소의 main 외 경로는 PR 이벤트 또는 승인된 dispatch 필요성을 확인한다. 정상 대기는 CI 알림 절의 일반 프로세스를 사용한다.
- 보고에도 ID·한글 작업명·변경 이유·파일·검증·남은 일·관련 학습 개념을 설명한다. 코드 구현만으로 전체 완료라고 쓰지 않는다.

## 재개와 학습 기록

재개 시 현재 Git/원격·코드·프로세스·진행/검증 기록을 대조해 기존 호출이나 명령을 중복 실행하지 않는다. 이전 상태를 현재 사실로 단정하지 않는다.

작업별 검증 문서에는 ID·요구사항·선행 조건·변경 파일·명령/종료 코드/실제 결과·대상 SHA·검토 지적/해결·실기 대기·다음을 남기고 progress의 해당 기록을 갱신한다. 모델 선택 이유·요청/관측 구분도 보존한다. 자기 커밋 SHA는 커밋 후 또는 Git 이력으로 확인한다.

중단 시 문제 ID·원인·상향 전후 모델/추론·수정 방법·실패 횟수·미커밋·실행 프로세스·남은 검사·담당자·재개 조건/명령을 기록한다. 환경 문제와 코드 실패를 분리하고 기존 ENV-GRADLE-LOOPBACK 3회 이력도 초기화하지 않는다. 사용자 수정 회신은 실제 코드/결과와 대조한다.

사용자 검증 결과는 명시한 범위만 인정한다. “폰 연결”은 실제 연결을 확인하고, 결과 없는 “진행해”는 실기 통과가 아니다. 제품 작업에서는 트랜잭션·멱등성 등 실제 구현에서 선택한 개념과 이유를 설명하며 일부 큐 테스트 성공을 양방향 동기화 전체 완료로 확대하지 않는다.

## 후속 점검과 휴대폰 알림

AI가 해결 가능한 명령·환경 오류는 먼저 직접 확인하고 처리한다. 실제 사람의 로그인·USB·실기·정책 판단, AI 해결 불가 중단, 한도 도달 및 승인 범위 완료 후 종료는 폰 알림 대상이다. 중단에 필요한 조작을 사용자가 다시 질문해야만 알 수 있도록 넘기지 않는다.

`tools/phone-notify.ps1`의 기존 무료 ntfy 설정·고정 문구를 사용한다.

| 상황 | 모드·종류·필수 근거 |
|---|---|
| 최초 연결 시험 | Init → 앱 설치/알림 허용 → USB Subscribe → Send/Trial → 실제 수신 회신 → Confirm |
| 실기 요청 | Send/PhoneTest, 사전 등록된 ItemId/Revision 및 Action=PhoneSteps |
| 실제 사람 개입 | Send/Intervention, 요청 기록의 ItemId/Revision/Action |
| 최대 수준 실패·설정 개입 | Send/Escalation, 상향 전후 모델/추론·안전한 실패 분류. 미확인 상향은 unconfirmed |
| 승인 범위 완료 | Send/Completion, 실행별 CompletionKey. USER 항목을 만들지 않음 |

알림 전에 실제 기기/앱/화면·선택할 계정/버튼·준비·순서·정상 결과·회신 내용을 대화와 요청 기록에 작성한다. GitHub 계정은 ksh321이다. 미확인 절차를 꾸미지 않는다. 자세한 절차가 아직 없어도 실제 해결 불가 중단 알림은 누락하지 않고 확인 사실/불확실성을 구분해 AI가 후속 안내를 보완한다.

provider 승인 요청 자체는 사람 도움 필요 판정이 아니다. call.requests를 보존한 WAITING_AI에서 아래 자동 복구 절의 등록 명령 처리 또는 같은 스레드의 AI 확인을 수행한다. 임의 자동 승인·보안 우회는 금지한다. 실제 개입 필요·복구 실패·불확실한 실행이 확인되면 근거와 필요한 행동을 저장하고 폰으로 알린다.

전송 의도를 먼저 저장하고 UNKNOWN/동일 ID·판본/완료 키는 자동 재전송하지 않는다. 완료 전송 실패는 제품 완료 여부와 분리해 로컬·대화로 알린다. 서버 접수는 폰 수신이나 실기 통과가 아니다. Confirm은 해당 Trial 수신 회신 뒤에만 한다. topic·토큰·기기 원본 로그는 알림/커밋에 넣지 않는다. 기존 수신 확인은 phone/confirmed.json으로 별도 보존한다.

## 리셋권 — 현재 유효한 지침

자동 리셋권 사용은 금지한다. 한도 도달 시 공식 한도 결과·상태·실패 이력·재개 정보를 저장하고 내가할일에 사용자 직접 갱신 요청을 등록한 뒤 ntfy로 알린다. 갱신 회신 후 공식 한도를 확인한다. 과거 허용·사용량 기록은 현재 권한/잔여량이 아니며 다른 과금 경로로 전환하지 않는다.

## 작업 선택·차단·종료

**종료 판단 전 필독: 승인 범위의 현재 순서에서 실행 가능한 단계나 진행 중 실행이 있으면 계속한다. 현재 번호가 막히면 뒤 번호의 실행 가능 여부와 관계없이 상태 저장·필요 알림 후 종료한다.** 단계 보고·문서 저장·사용자 할 일 0건은 종료 사유가 아니다.

1. 실제 Git·프로세스·최신 근거와 원본 tasks.json 전체를 workflow-state coverage에 대조한다. preserved_scope는 기존 검증 보존이며 후속 미구현의 완료 판정이 아니다. tracked는 실제 실행 단계에 연결하고 미확정은 unassessed로 분석한다.
2. 계획서 번호 순서로 가장 앞선 미완료 작업의 연결 흐름을 끝까지 처리한다. `priority_order`·`sequence_start`는 최신 승인/완료 근거와 대조한다. 이미 뒤 번호에서 만든 변경은 보존하고 우선 실행하지 않는다. A1→B1→A2 전환이나 차단 우회용 후속 단계 신설은 하지 않는다.
3. 기존 세부 ID·미완료 범위·선행 조건·검증 기준을 유지한다. 새 작업은 원본 ID 단위로 묶으며 파일/함수 차이만으로 쪼개지 않는다. 새 세부 ID는 별도 승인·독립 의존관계·배포/검증 경계가 있을 때만 등록한다.
4. 차단에는 해당 단계·근거·읽기/쓰기 파일·권한·행동·담당자·재개 조건을 남긴다. 전체 단계 보류는 계획서의 실제 선행 근거를 확인한다. 폰/CI 대기를 다른 작업의 선행 조건으로 임의 추가하지 않으며 현재 번호의 필수 대기는 다음 번호 착수를 막는다.
5. 완료·차단·회신 때 근거/권한/파일 소유 범위와 상태/색인을 갱신하고 `python tools/select_work.py`를 실행한다. 실행 직전 현재 단계를 active로 예약해 다시 확인한다. CONTINUE이면 실제 작업을 수행한다. IN_PROGRESS는 결과 수집/계속 대상이며 재실행·종료 허용이 아니다.
6. 종료 전에 이 절과 AGENTS의 종료 원칙 → 최신 관련 기록·전체 미완료 의존관계·실제 프로세스 → `python tools/select_work.py --check-stop` 순서로 확인한다. ready/active가 있으면 계속한다. 선택기 결과만으로 필수 검토나 제품 완료를 선언하지 않는다.
7. 진짜 차단·한도·세션 제약은 구체적 사유·미커밋·프로세스·남은 검증을 기록한다. 응답 대기 sleep/반복 조회를 만들지 않는다. 단순 종료 결정을 실행 한도로 포장하지 않는다.

기존 Goal을 이어갈 때 `get_goal`로 실제 상태를 확인하고 중복 생성하지 않는다. 상태 변경은 도구 조건을 따른다. 과거 등록 기록은 활성/자동 재개·무중단 보장이 아니며 Goal도 승인·비용·검증·데이터 경계를 넓히지 않는다. 미검증 Stop hook을 작동한다고 주장하지 않는다.

## 상담과 코드 작업의 분리

과거 결정/해결 맥락이 불명확할 때만 저장된 결정·검증 근거를 먼저 읽고 상담한다. 일반 구현·검토는 현재 모델이 직접 수행한다.

| 구분 | 대상·목적 |
|---|---|
| 과거 맥락 상담 | 기존 ChatGPT ‘노래 기록 → 워크플로우 순서 검토’에 불명확한 결정·해결 과정 질문 |
| 구현 | 현재 작업 모델이 승인 원본·현재 코드에 따라 직접 구현/검사 |
| 검토 | 현재 모델이 별도 단계에서 실제 diff·원본·결과 대조. 독립 검수자/새 Reviewer가 아님 |

대상·목적·전달 자료·현재 열람 가능 여부를 명시한다. 연결은 현재 도구로 확인하며 이전 성공으로 권한을 승계하지 않는다. 상담 대상 식별자는 프로젝트 `g-p-6aa2326df0708191aeb49fb5224c911d`, 대화 `6abb447a-d7f0-83ee-94bc-b57f744407c5`다. 새 Codex 대화로 대체하거나 ChatGPT 대화에 Codex 전용 wait_threads를 적용하지 않는다.

list_projects/list_threads/read_thread로 실제 대상과 읽기 연결을 확인한다. 사용자에게 승인된 상담 범위의 질문만 send_message_to_thread로 전달하고 read_thread로 실제 답변을 확인한다. 새 대화를 만들거나 응답 대기용 반복 조회를 만들지 않는다.

접속 불가는 목표/문제·확인/미확인·시도/결과·최소 코드/설정/오류·후보/구체 질문을 비밀값 없이 작업 검증 문서에 작성한다. 실제 사용자 전달이 필요할 때만 할 일에 정확한 대화 이름·질문 링크·회신 방법을 적고 알린다. 비밀번호·토큰·개인 데이터·기기 원본 로그·서명 키/로그인 설정은 제외한다.

답변은 현재 코드/로그·승인과 대조해 질문/답변 ID·날짜·채택 범위·불확실성을 결정/검증 문서에 남긴다. 이미 확인한 맥락은 반복 질문하지 않는다. USER019 별도 검수 승인은 과거 이력이며 USER020 새 Worker/Reviewer 전달 요청은 취소됐다. 이 승인을 재사용하거나 새 전달 승인을 요구하지 않는다.
